# The axiom binary

> **Files:** `backend/`, `qml/services/core/BackendManager.qml`, `qml/services/core/DevManager.qml`, `qml/components/views/Settings/DeveloperOptionsCard.qml`, `qml/components/views/Settings/DevTreeCard.qml`, `qml/components/views/Settings/DevConfigDiffCard.qml`, `qml/components/bar/widgets/DevMode/DevMode.qml`, `qml/config/json/backend.json`, `scripts/check_go.sh`, `scripts/generate.sh`, `scripts/dev/fixtures.py`
> **Related:** [Config manager](../core/config-manager.md), [Packaging](../packaging.md), [Testing](../testing.md)

`axiom` is one Go binary (source in `backend/`, rules in `backend/AGENTS.md`). It is being brought in in stages; this page says what exists now and grows with it.

### What it is for
- The **parent process** of the shell (`axiom run`) and the greeter (`axiom greeter`): it starts quickshell, restarts it when it crashes, and keeps one instance per display.
- The **owner of config.json**: loading, migrating, validating and writing, with the shell as a client over a unix socket (NDJSON JSON-RPC 2.0).
- The **command line**: `axiom config …`, named commands and `axiom ipc <target> <fn>` passthrough to the shell.
- Later, the side effects that need a Wayland connection (idle, gamma, clipboard).
- **The direction:** Quickshell ends up only drawing Wayland windows (layer shell, popups, the session lock, focus grab, screencopy) and running the QML. Next to move here are Quickshell.Io's side effects (processes, file views, sockets, IPC handlers): `scripts/quickshell-io-allowlist.json` lists the files still using them, and `check_structure` keeps the list from growing. D-Bus services (notifications, tray, UPower, Mpris, Polkit, Bluetooth, networking) and native-library ones (Pipewire, PAM, which would need cgo) are planned, not scheduled. The stages, and the rules for each move: [roadmap](roadmap.md).

### What exists now
- **`axiom run [--dev] [--tree DIR]`**: the daemon for `$WAYLAND_DISPLAY`.
  - **The tree** is a folder holding `qml/shell.qml` and `qml/config/` (`tree.IsTree`): `--tree`, else `$AXIOM_TREE`, else the nearest one up from the working directory, else the installed one (`tree.Find`; `tree.Installed`: `axiom-shell` under `$XDG_DATA_HOME`, then under each of `$XDG_DATA_DIRS`, so `~/.local/share/axiom-shell` from install.sh before a package's `/usr/share/axiom-shell`): a compositor's autostart runs it from `$HOME`. Nothing looks in `~/.config/quickshell`. The tree found is the **install tree** (self-update's and the greeter's); dev mode may run another (below).
  - It takes the display's instance lock, then (no handoff) takes the session start's dev-mode decision (below), and builds the schema from the tree (`qml/config/schema/`; `tree.BuildSchema` reads it relative to `qml/`).
  - It opens the config, writes both for the shell into `$XDG_RUNTIME_DIR/axiom/<display>/`, serves the socket there, and supervises `qs -p <tree>/qml` (`daemon.ShellCommand`, also the greeter's: its `--log-rules` drops Qt's text-input-v3 warnings, which are Qt's own bookkeeping going stale when a focused surface hides).
  - Supervision: restart with a growing delay after a crash, give up after 5 crashes in a minute, stop an orphan an earlier daemon left (its process group, matched by its exact command line; never the shell a re-exec adopts). A run that ended on its own is `OnExit`'s, a stop the supervisor asked for `OnStop`'s. qs runs with transparent huge pages off, through a re-exec of the running image that sets the flag and execs it (`supervise.ExecNoTHP`; [memory](../core/memory.md) › Transparent huge pages).
  - It holds its own Wayland connection (`wayland/outputs` on a `wire.Conn`) and stops when the compositor closes it: a daemon outliving its session would hold the display's lock, and the next session's `axiom run` would find it taken. If that connection fails otherwise (a protocol error), an idle one (`wire.Watch`) still watches.
  - The shell gets `AXIOM_SOCKET`, `AXIOM_SCHEMA`, `AXIOM_CONFIG`, `AXIOM_TREE` (the tree it runs on), `AXIOM_INSTALL_TREE` (the installed tree), `AXIOM_BIN` (the installed binary, never a dev build) and, read at each start, `AXIOM_INCOMPATIBLE` while the tree's schema isn't the binary's and dev mode is off.
  - `--dev` starts in dev mode whatever was chosen last, and logs to the terminal (and the shell's output with it).
  - SIGINT, SIGTERM and SIGHUP (its terminal closed) stop it cleanly, its shell with it (`cli.Main`); SIGHUP stays ignored when it started ignored (`nohup`).
- **The daemon's parts** (`backend/internal/daemon/tasks.go`): each piece is a `part` (`core`, `config`, `ipc`, `sharing`, `compositor`, `topics`, `tools` (one-off calls: `deps.check`, `tz.*`, `media.art`, `screenshot.stitch`, `system.kill`, `net.addresses`, `filepicker.pick`, `notify.send`), `dev mode`): the RPC methods it registers, a `run(ctx)` started on the daemon's `tasks`, and an `onConfig` told of every store event in order. A part's methods are also listed in `methodSets` (`contract.go`), from which `BuildContract` builds the registry without starting anything (`backend/internal/daemon/contract_test.go` checks the two agree; [protocol](protocol.md) › Changing the protocol). Every goroutine is started through `tasks.Go` (the locker gets it as `lockscreen.Options.Go`) and `Run` waits for all of them; work that must not overlap itself (`saved.Changed`, dev builds) is a `kicker`.
- **Store events** are queued under the change lock and delivered after it's released, one at a time in revision order: a subscriber may read and write the store (its own event is delivered after the one it was handed).
- **Pushes go by topic**: the hello's `subscribe` is `true` (every topic, what the shell asks), `false`, or a list of `config` (`config.changed`, `config.state`, `schema.changed`, `schema.error`), `saved` (`saved.state`), `daemon` (`daemon.state`, `dev.state`). A new topic or method needs no protocol bump; changing what an existing one means does. Whole-state pushes are latest-wins ([protocol](protocol.md) › The wire). Polled data is a separate opt-in: a connection subscribes to each [polled topic](protocol.md#polled-topics) (`backend/internal/topics`) by itself.
- **Writable or read-only**: a tree whose schema isn't the one the binary embeds (or any tree, from a binary built without its embedded schema) runs read-only (`compatible: false` in the hello, config writes refused) unless dev mode is on. In dev mode too while the tree's schema is a config version past the binary's migration steps (`aheadReason`): a save would prune the config against the new shape before the step that moves its keys runs; the dev build that has the step re-execs and lifts it (`rebuildSchema` pushes `daemon.state` with each new schema). It changes at runtime with dev mode (`daemon.state`); the shell's start-up notice (`BackendManager.incompatible`, `qml/shell.qml`) clears once it becomes writable, but never comes back while the shell runs.
- **Dev mode** (`backend/internal/daemon/dev.go`, `devbuild.go`, `devstart.go`, `devsync.go`; `backend/internal/devconfig`; `axiom dev status|on|off|rebuild|set|options|config`, `dev.get|set|rebuild`, `dev.config.*`; `DevManager`, Settings › Development, the `DevMode` bar widget, `/dev`) runs a **dev tree**, any clone with the Go source (`axiom dev set <path>`: absolute, symlinks resolved, `tree.IsTree` plus `backend/go.mod`; `--clear` unsets it while off), on **its own binary, built from it**, and **its own config**. The choice is kept in `$XDG_STATE_HOME/axiom/dev.json` (`{enabled, tree, options}`; state, never config.json; written read-modify-write, keeping keys it doesn't know) until turned off; `options` alone shows Settings' Development category (whether dev mode is on or not). With no axiom running, `dev set` and `dev options` write it themselves (`daemon.SaveDevChoice`, as install.sh runs `dev set` before the first start); on and off need a running axiom. `dev on` needs a dev tree. `--dev` forces dev mode on for one run of the tree `axiom run` found: never saved (a `dev.set` saves `enabled` only when it's asked for), and with no dev tree its options still change.
  - **Images.** A daemon image runs a tree, a config folder and dev mode (`image`). The **dev image** is the dev build (`$XDG_STATE_HOME/axiom/dev/axiom`) on the dev tree and the dev config (`$XDG_CONFIG_HOME/axiom/dev/`); `dev.state.active` says it runs. Dev mode on but not active means the installed image runs the install tree on the live config while the dev build is built. Off, from the dev image, re-execs into the installed binary on the install tree and the live config.
  - **One build queue** (`devMode.builds`, a kicker, running while a buildable dev tree is set): an edit, `dev.rebuild`, a stale build at the session start or at a carried re-exec of the installed axiom with dev mode on (a rebuilt installed binary, a self-update: the build running died with the exec), `dev on` and a new dev tree while on all kick it (the last two, and the starts, through `startKick`, taken by the builds the watchers restart with, so a kick never lands in the ones being cancelled). A build runs `go generate ./internal/assets` + `go build` into the dev binary, checks it runs (`version --json`), records it in `$XDG_STATE_HOME/axiom/dev/build.json` (`{tree, fingerprint, commit, dirty, handoff, protocol, at}`) and re-execs into the dev image, the shell restarted onto the dev tree. `dev.rebuild` works with dev mode off too: it only builds and records (the next `dev on` finds the build fresh and switches at once). It doesn't switch when dev mode is off, the dev tree changed (`gen`), another switch was scheduled (`switching`, which also refuses a `dev.set`), or the source changed (`devMode.edited`: the edits' own kick builds again, so the image is never older than the tree). A failed build keeps the running image, its output in `dev.state.lastBuild` and a notification. A build whose `buildinfo.Info.Handoff` is below 2 is never exec'd ("this tree predates dev trees: merge main"), so an old branch can't open and migrate the live config; a build that replaced the dev binary but isn't recorded (that refusal, or no fingerprint) removes `build.json`, so the old record never vouches for it. Builds need the dev tree's `backend/go.mod` and `go` (`available`, else `unavailable` says why).
  - **Fresh** is a content hash of the dev tree's build inputs (`fingerprint`, over the files `isBuildInput` takes: the Go source and module files under `backend/` and the files the binary embeds from `qml/`; one predicate with `watchSource`), not git's dirty state, matched with build.json's tree and the binary there (`buildFresh`). `dev.state.build` holds it with the build's commit; `branch`, `commit` and `dirty` are the dev tree's checkout (`gitInfo`, read at a switch or a build, never polled).
  - **The session start** (`devstart.go`, `startPlan`, pure): at login the installed axiom starts first. With dev mode on, a dev tree and no `--tree`/`$AXIOM_TREE`, a fresh build is exec'd into at once, before the schema, the store or the shell, with a `fresh` handoff; a missing or stale one runs live now, builds in the background, then switches. The **boot guard**: before every exec into the dev image (that one, and a runtime switch's re-exec: `dev on` with a fresh build, a build finishing; `reexecInto`) `$XDG_STATE_HOME/axiom/dev/boot.json` is written naming the build (a failed exec leaves none), and the dev image clears it at its shell's hello; a marker still there for the same build at the next start keeps the session live, with a notification, until it's built again. A dev image that fails before it serves (its tree's schema, its config) execs back into the installed binary (`fallBackLive`): from a session start with no handoff; from a runtime switch with the handoff it carried (`fallBackCarried`: the instance lock, the socket, the shell, the commands, and the live config's writer lock taken again, waiting up to a second for a child of its own still between its fork and its exec to let go of the copy it holds), onto the install tree and the live config in dev mode, whose `startPlan` finds the marker and stays live, told the same way (decided 2026-11-04). A dev tree gone stays live, said the same way.
  - **Watchers**, by (on, dev tree): the builds while a buildable dev tree is set; the dev tree's build inputs while on (`watchSource`, 1 s of quiet); the schema's YAML only in the dev image (`watchSchema`: rebuilt within 100 ms of an edit, `schema.changed` pushed before the config is read again through it, as a reload, a `config.changed` only when it comes out different; the tree's `qml/config/json/config.schema.json` is rewritten only in a git checkout); the installed binary only outside it (`watchBinary`: a rebuilt one is re-exec'd into). A self-update's re-exec targets the dev build while it runs, else the installed binary (`upgradeTarget`).
  - **The dev config** (`devconfig`; the install never reads it): `devconfig.Prepare` readies it before the dev image's store opens. The first time it's live's raw bytes (migrated by the dev store on open), and `$XDG_STATE_HOME/axiom/dev/base.json` (live's bytes at the last sync) is too; live newer than the dev tree's migrations seeds the defaults plus live's takeover settings instead, with a note (`dev.state.config.note`). Then dev's takeover settings are set to live's, and `dev.state.config.liveChanged` says whether live moved on since the base; the shell then offers "Bring live changes over" or "Replace dev config with live" (`DevManager`, once per dev start).
  - **Dev and live** (`devsync.go`, from either image while a dev tree is set): `dev.config.diff` lists every setting they disagree on, three ways against the base (`side`: changed in `dev`, `live` or `both`), compared in dev's shape; `devOnly` marks one the install tree's schema lacks or holds in another shape (dev's value fails its node there), and `devVersion` / `installVersion` the two schemas' config versions, which the card names when they differ. A list whose items all carry ids (bars, pages, edge menus, OSDs, widgets) is compared by id (`config.DiffByID`): a row per item added or removed, an item on both sides followed down to what changed (set whole when its `type` did), each copied on its own by its `{id}` path, a copied new item going last; any other list, or one whose shared items changed order, is one row whole. `dev.config.copy {paths, to}` copies chosen rows either way (a dev-only setting can't go to live); takeover settings are never rows nor merged (`devconfig.Rows`/`Merge` leave them out; they're per machine, below), and a copy naming one is refused (`takeover_refused`) either way, so a copy never writes one (no takeover grant on the copy or pull path; decided 2026-11-04); `dev.config.pull {mode}`: `merge` applies live's changes where dev left the setting as the base had it, `replace` makes dev live's copy; either way the base becomes live. Nothing merges by itself.
    - **One implementation, two images** (`devEnds`: where live and dev are). The image's own config goes through its store; the other is a file, written on its raw JSON under its writer lock (`<file>.lock`, `fsx.TryLock`: held by a store elsewhere, `running`), checked against its schema (`Pipeline.Check`, never a load), `version` untouched, never migrated. In the **dev image** dev is the store and live the file (`devconfig.WriteLive`, the install schema `tree.BuildSchema(installTree)`, cached by the YAML's times); a copy to live shifts the base too. In the **install image** (dev mode off, or on while the dev build is built) live is the store (a copy to live is a `store.Set` under the install's own rules, then `devconfig.ShiftBase`) and dev the file (`devconfig.WriteDev`, `ReplaceDev`), its schema the dev tree's (`tree.BuildSchema(tree)`, cached likewise). Each call first readies the dev config with `devconfig.Prepare`, as a dev start does (seeded from live the first time, its takeover settings live's), so there's one path whether it exists yet or not; it then fills `dev.state.config` (the on-disk dev config against live). The install image loads every side through its own migrations, so a dev tree whose schema is at a newer config version than the installed binary's steps is refused (compare while the dev image runs). No dev tree: `unavailable`.
  - **One per machine:** a takeover setting changed in dev is written to live too (`onConfig`, the dev image's own writes only), the only way one reaches live from dev mode. `saved/` is shared: while the dev image runs, a save never writes over a snapshot whose version the installed axiom can restore; the active-snapshot pointer is per config (`$XDG_STATE_HOME/axiom/ui/dev/savedconfigs.json` for dev). The greeter bundle isn't exported while the dev image runs (`DevManager.active`). Everything else the config drives (managed compositor files, theme integrations, Idle) follows the dev config while it runs; dev off renders them from live again.
  - While on, a tree whose schema isn't the binary's may save (unless its config version is past this build's migration steps, until the dev build with them re-execs: `aheadReason`), and the log is at debug level (`Options.LogLevel`).
  - A CLI whose hello is refused for its protocol (a bump the dev build has and the installed `axiom` doesn't, as binds call `$AXIOM_BIN`) runs the command again with the dev build, once and only while the daemon runs it (`/proc/<daemon pid>/exe`: a dev build left from an earlier dev mode never runs; `cli.devBinary`, `AXIOM_DEV_CLI` set); the shell reads `backend.json`'s protocol for each hello, so a re-exec's bump needs no QML reload.
- **`axiom greeter [--tree DIR] [--dir DIR] [--safe]`**: the login screen's parent (`greeter-session.sh` runs it as greetd's user). It loads the exported bundle, else the install's snapshot, else the defaults, through the same pipeline (`backend/internal/greeter`), writes it to `$XDG_RUNTIME_DIR/axiom/greeter-<display>/` and runs `qs -p <tree>/qml/greeter.qml` on it, staying its parent until it exits (non-zero when qs failed): a socket in that folder answers the greeter's commands, lookups, weather, lock keys and compositor requests (Hyprland's, niri's and its event stream), and nothing else ([Greeter runtime](../features/greeter-runtime.md), [protocol](protocol.md)).
- **`axiom greeter-install install|update|uninstall …`** (hidden): the login screen's installer, run as root through pkexec by `data/greeter/greeter_install.sh` (its shim) or, for a first install, by the daemon's `greeter.apply`. `cli.Main` hands it over before anything else, so nothing of the user's is opened as root; it prints one JSON object ([Greeter install](../features/greeter-install.md)).
- **The config store** (`backend/internal/store`):
  - The one writer of config.json, holding `config.json.lock`.
  - Loading: format 1 through the frozen migrations and the conversion to format 2 (the file kept as `config.format1.json`), then the format-2 steps (`migrate/steps`; a format-2 file without its version fails, and a migrated one is kept once as `config.v<version>.json`), with defaults written on a first run. A file that doesn't load blocks saves until fixed; at the start the store then runs on the defaults (`State.Defaults`), which the saved configs never save over a snapshot. Edits made outside are watched (`Store.Watch`, the config part's run) and pushed like a save; the store's own writes are recognised.
  - Writing: path ops (keys and `{id}` selectors, never positions), validation, and takeover settings refused without `takeover`. A replace or restore keeps them (making a section it lacks, so the defaults can't reset one); over a file that didn't load at the start, the values in effect (below), not the defaults the store runs on.
  - The takeover values in effect are kept in `$XDG_STATE_HOME/axiom/takeovers.json` after every good load or write (`Options.TakeoversFile`; the offline CLI keeps it only for the XDG config, never a `--config-dir`). Over a file that doesn't load at the start they are the file's own when it is JSON, else the ones kept, so a restore keeps them (decided 2026-10-28). With none kept (a first start on a broken file, the state folder wiped) they're unknown, and a restore is refused until the file is fixed by hand.
  - Outside edits are told from its own writes by the bytes last written or read, so undoing a broken edit back to them is read again. A write while the file holds other bytes (an outside edit its debounced reload hasn't read yet) is refused as a Conflict and the file read again then, so the shell, reading its config back (`ConfigManager.saveRefused`), gets the edit.
  - An outside edit never changes a takeover setting (`holdTakeovers`): the value in effect is kept, each key ignored is logged, and the file is written back with it (normalized, like any write of the store's), so the file matches what's in effect and a restart can't release a managed config (decided 2026-10-28). Only while the values are unknown does the first edit that loads set them. `Store.Takeovers` hands out the values in effect: the compositor's mode is read from it, the one hold of every takeover.
  - Writes are atomic and keep a symlinked config a symlink.
- **The shell's side:**
  - `BackendManager` (the connection, hello, reconnect; `incompatible` and `dev` from the hello and its pushes).
  - `ConfigManager`: the config read from the snapshot and pushes. Writes are checked against the schema in JS, applied at once and sent to the daemon, whose answer stands.
  - `IpcTarget` (every IPC target, registered with the daemon).
  - `LockManager` reporting the lock.
  - A shell started by hand, without `AXIOM_SOCKET`, shows only a notice with the line that starts it (`NoParentNotice`).
- **IPC through the daemon:**
  - `axiom ipc <target> <fn> [args]`, `axiom ipc list`, and named commands (`axiom launcher toggle`, `axiom volume up`, …, checked against `docs/dev/generated/ipc.md`), as is `axiom message`, which passes its `--osd` / `--detail` flags to `osd.message` as arguments, `""` when not given, since IPC functions take no optional ones). `axiom notify TITLE [BODY]` calls the daemon's `notify.send` itself (not the shell), with `wait` so the call answers the picked button ([notifications](../features/notifications.md) › From scripts).
  - The shell's registered targets are called over its connection, the only way in: each target's functions come with `ipc.register` (names and argument counts), and arguments go as text.
- **`axiom lock`:** exits 0 only once the compositor has acknowledged the session lock (`WlSessionLock.secure`) and the shell reports a lock surface on every monitor connected (with none connected, the session lock alone). Otherwise (after 3 s, or 10 s more while the shell holds the lock unacknowledged) it starts the shell locked, then fails. A shell that dies while locked (holding the lock, `lock.state`'s `holding`, acknowledged or not) is restarted at once, locking first; `axiom restart` while locked starts the next one locked too, and a stop axiom asked for never relaunches it. Nothing unlocks but PAM; `lockscreen` takes only `lock`. With `Lockscreen.mode` `none` it runs `Lockscreen.lockCommand`, never `loginctl lock-session` (which loops back to axiom).
- **The compositor's config** (`backend/internal/compositor/`, `daemon/compositor.go`): the daemon writes it in every mode ([Config modes](../compositor/config-modes.md)); it reads what the layer is made of from the config, the shell sends what only it knows (`compositor.inputs`) and shows the state.
  - `compositor/manager`: the modes, the takeover's approvals, the runtime layer and the live parts, one goroutine, one writer per compositor; `compositor/render` (pure): the texts, ported from the JS helpers and checked against their frozen cases; `compositor/ipc`: Hyprland's, sway's and niri's sockets, their reload events and their output lists (`Outputs`, as `render.Output`s for `render.MatchProfile`; not called yet);
  - the managed mode's takeover (`compositor/takeover`, every compositor's `check`/`claim`/`release` as one flow over a `Kind`; [Managed takeover](../hyprland/managed-takeover.md)): the compositor manager runs it, and `axiom compositor check|claim|release --kind K -- DIR HEADER [FALLBACK]` from the command line;
  - the bind merge (`compositor/binds`, `extract` and `remove` with one JSON for every compositor; Hyprland's files run under gopher-lua; [Bind merge](../hyprland/bind-merge.md)): the compositor manager runs it (`compositor.merge`), `axiom compositor binds extract|remove` from the command line. What commands map onto comes from the bind actions' table (`compositor/actions/table.json`, embedded, pure; the shell reads the same table through `compositor.bindActions`);
  - reading the user's own config (`compositor/userconf`: niri's through `compositor/kdl`, pure; sway's with its includes put in): `axiom compositor niri main|includes|binds|info` and `axiom compositor sway-text`, which the shell runs as `Paths.toolBin`: the binary the daemon runs now (`/proc/<daemon pid>/exe`, so a dev build's re-exec counts, where `$AXIOM_BIN` stays the installed binary), and in the greeter (whose axiom sets no `AXIOM_DAEMON_PID`) `$AXIOM_BIN`, which `axiom greeter` sets to itself;
  - `compositor/luacheck` (whether an edit to a user's Lua still parses: `luac` where installed, else gopher-lua) and `compositor/edit` (atomic replacement and dated backups of a user's files; also the hookups' Apply, `hookup.status` / `hookup.apply`, deciding through the pure `hookup`: [Theme integrations](../theming/theme-integrations.md) › The hookups in the daemon).
- **The rest of the CLI:**
  - `axiom ping|restart|quit`, `axiom daemon status|reexec|logs`, `axiom dev status|on|off|rebuild|set|options`, `axiom dev config diff|copy|pull`
  - `axiom log [-f] [--debug] [-- QS-ARGS]`: the shell's log, `qs log -p` on the running shell's QML dir (`daemon.status`'s `qmlDir`; with no daemon, `tree.Find`'s), console.log and debug lines left out unless `--debug` (`cli/log.go`; `scripts/log.sh` wraps it)
  - `axiom config path|get|set|reset|validate|status`: online, or `--offline` against the file under the writer lock
  - `axiom exec refresh COMMAND`: runs a command the shell watches again now (a script's stand-in for Waybar's `signal`)
  - `axiom schema build|check|hash`, `axiom debug wayland-globals|wayland-outputs`, `axiom version`
- **Re-exec** (`axiom daemon reexec`, a hello from a client speaking a newer protocol that a binary on disk speaks ([protocol](protocol.md) › Changing the protocol), a self-update that rebuilt the binary ([Self-update](../features/self-update.md)), or dev mode on a rebuild): the new image takes over the instance lock, the writer lock, the socket and the shell (still its child), and the commands running as its children (`command.Children`: the shell's runs, watches and streams and the daemon's own `checkupdates`, `ddcutil` and `tailscale`, run through `command.Run` with `Stop`, which kills one past its time limit; their output drained, reaped when they exit, handed on again by a later re-exec, a stream stopped). Its clients are told first (`daemon.closing`, [protocol](protocol.md) › A session). It trusts the handoff only when the inherited lock really is this display's held lock. The adopted shell's supervisor is made, its pid known (`supervise.Options.AdoptPID`), before the socket serves, so the shell's hello, queued while the image was replaced, is never checked against no pid. A shell that held the session lock is taken as holding it until it reports again, so dying in between it restarts locked.
  - The descriptors lose close-on-exec only under `syscall.ForkLock`, so no child starts meanwhile and inherits a lock; an exec that fails gives them it back and thaws the store.
  - The handoff carries the image the next one runs (`image`: its tree, its config's folder, dev mode), the install tree, the installed binary (while a dev build runs), the shell's QML dir and config folder, the schema's hash and whether the session was locked. The writer lock is adopted only when the next image runs on the same config folder; otherwise (into or out of the dev config, `Config/dev/`, readied by `devconfig.Prepare`) it's closed, the store opens afresh and the snapshot is written anew. The shell restarts when its QML dir, its config folder or the schema differs (`needsShellRestart`), locked first when it was. A `fresh` handoff (an exec at session start) carries only the instance lock, the installed binary and the install tree; the next image runs dev.json's tree on the dev config. `daemon.status` names the `configFile`.

### Wayland
The daemon holds its own Wayland connection ([wayland.md](wayland.md)): `backend/internal/wayland/wire` (the wire protocol, a `Conn` with objects and their events), shared by its clients (`wayland/client`): `wayland/outputs`, the outputs by place that `share.*` names monitors with, the seat, and idle notifications ([idle](../features/idle.md)). Gamma, clipboard and typing come next (roadmap stage 2).

### D-Bus

### Building and checking
- `cd backend && go build ./cmd/axiom` builds it (pure Go, `CGO_ENABLED=0` works).
- `scripts/check_go.sh` runs the Go checks of CI's go job (`check_all.sh --ci go`; `--ci` adds govulncheck), failing on stale generated code; `--fix` regenerates and formats. `scripts/dev/verify.sh` runs it when `backend/` or an embedded file changed.
- The embedded copies under `backend/internal/assets/data/` are generated and gitignored, the schema among them (built from `qml/config/schema/` by `go generate`, since the binary can't build what it embeds before it compiles; the same run writes the tree's `qml/config/json/config.schema.json`): edit `qml/config/json/…` and the YAML. A fresh clone runs `scripts/generate.sh` once before `go build`.

### Security
Code handling sockets, locks, runtime directories, atomic writes, the child's environment or the lock screen is security-relevant: every rule it enforces has a test, and a change to it is reviewed against this list.
- The runtime directory must be a real directory owned by the user with mode 0700; `$XDG_RUNTIME_DIR` is required, never replaced by `/tmp`.
- A lock is taken before anything it guards is touched (a stale socket is removed only while holding the instance lock).
- Every socket connection's peer must be the same user (`SO_PEERCRED`), and a hello as `"shell"` must come from the pid of the shell the daemon runs (`Conn.PeerPID`): only it reports the lock and registers IPC targets.
- Writes are atomic (temp file, fsync, rename, fsync the directory) and never follow a planted symlink.
- Nothing unlocks the lock screen but PAM: no RPC, CLI or IPC path exists for it.
- Descriptors received over a socket (D-Bus, and Wayland as it gains them) are close-on-exec on arrival and closed when nothing takes them (`internal/unixmsg`), so no child inherits one.
- A command the shell asks for (`exec.run`, `exec.spawn`, a watched one through `exec.watch`; `internal/command`) gets the shell's environment and only stdio; what it reads as a secret comes on stdin, never argv or the log, a spawn starts in a session of its own (in its `cwd`, when given: a desktop entry's `Path=`), never the daemon's child, and a streamed watch runs in a process group of its own, killed whole when it stops.

### Shared fixtures
Behaviour implemented on both sides (`SchemaValidation.qml`, which the shell still fills defaults with for previews, and Go's `config` pipeline; `SchemaLayout.showIfHolds` and `schema.Holds`, the condition grammar of `x-showIf`, `x-enabledIf`, `x-enumShowIf` and `x-scopeIf`; `ConfigOps.qml`'s path ops and `config.set`) is tested from one set of cases under `tests/fixtures/shared/`, read by both `go test` and qmltestrunner (`tests/tst_Shared.qml`), with expected output stored as exact bytes. The directory is generated and gitignored: `scripts/generate.sh --fixtures` records it when what it's made from changed (`fixtures.py ensure`, a stamp of the inputs), and CI records it before the tests.
- **A case** is `<suite>/<test>/<name>.json` (`{op, args}`) plus `<name>.expected.json`: the output as 2-space JSON in JS key order with a trailing newline (`Shared.canonical`). `index.json` lists every case (qmltestrunner can't list folders).
- **Arguments** larger than 2 KB are stored once in `blobs/<hash>.json` and referenced as `{"$blob": hash}`; the live schema is named by its path, `{"$repoFile": "qml/config/json/config.schema.json"}`.
- **Ops** are `schema.applyDefaults` and `schema.resolveRef` (validating is Go's alone: `backend/internal/config/validate_test.go`). `tests/Shared.qml` maps each onto `SchemaValidation`; `backend/internal/config/shared_test.go` onto the pipeline. `ConfigOps.diff` / `apply` (and the bind and layer helpers' functions, `BindActions`, `BindKeys`, `KeyNames`, `LayerStack`, replayed through `compositor/render`) are `<Helper>.<function>`: `backend/internal/daemon/configops_shared_test.go` decodes each diff strictly as `config.set`'s params (as `ConfigManager.commit` sends them), applies it, and checks Go's `Diff` and `ApplyOps` make the same bytes, since the contract check sees only the params' literal keys, not the ops built into them.
- **Recording:** `scripts/dev/fixtures.py record` runs tst_Config (the live schema's defaults), tst_SchemaValidation (inline schemas), tst_SchemaLayout (the condition grammar's rows), tst_GreeterBundle (the exported bundle filled, which `shared_test.go` also validates), tst_ConfigOps and those helpers' tests with recording on (the compositor renderers the shell no longer has, `HyprLua`, `SwayConf`, `NiriConf`, `CompositorLayer`, left their cases frozen in `compositor/render/testdata/frozen.jsonl.gz`). The tests call the helpers through `Shared`, which logs every call (arguments and output bytes), so the tests' inline cases become fixtures without being copied by hand. `fixtures.py check` (CI) checks the index and the blobs.
- **The format-1 migration's cases** aren't here: they were recorded from the shell's own migrations before that copy was removed, and frozen as the binary's testdata (`backend/internal/migrate/legacy/testdata/frozen.jsonl.gz`: each input with the sha256 of the bytes V4 made of it; `testkit.Frozen`). `legacy.js` and `schema-v75.json` are hash-checked beside them. Share, pruning and the rest have Go tests of their own.
- **One known difference:** V4's `JSON.stringify` writes a lone surrogate unescaped (it predates ES2019); Go never holds one (`jsonx` decodes it as U+FFFD). No JS-owned case holds one (recording refuses it).
