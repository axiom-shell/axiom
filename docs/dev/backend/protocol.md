# The shell ↔ daemon protocol

> **Files:** `services/core/BackendManager.qml`, `components/methods/JsonRpc.qml`, `services/core/IpcTarget.qml`, `backend/internal/rpc/`, `backend/internal/daemon/methods.go`, `backend/internal/daemon/daemon.go`, `backend/internal/daemon/contract.go`, `backend/tools/rpcshapes/`, `backend/internal/topics/`, `backend/internal/daemon/topics.go`, `backend/internal/ipcroute/`, `backend/internal/lockscreen/`, `config/json/backend.json`, `config/Paths.qml`
> **Related:** [The axiom binary](README.md), [Config manager](../core/config-manager.md), [Config modes](../compositor/config-modes.md), [every method and push](../generated/rpc.md) (generated)

Where the QML shell and the axiom binary meet. This page says how the connection works. The methods, pushes and the files that use them are listed in [rpc.md](../generated/rpc.md), which `scripts/gen_docs.py` builds from the code and the daemon's own registry, with every method's params and result fields and every push's.

### The channels
The shell (`qs -p <tree>`) is a child of the daemon (`axiom run`). Six channels connect them:
- **A. The environment** the daemon starts the shell with (`daemon.go`, `shellEnv` / `shellEnvNow`):
  - `AXIOM_SOCKET`: the socket (`BackendManager.socketPath`; unset means a shell started by hand, `BackendManager.active` false).
  - `AXIOM_SCHEMA` and `AXIOM_CONFIG`: the runtime files below.
  - `AXIOM_TREE`, `AXIOM_BIN` (the installed binary, `Paths.axiomBin`) and `AXIOM_DAEMON_PID` (`Paths.toolBin` runs `/proc/<pid>/exe`, the binary running now).
  - `AXIOM_INCOMPATIBLE`: set only while the tree's schema isn't the binary's and dev mode is off (`BackendManager.incompatible`).
  - `AXIOM_LOCK_ON_START=1`: a relaunch after a crash while locked (`shell/Lockscreen.qml`).
- **B. Runtime files** in `$XDG_RUNTIME_DIR/axiom/<display>/` (0700, written atomically):
  - `config.json`: the config, loaded, migrated and filled, read once at start (`ConfigManager`'s snapshot); pushes keep it current after that.
  - `config.schema.json`: the schema built from the tree (`ConfigManager`; `BackendManager` sends its md5 in the hello).
  - `compositor.json`: the daemon's own state, kept across re-execs; the shell never reads it.
- **C. Calls, shell → daemon**: JSON-RPC requests on the socket (`BackendManager.call(method, params, done)`).
- **D. Pushes, daemon → shell**: notifications by topic (`BackendManager.listen(method, fn)`). Each listener runs on its own: one that throws is logged and the rest still hear the push.
- **E. Calls, daemon → shell**: `ipc.call`, how `axiom ipc <target> <fn>` and `axiom lock` reach an `IpcTarget` without a process per call (`BackendManager.handle`; answered by `_callTarget`).
- **F. The binary as a command**: the shell runs `Paths.toolBin` for things that need no daemon (`compositor niri info`, `compositor sway-text`), and `Paths.axiomBin daemon reexec` after an update (`SelfUpdateManager`). The compositor configs the daemon writes call `axiom ipc …` for binds. The greeter runs `$AXIOM_BIN`, which is the greeter's own binary.
- **The greeter's axiom**: `axiom greeter` stays the parent of the login screen's qs and serves the same protocol on `<its runtime folder>/axiom.sock` (`AXIOM_SOCKET`; `daemon/greeter.go`, `RunGreeter`), answering only that qs's hello and then `exec.run`, `exec.spawn`, `tz.zones`, `tz.offsets` and `net.addresses`: no config, lock, compositor layer, Wayland connection or pushes. Any other method is `not_found`.

The daemon also talks to the compositor over its own sockets (`backend/internal/compositor/ipc`). That is a separate connection, not part of this protocol.

### The wire
JSON-RPC 2.0, one message per line (NDJSON), over a unix socket in both directions (`backend/internal/rpc`; on the shell side `JsonRpc` builds and parses each line). Every message on a connection leaves through one queue, so a push caused by a request arrives before that request's reply: `config.changed` comes before the answer to the `config.replace` that caused it.

The whole-state pushes (`daemon.state`, `dev.state`, `saved.state`, `compositor.state`, `idle.state`, `wayland.state`, `nightlight.state`, `clipboard.state`, and every [polled topic](#polled-topics)'s `<topic>.state`) are **latest-wins** (`Conn.NotifyLatest`, an `rpc.Push` declared `Latest`): each holds one place in the queue, taken where its first unsent state was sent, and what is written there is the newest state. A shell that stalls gets fewer states, never a full queue (4096 messages, after which the daemon drops it). Events (`config.changed`, `schema.*`, `compositor.applied` / `notify` / `bindsMerged`) and `config.state`, which follows its `config.changed`, stay one message each. A message may be up to 16 MiB and nested 64 deep, with at most 256 requests in flight per connection.

### A session
1. The shell connects and sends `daemon.hello` with `protocol` (from `config/json/backend.json`), `client: "shell"`, `schemaHash` (md5 of the schema file it read), `subscribe: true` (every topic) and `pid`. Calls made earlier wait in `BackendManager`'s queue.
2. The daemon refuses a different protocol, a schema other than the one it built, and a `"shell"` hello from any pid except the shell it runs. A refusal fails every call with that error until a later hello is answered.
3. The answer describes the daemon: version, commit, pid, display, tree, `dirs`, the config `state` (`firstRun`, `blocked`, `issues`, `revision`), `compatible` / `reason` and `dev`. It's available as `BackendManager.hello`.
4. The queue is sent, the shell registers its IPC targets (`ipc.register`, names only; the daemon reads their signatures from `qs ipc show`), and `greeted` fires. `ConfigManager` applies the state, acknowledges a first run (`config.ackFirstRun`) and reads the config again (`config.get`) in case it missed a push while disconnected.
5. When the connection drops (a re-exec or a restart), calls in flight fail with `unavailable`, queued notifications wait for the next connection, and the shell reconnects at once when that connection had been greeted, otherwise (and while reconnecting fails) after 200 ms × 2ⁿ (at most 5 s), saying hello again; so a daemon that accepts and closes before the hello isn't retried in a tight loop. A re-exec or quit is announced first: `daemon.closing` (`{ reexec }`, to the `daemon` topic) goes out and the daemon waits up to 300 ms for its clients to close their side, so the shell closes the connection itself (Quickshell's `Socket` warns on any close it didn't make) and connects again 200 ms later after a re-exec, or with the usual backoff after a quit (a shell run apart, beside `axiom run --no-shell`, finds the next daemon). Each attempt is a fresh `Socket` (a Quickshell `Socket` whose connect failed never tries again), and a finished one is destroyed.

### Topics
A hello's `subscribe` is `true`, `false` or a list of topics:
- `config`: `config.changed`, `config.state`, `schema.changed`, `schema.error`
- `saved`: `saved.state`
- `daemon`: `daemon.state`, `dev.state`, `daemon.closing`
- `compositor`: `compositor.state`, `compositor.applied`, `compositor.notify`, `compositor.bindsMerged`
- `idle`: `idle.state` (latest-wins)
- `wayland`: `wayland.state`, `nightlight.state` (latest-wins)
- `clipboard`: `clipboard.state` (latest-wins)

The CLI subscribes to nothing.

### Polled topics
Data the daemon polls for the shell (`backend/internal/topics`) is not a hello topic: `subscribe: true` doesn't include it. A connection asks for it:
- `<topic>.subscribe` with `{ interval }` (ms) plus whatever the topic's own request carries; called again, it replaces that connection's request. `<topic>.unsubscribe` drops it, and closing the connection drops all of them.
- The daemon fetches once for every subscriber, at the shortest interval asked (never below the topic's floor), and not at all with none. A topic whose last subscriber left forgets its state.
- It pushes `<topic>.state` to the subscribers when the state changes (latest-wins, below), and to a new subscriber at once when it has one. `<topic>.refresh` fetches now.
- The shell: `BackendManager.acquire(topic, request)` / `release(topic)` / `refresh(topic)`, subscribed again after every hello (a reconnect or re-exec forgets them). The service owning the topic merges its consumers (`ConsumerRegistry`) into one request and listens to `<topic>.state`.
- A topic is a `topics.Source{Name: "…", Floor, Default, Fetch, Request, State}` (the last two the Go types of a request and of what `Fetch` returns) in the package owning its side effect, listed in `daemon/topics.go` (`sources`); `rpc.md` reads the name from that literal. A source whose interval comes from a setting takes `topics.MinInterval` (1 ms, no real floor: the setting's schema `minimum` is the limit) as its `Floor`, and `TestIntervalSettingsMeetMinInterval` fails on any interval setting whose schema `minimum` is below it, so every value a setting offers is polled at. A topic polled at a fixed interval keeps its own floor: `claudeUsage` ticks every minute, and its setting is `every`, floored in Go (`minEvery`).
  - A request asking for something no subscriber asked for yet (anything but its `interval` differs) is fetched at once, not at the next interval: `system`'s page just opened fills straight away, `claudeUsage`'s new account and `updates`' new AUR helper are checked now. The same request at another interval only moves the next fetch.
  - `OnRefresh` tells the source of a `<topic>.refresh` before the fetch, for a Fetch that does more when asked (`claudeUsage` refetches every account not rate limited).
  - A state that must reach the shell after every fetch (a failure, a sample for a history) carries its time (`at`), since an unchanged state isn't pushed (`updates`, `system`).

### Guards and errors
- Every connection's peer must be the same user (`SO_PEERCRED`, `rpc.SamePeerUser`).
- **Shell only**: `ipc.register`, `lock.state` and every compositor method that changes something answer only the connection whose hello was the shell's.
- **Writable**: config writes (`config.replace`, `config.restore`, `config.set`, the `share.*` applies, `saved.restore`) are refused with `incompatible` while the tree's schema isn't the binary's and dev mode is off. `daemon.state` pushes the change.
- The lock screen takes only `lock`: no method unlocks it (`ipc.call` to `lockscreen` is anything but `lock` → `refused`).
- Errors are `{ kind, message, issues }`. `kind` comes from `axerr.Kind` (`invalid_config`, `bad_request`, `conflict`, `takeover_refused`, `incompatible`, `unavailable`, `running`, `not_found`, `refused`, `internal`); messages stay English, and the shell translates by kind.

### Changing the protocol
- **A new method, push or topic** needs no protocol bump: an older peer never calls or hears it. Add the handler (`rpc.Handle` in the daemon part it belongs to) or declare the push (an `rpc.Push[T]` beside the topic constants in `backend/internal/daemon/methods.go`, sent with its `Send`, and listed in `pushShapes` in `contract.go`), call it through `BackendManager`, and let `scripts/dev/verify.sh` regenerate [rpc.md](../generated/rpc.md). A method the shell picks at runtime goes in a `// rpc: a, b` comment directly above the helper that sends it (`ClipboardManager._call`, `SavedConfigsManager._apply`; other comment lines between are fine), so the generator sees it: each call of that helper naming one of those methods as a string literal has its next argument checked as that method's params. A note anywhere else fails the check. `rpc.Handle` keeps the handler's params and result types (`Registry.Types`); `rpc.ShapeOf` walks a type into the field tree `encoding/json` writes for it (tag names, `omitempty`, embedded fields inlined; `json.RawMessage`, `any` and types with their own `MarshalJSON` opaque). `daemon.BuildContract` builds the registry from the same method sets as `Run` without starting anything (`TestContractIsTheRegistry` checks they match), and `backend/tools/rpcshapes` prints its methods, pushes and topics with their field trees: `scripts/generate.sh` writes that to `docs/dev/generated/rpc-shapes.json` (gitignored) before `gen_docs.py`, which fails when its scan by name and the registry disagree on what exists.
- **The call rule.** A call to the daemon (`BackendManager.call` / `notify`, `JsonRpc.request`) names its method as a string literal and passes its params as an object literal, at the call or through a `// rpc:` helper; a result or push is read in an inline arrow callback. That's every shape `gen_docs.py` reads, and it learns no new ones: a call that doesn't fit is rewritten to fit, or, when it can't be (a whole object built elsewhere), marked `// rpc: unchecked (<reason>)` on its line or the line above. `rpc.md` lists the marked calls with their reasons under Unchecked call sites, and that list only shrinks. `BackendManager`'s own generic paths (`call`, the topic subscriptions) are exempt, and calls inside a `// rpc:` helper are covered, since its callers are checked.
- **What's checked** (`gen_docs.py`, so `verify.sh` and CI): a call, `// rpc:` note or listener in the shell naming a method or push the daemon doesn't define; a call whose params are an object literal with a key the method's params don't have, nested literals included (`{}`, `null` and no params pass; a key into a map or opaque params, such as `compositor.inputs`, isn't checked); a call it can't read (params passed as a variable, with a spread or a computed key; a method that isn't a literal) without the mark; a mark on no such call; and a `// rpc:` note that isn't directly above its helper's `function`. A first-level read of a result or push in an inline arrow callback (`(error, result) => … result.key`, `listen("x", state => … state.key)`) fails on a key the result or push doesn't have; a result stored whole and read elsewhere (`root._state = state`) isn't checked, nor are polled topics' requests (built from config, `JSON.parse`d in `BackendManager.acquire`): `rpc.md` shows those shapes to read against. At runtime `rpc.Handle` decodes params strictly (`rpc.DecodeStrict`), and a topic's `subscribe` checks its request against the source's `Request` plus `interval`: a key with no field, at any depth, is a `bad_request` naming the key (except in `daemon.hello`, decoded leniently so a peer from another version still hears the protocol mismatch), so an unchecked call with a renamed key fails in the log instead of running on a zero value (params typed `json.RawMessage`, a map or `any`, such as `compositor.inputs`'s, take any key). The shell and the CLI send only the keys a method takes, so a peer from another version adding a key to an existing method is a protocol change (below).
- **Changing what an existing method or push means** (its params, its result, when it's sent) bumps `protocol` in `config/json/backend.json`. The binary embeds that file, so a mismatched shell and binary refuse each other at the hello and don't misread each other.
