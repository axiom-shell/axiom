# Config modes (detached / included / managed)

> **Files:** `backend/internal/compositor/manager/`, `backend/internal/compositor/render/`, `backend/internal/compositor/ipc/`, `backend/internal/compositor/takeover/`, `backend/internal/compositor/binds/`, `backend/internal/compositor/userconf/`, `backend/internal/daemon/compositor.go`, `services/compositor/CompositorConfigManager.qml`, `config/CompositorConfig.qml`, `components/methods/CompositorLayer.qml`, `components/views/Settings/CompositorStatusCard.qml`, `services/ui/IntegrationHookupManager.qml`, `config/WindowBehaviourConfig.qml`, `services/ui/CursorThemeManager.qml`, `scripts/cursor_theme.py`
> **Config:** `Compositor.mode`, `Compositor.requiredSettings`, `WindowBehaviour.*`, `Keybinds.binds`, `Monitors.items`, `WindowLook`, `Input`, `Session`, `Workspaces.strips`
> **Related:** [Contract](contract.md), [Window look](window-look.md), [Hyprland's writer](../hyprland/config-modes.md), [Managed takeover](../hyprland/managed-takeover.md), [Sway backend](sway-backend.md), [niri backend](niri-backend.md), [The axiom binary](../backend/README.md)

How axiom sets the compositor up, the same on every compositor with `supports.configModes`. The axiom daemon does it (`backend/internal/compositor/manager`): it writes the compositor's config, takes it over and gives it back, moves the user's binds in, and applies the runtime layer, talking to the compositor itself (`compositor/ipc`). The shell sends it what the layer is made of and shows what it pushes back (`CompositorConfigManager`). Read this before touching anything axiom writes into a compositor's config.

### Who does what
- **The shell** (`CompositorConfigManager`) resolves the layer's inputs with its readers and sends them as `compositor.inputs` (shell only): the binds (`KeybindsConfig.activeBinds`), the bind context (`Paths.shellCommand`, the apps), the window look and input as specs (`spec(true)` for files, `spec(false)` for now: `CompositorLayer.look` / `.input`), the monitor profiles and, for sway and niri, the matched profile's rules (`_outputRules`, null until `MonitorManager` read the outputs), the strips, the session, the managed options, the theme colors they name (`colors`), the motion, `Idle`/`Polkit`, `supports` and SwayFX (`fx`). With them go two keys: `layerKey` (a change re-applies the layer) and `liveKey` (a change is only evaluated at runtime).
- **The daemon** (`manager.Manager`, one goroutine, everything in order) reads the mode from the config itself, renders the text (`compositor/render`, the port of the JS helpers, checked against their frozen cases), and does the rest. It does nothing until the shell's inputs come for its compositor: what it would write depends on them.
- **Back to the shell**: `compositor.state` (status, problem, the takeover, the merge, skipped keys, which binds are complete, niri's running config, the files and lines), `compositor.applied` (the compositor was changed at runtime: the backend reads back what it follows, `layerApplied()`), `compositor.notify` (a notification to send, translated, once per session) and `compositor.bindsMerged`. Pushes go under the `compositor` topic.
- RPC: `compositor.state`, `compositor.checkManaged`, `compositor.allowTakeover`, `compositor.merge`, `compositor.previewMerge`, `compositor.reload`, `compositor.entries` (the binds in effect, for the Keybinds page on sway and niri).

### The layer
- One layer covers: the binds, the required settings (`Compositor.requiredSettings`), the [window look](window-look.md), the input (`Input`), the blur behind axiom's surfaces (`render.SurfaceBlur`), the monitor profiles (`Monitors.items`) and the strips. In managed mode the writer adds `Session`, the shared options (`WindowBehaviour`, each field by its `x-compositor` spec) and the compositor's own (`Compositor.hyprland`, `.sway` or `.niri`).
- The mode picks how the layer gets to the compositor:
  - **detached**: evaluated at runtime (the writer's `runtimeApply`), again after every config reload, which drops it
  - **included**: written to a module (`moduleText` → `includePath`) the user's config loads (`includeLines`)
  - **managed**: written as the compositor's config itself (`managedText` → `managedPath`), after a takeover, loading the user's own files (`userFiles`) after it.
- Whenever a file isn't loaded (included but the lines are missing, or a takeover refused), the runtime layer stands in and `problem` says why. The writer's `checkLoaded` tells; it may say the compositor couldn't load its config at all (niri), and then nothing stands in.
- **Included but not loaded**: a notification, once per session and not while the onboarding is open, offers **Add it for me** (`addIncludeLines`: the `compositorModule` hookup, the include lines added with a backup, then `compositor.reload`) and Open settings. The Compositor card has the same button next to Copy while the module isn't loaded.

### The runtime layer
- What every compositor's shares (`manager/runtime.go`): the binds in effect are read first, so a bind on a key the user's config already takes is skipped (`render.RuntimeBinds`, `skippedKeys`), each taken key logged once. A writer that couldn't read the user's binds (sway, no config found) binds anyway and says so as `problems().UnreadBinds`, which `problem` shows unless a file mode's own problem is there, until a later apply reads them. A reload while it reads (counted by the event stream as it comes) makes what it read stale, and it reads again.
- Hyprland's keeps the keys it bound in Hyprland's Lua state (`AXIOM_RUNTIME_KEYS`), unbound before the binds are read; sway's keeps the commands unbinding them (state, below); niri takes nothing at runtime, so its runtime layer is a file: a wrapper niri loads in place of the user's config (`load-config-file`), including it and then axiom's module.

### Writing files
- Written only on change, atomically (`compositor/edit`), then the compositor reloads (it doesn't watch files its config loads). A writer that can check its text first (niri: `niri validate`) leaves the file as it was when the compositor would refuse it, and `problem` says why.
- The manager's state that must outlive a re-exec of the daemon (dev builds) is in its runtime folder (`compositor.json`), for the compositor instance it was written for only: the mode last applied (so a load never gives anything back), the live parts evaluated since the last reload, the cursor set, sway's unbind commands, whether niri runs the wrapper.

### Live parts: the look and the input
- Evaluated at runtime as they change (`liveKey`, debounced), in every mode: a reload on every step of a setting stalls the desktop, and detached, re-applying the whole layer redoes every bind. The file holds them as of its last write.
- After every reload in the file modes they're evaluated again, so they win over the user's own lines while they're on.
- A runtime eval can't take a setting back: a part turned off since it was evaluated reloads the compositor's config (`manager.undoLive`). Only the parts the compositor applies count (`supports.window<Part>`, `inputConfig` for `input:<part>`), so one it can't apply (blur on sway) never causes a reload.
- Once they've settled (2 s), the file modes' file is written with them too, without a reload, so the next session starts from them.
- The cursor theme is set as it changes (a reload keeps it).
- **The cursor theme's XCursor name** (`CursorThemeManager`, `scripts/cursor_theme.py`): a theme naming its cursors only the X11 way and inheriting nothing (Oxygen: `left_ptr`, no `default`) shows the `default` theme's cursors for the standard names it lacks. While the cursor part is on, such a theme gets a companion, `axiom-cursor-<theme>` in `$XDG_DATA_HOME/icons/`, inheriting it with those names linked to its own cursors; `CompositorLayer.input`'s `cursor.xcursor` is its name, which niri's `xcursor-theme`, sway's `seat * xcursor_theme`, `XCURSOR_THEME` and GTK take. Hyprland's `setcursor` keeps the theme's own name. The shell waits for the first answer (`CursorThemeManager.ready` in `live`), so a start writes the name once.

### Include and autostart lines
- `includeLines` (included) and `autostartLines` (included and detached) are the writer's, as hookup targets `includeTarget` / `autostartTarget` in the state. `IntegrationHookupManager` runs them under the keys `compositorInclude` and `compositorAutostart`, so the onboarding offers Apply with a backup ([Theme integrations](../theming/theme-integrations.md)). Their titles and notes are translated by the shell (`CompositorConfigManager` declares them).
- The Compositor card checks `compositorAutostart` when it's shown and when the mode changes; while the line is missing it shows the line with Copy and **Add it for me** (no reload: it only matters at the next login).

### Status card and saving
- The settings page's Compositor section starts with `CompositorStatusCard`, built from `status` (`runtime` | `loaded` | `fallback` | `pending`) and `problem`.
- A mode picked there waits for Save (`x-applyOnSave`). The card predicts a takeover with `checkManaged()`: `ours` | `adopt` | `stock` | `released` | `new` | `blocked` (`managedBlockedBy` `link` or `git`).

### Approving a takeover
- Managed mode takes over a config of the user's only once they've allowed it on that compositor. The approvals are state, not config (`$XDG_STATE_HOME/axiom/ui/takeover.json`, `{ approved: [kind] }`), so a config imported, or carried over from another compositor, with `mode: "managed"` never counts as one.
- Allowed only by `allowTakeover()` (the card's Allow takeover, the notification's button; the daemon's `AllowTakeover` is the only thing that records one). No mode change is ever the approval, whatever made it: saving managed on the card or in the onboarding, a session starting with the file already saying managed, or a config.json that didn't load at the start fixed from outside to say managed (otherwise an edit from outside doesn't change the mode at all, see Leaving a mode). After Save the card shows Allow takeover, as it does when a session starts in managed mode with the user's config in place.
- An approval is for one takeover: giving the config back (leaving managed) uses it up, and so does finding it given back behind axiom's back (`axiom compositor release` while managed: the managed config is then never written over). Taking it over again asks again.
- Before claiming, the takeover's `check` runs: with nothing of the user's to take over (`ours`, `new`, `stock`, `released`) it claims without asking; `blocked` claims, which reports it. `adopt` waits: `takeoverPending`, the runtime layer stands in, and a notification (once per session) offers Allow, except right after the shell's Save, where the card already does. A mode read from config.json (one that didn't load at the start, fixed from outside to say managed: the store's event says `FromFile`) has no card open, so it notifies.
- Never press Allow for the user while testing (AGENTS.md › Never).

### Leaving a mode
- A switch made while axiom runs gives back what the mode took. Only the Compositor card switches it: `Compositor.mode` is `x-takeover`, so an edit of config.json from outside (a saved config copied over it, a sync tool) leaves the mode in effect and is logged as ignored ([ConfigManager](../core/config-manager.md)). Outside managed mode, a compositor config that's still axiom's (its header on the first line) is given back too, whatever the mode last applied: a mode changed while axiom wasn't running, or a release that failed.
- While config.json doesn't load from the start (axiom runs on the defaults, which say detached), the mode is the one the file holds (`Store.Takeovers`), so a managed config is never given back for it; the shell's `CompositorConfigManager.mode` and `status` are then the daemon's (its `compositor.state` push, while `ConfigManager.savesBlocked`), so the status card, `KeybindManager` and `MonitorManager` see that mode, not the defaults' detached (`modeFromDaemon`; the card shows no pending switch to the draft's defaults meanwhile). When the file isn't JSON, the mode isn't known: the manager holds (status `pending`) until the file is fixed, setting up and giving back nothing and keeping the mode applied. A managed config or an include of axiom's actually in place (`configIsOurs`, or the module loaded with axiom's layer in it, `moduleLoaded`: an emptied one niri's config still includes isn't; `AppliedMode` managed alone isn't, since a takeover awaiting approval, blocked or failed left the user's config) stays as it is (a runtime layer comes off once axiom's file, the module or the managed config, is loaded, as outside the hold); with neither in the compositor's config, the defaults' runtime layer applies as in detached, and again after a compositor reload, so a detached user keeps axiom's binds. Leaving the hold, the first mode read (a saved config or example restored over the file, which keeps the defaults' `detached` since no takeover value was known, or a hand fix) never switches away from what was applied (`keptMode`: `AppliedMode`, else managed when `configIsOurs`, else included when `moduleLoaded`): the manager keeps it and saves it back to `Compositor.mode` as its card would (`Options.KeepMode`, refused like any write while the daemon is incompatible with the tree), so the file says what is in effect; only a later change gives the config back. A save refused (config.json broken again meanwhile, or the daemon incompatible) leaves the kept mode pending (`KeptMode` in the runtime file, so it outlives a re-exec, often the one into the compatible binary): it stays in effect, the file's stale mode never applied, and the save is tried again on every config event (config.json loading again, a restore) and when the daemon turns compatible (`ConfigWritable`, from `pushState`), and at a re-exec's start. The card's change of the mode meanwhile (any change of the mode since the last config event: an edit from outside is held by the store, so only the card's write can, whichever event tells it) is a real choice: it applies and the kept mode is dropped, never saved over it (a retry first checks the mode is still the one last read). Until shell saves carry `takeover` only on a takeover card's op, any shell save made from a config that predates the kept mode's save puts the stale mode back and is taken as that choice ([issue](../issues.md#shell-saves-carry-unsaved-settings-and-every-takeover)); the one sent right after a restore, a community setup's wallpaper, goes without `takeover`.
- Leaving managed runs the takeover's release ([Managed takeover](../hyprland/managed-takeover.md#release)); detached waits for it before applying its runtime layer. A release that fails (an error, or the dir now a link or in git) is tried again after 10 s, doubling up to 5 min, while `releaseProblem` says why (the status card shows it).
- Leaving included, or leaving managed for detached, empties the module if it exists: every part becomes a no-op, so a config still loading it gets nothing (the runtime layer only adds, and couldn't undo it).

### The writers
One per compositor in `manager/` (`hypr.go`, `sway.go`, `niri.go`), each the `writer` interface: its files and lines, its texts from the inputs (through `render`), the runtime layer, `checkLoaded`, `reload`, the event stream of its reloads (`ipc`), and the takeover kind and bind merge it uses ([Managed takeover](../hyprland/managed-takeover.md), [Bind merge](../hyprland/bind-merge.md)). A new compositor adds a writer, a takeover `Kind`, a bind merge and an IPC client ([recipe](../../recipes/compositor-backend.md)).

### Testing
- Never switch the user's real config into or out of `managed` to test it. (Rule: AGENTS.md › Never, while testing.) Try the modes in a nested session (`scripts/dev/nested.sh <compositor> [--managed]`), which runs its own daemon on scratch folders.
- The texts: `render`'s frozen cases (`testdata/frozen.jsonl.gz`, recorded from the JS helpers before they went) and the shared cases of the helpers the shell still uses; `TestCompositorsReadTheFiles` has `luac`, Hyprland (`--verify-config`) and niri (`validate`) read the files, where they're installed.
- The whole files: `TestGoldenFiles` (`manager/golden_test.go`) has each writer make every file (module, managed, released for each mode, empty module, the live lines) from one shell's inputs (`manager/testdata/inputs.json`, captured from a live shell, its paths and names made generic) and compares them byte for byte with `manager/testdata/golden/<kind>/`; `luac`, Hyprland, `sway --validate` and `niri validate` read them where installed. A change meant to show in a user's config: `go test ./internal/compositor/manager -run Golden -update`, and read the diff.
- The manager's flows: `manager_test.go` (a fake writer); the IPC clients against fake sockets.
