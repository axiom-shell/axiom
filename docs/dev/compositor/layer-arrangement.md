# How compositors arrange and stack layers

> **Files:** `components/methods/LayerStack.qml`, `tests/tst_LayerStack.qml`, `components/methods/LayerArrange.qml`, `tests/tst_LayerArrange.qml`, `services/compositor/LayerManager.qml`, `components/hosts/popout/LayerOrigin.qml`
> **Config:** none
> **Related:** [The compositor](README.md), [Backend contract](contract.md), [Layer stacking](../generated/layers.md), [Bars and the border](../bar/layering-and-corners.md)

What a compositor does with axiom's layer-shell windows: which one reserves its space first, which is drawn on top, and where each one ends up. Axiom works this out for itself, on every compositor, rather than asking Hyprland. Read this before changing how a window reserves space or maps.

### Measured (2026-10-16)
Probed in nested sway and niri: coloured, overlapping layer windows, a screenshot inside the session. Both gave identical results.
- **One sequence per output.** Within a layer, surfaces are arranged and drawn in the order they mapped, across all edges at once. A surface takes the usable area as it is at its turn: a top strip mapped before a left strip spans the full width and owns both top corners. The left strip starts below it.
- **Remapping goes to the end.** Toggling a `PanelWindow`'s `visible` off and on puts it after everything mapped meanwhile, both in arrangement and in drawing.
- **Margins count.** A surface's margin on its anchored edge adds to its exclusive zone. Zone 20 with margin 10 leaves 30 px for the next surface.
- **Exclusive surfaces first.** Every surface with an exclusive zone is arranged before any without one, whatever their map order. Non-exclusive surfaces are placed in what's left; `ExclusionMode.Ignore` surfaces get the whole output.
- **Drawn last is on top.** The surface mapped later is drawn over the earlier one.

### Hyprland
- A layer rule's `order` (`LayerStack.layers`, made into rules by `render.LayerRulesLua`) sorts the surfaces before map order applies. Higher is arranged first *and* drawn first (underneath). That's the same as having mapped earlier, so mapping the surfaces in that order on sway and niri reproduces Hyprland's result.
- Hyprland reads `order` only as a surface maps, so a window whose namespace changes is remade.
- Hyprland also counts what it reserves for itself (`addreserved` on a monitor) and other apps' layers. Axiom's own calculation doesn't see either, so on Hyprland it's corrected from Hyprland's list (below).

### How axiom places its layers
- Every window whose position matters (bars, border strips, docks, integrated edge menus, edge popouts) has a `hosts/popout/LayerOrigin`. It reports how the window asks to be laid out to `LayerManager`: output, layer, anchors, margins, requested size (0 where it's stretched between two anchors), zone (`Ignore` is -1; `Auto` is its size across the edge), and whether it's mapped.
- `LayerManager` gives each window a map sequence number as it maps (dropped as it unmaps, so a remap goes to the end) and runs `methods/LayerArrange.arrange` over them all. That uses `LayerStack.orderOf` first where the compositor sorts by it (`supports.layerOrder`), then the map order. Windows that reserve nothing and aren't mapped yet are placed too, where they'd go.
- `arrange` also gives each output's `reserved` (what the reserving windows take from each edge): niri's outputs' `reserved`, which niri doesn't report.
- `LayerOrigin.origin` is the window's rect from that; `placed` falls back to an estimate on its edge while there's none. `settled` is true once there's an origin, or 400 ms after it went missing (a window on a screen `LayerManager` doesn't lay out never gets one).
- **Corrections from Hyprland's list.** 600 ms after the rects last changed or a layer mapped, `LayerManager` pairs each mapped window's computed rect with Hyprland's own in its namespace (`methods/LayerArrange.match`: nearest in place and size first, each taken once) and keeps the difference as that window's correction, which `rectOf` adds. Sampled only once things have settled, so a window resizing every frame keeps its last correction rather than a stale rect. Kept while a window is unmapped, dropped when it maps with no rect of its own reported. Each difference is logged: `scripts/log.sh --debug -g LayerManager`. `tests/fixtures/layers/` holds captured setups that `tst_LayerArrange` checks against Hyprland's own result. When a mismatch shows up, capture its input as another fixture and fix `LayerArrange`.

### Mapping in order
- The windows with a fixed place in the stack (bars, border strips and corners, the border's shadow window, docks, integrated edge menus, hot corners) bind `visible` to a `hosts/popout/LayerSlot`'s `shown` and hand it what used to decide it as `wanted`.
- `LayerManager` runs `LayerStack.sequence` over them. On each output and layer, a window shows once every wanted window ordered before it has mapped (and had 50 ms to be drawn), so they map highest order first. A window already showing stays up when one ordered before it starts showing (the backdrop as the overlay opens). This happens on every compositor, Hyprland included.
- **Without `supports.layerOrder`**, a mapped window that a window ordered before it mapped after is out of place. It's hidden until it has unmapped, then shown again, and so lands after it. That happens, for example, when a bar is remade by a change of kind, which also changes its namespace. Where the compositor puts a window moved to another layer on top of it (`supports.layerRestack`: SwayFX, checked in 0.6; niri 26.04 keeps its place), the move counts as mapped anew: when the blur window comes back down to Top after a fullscreen window, the chrome ordered over it maps again. Each such remap is logged: `LayerManager: mapping … again, in its place`.
- A window that only maps while open (an integrated edge menu) would put everything after it out of place each time it opens. Such windows are `held`: without `layerOrder` they stay mapped while not wanted, drawing and reserving nothing (`LayerSlot.idle`).
- The held windows: integrated edge menus (a pixel deep, reserving nothing, while closed), each screen's backdrop window (`surfaces/backdrop/ScreenBackdrop`, a pixel in the corner while idle), and the border's shadow window (`surfaces/border/RoundedBorders`, a pixel while BarStyle has no shadow: ordered before everything, it would otherwise remap the backdrop, bars, border and docks each time the shadow is turned on, which flashes the dimmed backdrop under an open overlay), and the blur window (`shell/BlurBackingWindow`, a pixel while nothing blurs, so turning the blur on or a fullscreen window leaving keeps it under the chrome on SwayFX). Resizing a mapped window doesn't remap it, and a held window that starts reserving is arranged in its map place (measured on sway and niri), so each keeps its place. A pixel-sized transparent window costs next to nothing.
- **Popouts sliding under a bar** (`axiom-popout-under`: detached bar popouts and edge popouts on a transparent bar's edge) aren't held. Each opens in its own window, which changes namespace between under and over the bar, so holding them would mean a window per bar kept at full size. Without `layerOrder` they open over the bar instead, sliding out within their own window, as they do over the overlay (`EdgePlacement.slidesUnder`, from `SurfaceContext.layout`).
