# The layer service: how axiom's layers are arranged and stacked

> **Files:** `qml/services/compositor/LayerManager.qml`, `qml/components/methods/layer/LayerStack.qml`, `tests/tst_LayerStack.qml`, `tests/layer/LayerStack.js`, `qml/components/methods/layer/LayerArrange.qml`, `tests/tst_LayerArrange.qml`, `tests/layer/LayerArrange.js`, `tests/layer/Fixtures.js`, `qml/components/hosts/window/LayerOrigin.qml`, `qml/components/hosts/window/LayerSlot.qml`, `backend/internal/compositor/render/hyprlua.go`
> **Config:** none
> **Related:** [The compositor](README.md), [Backend contract](contract.md), [Layer stacking](../generated/layers.md), [Bars and the border](../bar/layering-and-corners.md), [Hyprland IPC](../hyprland/ipc.md)

What a compositor does with axiom's layer-shell windows (which one reserves its space first, which is drawn on top, where each ends up) and the one service that decides it for every window, on every compositor. A window never sets its own layer: it states its place and the service answers. Read this before changing how a window reserves space, maps or rises over a fullscreen window.

### The daemon's contract
The daemon reads `LayerStack.qml` as plain JSON (`render.ParseTables`, from the constant `render.LayerStackFile`). The names it parses: the property `layers` and, per row, `namespace`, `order` and `noAnim`; the properties `blurSurfaces`, `blurBackdrops`, `blurReduced` and `blurChrome`. The other row fields (`layer`, `overFullscreen`, `modal`, `bar`, `why`) are the shell's; the daemon ignores them.
- On Hyprland the daemon writes one named layer rule per row that has an effect (`render.LayerRules`): `order` (Hyprland reads it as a surface maps) and `no_anim` in one `hl.layer_rule`. A rule that fails is tried again without its order and counts as refused.
- `compositor.layerRules` adds them (again after every config reload) and replies `{ ordered }`: true only when Hyprland took every rule. `HyprlandManager` publishes it as `supports.layerOrder`.
- On sway and niri the daemon writes no order: `supports.layerOrder` is false and the map order is the order.

### What a window states
- **Its row** in `LayerStack.layers` (the generated [layer stacking](../generated/layers.md) page lists them): `layer` (`top`, `overlay`, `bottom`, `background`), `order` (higher is arranged and drawn first; ties by map order), `overFullscreen` (`always`: on Overlay over a fullscreen window; `whileShown`: on Overlay there while shown; `never`: not shown while one is up on its screen; none: stays), `modal` (an instant action surface: last on Overlay, never mapped again, nothing new shows on its output and layer while it shows or is wanted, nothing moves onto its layer while it shows, where a move lands on top). Every namespace has one row (`check_structure`'s `layer-namespace-row`).
- **Its `LayerSlot`** (`hosts/window/LayerSlot`): `wanted` (its owner wants it shown) and `held` (stays mapped while not wanted, drawing and reserving nothing). The window binds `WlrLayershell.layer` to `slot.layer` and `visible` to `slot.shown`, and its namespace to its own `layerNamespace` (`layer-slot-binding`). Only the greeter's window and the no-parent notice, where no layer service runs, set a layer themselves.

### The pure model
- `LayerStack.layerOf(namespace, { fullscreen, wanted, movesKeepPlace, underModal })` answers the layer a window is on now, `""` for not shown now. The rules, in order: `hiddenUnderFullscreen` (a window that is never over a fullscreen window: the layer service hides it while one is up on its screen; the hot corner, the edge strips), `staysOnRowLayer`, `risesWhereMovesKeepPlace`, `risesWhileShown`, `downWhileNotShown`, `staysWhereMovesDont`; then `movesWaitForModal` keeps a window that would move onto the modals' layer where it is while a modal shows, where a move lands on top (`movesKeepPlace` false). A hidden slot's entry is `wanted: false, held: false` and keeps the row's layer.
- `LayerArrange.arrange` places every window (rects, `reserved`); `LayerArrange.sequence` decides which windows show and which map again, in `order`, from each output's slots as plain data.
- `LayerManager` runs both once per event turn and answers each owner: `slotOf(owner)` (`{ shown, layer }`), `slotOn(output, namespace)` (the same for the one window of a namespace on an output, null with none yet), `layerOn(output, namespace)`, `hasFullscreen(output)` (a fullscreen window is on that output, as the pass saw it; published in the same assignment as the layers, so a reader never sees one without the other), `rectOf(owner)`. Hosts read these and never re-derive them; nothing outside it reads `supports.layerOrder` or `supports.layerRestack`.

### Per compositor
- **Hyprland**: the daemon's order rules are in (`layerOrder`), so Hyprland keeps axiom's order whatever the map order, and a window moved to another layer keeps its place: nothing maps again at a fullscreen change. Axiom's own calculation doesn't see what Hyprland reserves for itself (`addreserved` on a monitor) or other apps' layers, so it is corrected from Hyprland's list (below).
- **sway** (`layerRestack`, no order): a window moved to another layer lands on top of it, so only the open overlay page moves over a fullscreen window and what is ordered over a moved window maps again; no dim is drawn over a fullscreen window there. The bars redraw once when a fullscreen window closes with the overlay open.
- **niri** (no order, no restack): a moved window keeps its place; the windows map in order and the surfaces fill themselves.
- **The fallback**: when Hyprland refuses a rule, `layerOrder` is false and the windows map one stage at a time in `LayerStack` order, mapping again where they land out of place, as on sway. `LayerManager` logs each change: `LayerManager: the compositor keeps the order (rules in)` or `LayerManager: map order (rules not in)`.

### What is excluded
`surfaces/greeter/GreeterWindow` (the greeter's own shell) and `qml/shell/NoParentNotice.qml` (shown where no shell runs) have rows but no slot: no layer service runs there. A window of another app is not axiom's to order.

### Measured (2026-10-16)
Probed in nested sway and niri: coloured, overlapping layer windows, a screenshot inside the session. Both gave identical results.
- **One sequence per output.** Within a layer, surfaces are arranged and drawn in the order they mapped, across all edges at once. A surface takes the usable area as it is at its turn: a top strip mapped before a left strip spans the full width and owns both top corners. The left strip starts below it.
- **Remapping goes to the end.** Toggling a `PanelWindow`'s `visible` off and on puts it after everything mapped meanwhile, both in arrangement and in drawing.
- **Margins count.** A surface's margin on its anchored edge adds to its exclusive zone. Zone 20 with margin 10 leaves 30 px for the next surface.
- **Exclusive surfaces first.** Every surface with an exclusive zone is arranged before any without one, whatever their map order. Non-exclusive surfaces are placed in what's left; `ExclusionMode.Ignore` surfaces get the whole output.
- **Drawn last is on top.** The surface mapped later is drawn over the earlier one.

### How axiom places its layers
- Every window whose position matters (bars, border strips, docks, integrated edge menus, free menus, edge popouts) has a `hosts/window/LayerOrigin`. It states how the window asks to be laid out to `LayerManager` (`setLayerSpec`, dropped with `dropLayerSpec`; the window itself is the owner): output, layer, anchors, margins, requested size (0 where it's stretched between two anchors), zone (`Ignore` is -1; `Auto` is its size across the edge), and whether it's mapped.
- `LayerManager` gives each window a map sequence number as it maps (dropped as it unmaps, so a remap goes to the end) and runs `methods/layer/LayerArrange.arrange` over them all, once per event turn on the input of every window and output as plain data (a `KeptList`, each window by its index), so equal content runs no pass. That arranges them in map order. Windows that reserve nothing and aren't mapped yet are placed too, where they'd go.
- `arrange` also gives each output's `reserved` (what the reserving windows take from each edge): niri's outputs' `reserved`, which niri doesn't report.
- `LayerOrigin.origin` is the window's rect from that; `placed` falls back to an estimate on its edge while there's none. `settled` is true once there's an origin, or 400 ms after it went missing (a window on a screen `LayerManager` doesn't lay out never gets one).
- **Corrections from Hyprland's list.** 600 ms after the rects last changed or a layer mapped, `LayerManager` pairs each mapped window's computed rect with Hyprland's own in its namespace (`LayerArrange.match`: nearest in place and size first, each taken once) and keeps the difference as that window's correction (`LayerArrange.correctionsOf`), which `rectOf(owner)` adds. Sampled only once things have settled, so a window resizing every frame keeps its last correction rather than a stale rect. Kept while a window is unmapped, dropped when it maps with no rect of its own reported. Each difference is logged: `scripts/log.sh --debug -g LayerManager`. `tests/fixtures/layers/` holds captured setups that `tst_LayerArrange` checks against Hyprland's own result. When a mismatch shows up, capture its input as another fixture and fix `LayerArrange`.

### Mapping in order
- Every axiom window but the two excluded ones (bars, border strips and corners, docks, integrated edge menus, free menus, the overlay, popouts, the OSD, the toast stack, prompts and pickers, the workspace overview, hot corners, edge triggers, the wallpaper and desktop widgets) binds `visible` to a `hosts/window/LayerSlot`'s `shown` (`LayerManager.slotOf(owner)`) and hands it what decides it as `wanted`.
- `LayerManager` runs `LayerArrange.sequence` over them (the same way, once per event turn, from the slots' state as plain data). On each output and layer, a window shows once every wanted window ordered before it has mapped (and had 50 ms to be drawn), so they map highest order first. A window already showing stays up when one ordered before it starts showing (the backdrop as the overlay opens). A modal window shows at once (`modalShowsAtOnce`, waiting for no window ordered before it), and a window not showing yet waits while one holds its output and layer (`waitsUnderModal`), so nothing maps over it. Both read `LayerArrange.modalHolds` (showing, or wanted in this pass), and so does `LayerManager`'s `underModal`. This happens on every compositor, Hyprland included.
- Windows of one order map by their `LayerSlot.rank`, lower first (the border's corners after its strips; bars of one namespace in `BarEnds.layerRanks` order, so bars of a kind stacked on one edge lie in list order). Ranks compare only within a `LayerSlot.rankGroup` (a bar's is its edge): bars on other edges sharing a namespace never meet, so one remade maps none of them again.
- A mapped window that a window ordered before it mapped after is out of place. It's hidden until it has unmapped, then shown again, and so lands after it. That happens, for example, when a bar is remade by a change of kind, which also changes its namespace. Where the compositor puts a window moved to another layer on top of it (`supports.layerRestack`: Hyprland, SwayFX, checked in 0.6; niri 26.04 keeps its place), the move counts as mapped anew: when the backing window comes back down to Top after a fullscreen window, the chrome ordered over it maps again. Each such remap is logged: `LayerManager: mapping … again, in its place`. Each layer move is logged: `LayerManager: … moves from … to …`.
- A held window ordered before the bars is built with them and kept for the session: nothing done at runtime (opening, closing, popping out, docking, a free menu at a widget) builds, destroys or moves one, since one that maps after the bars maps them all again. Only a layout change, a monitor change and a fullscreen window's coming and going do.
- A window that only maps while open (an integrated edge menu) would put everything after it out of place each time it opens. Such windows are `held`: they stay mapped while not wanted, drawing and reserving nothing (`LayerSlot.idle`).
- The held windows: integrated edge menus (a pixel deep, reserving nothing, while closed), free menus (a free menu's, and an edge menu's that can pop out: `surfaces/menu/FreeMenu`: full screen, `ExclusionMode.Ignore`, drawing nothing and with an empty input mask while closed; `axiom-menu` shares the integrated menus' order, which it never meets), each screen's backdrop window (`surfaces/backdrop/ScreenBackdrop`, a pixel in the corner while idle), the overlay's page (`hosts/overlay/OverlayPanel`, on Top after the backdrop and before the backing window, a pixel while closed; on Overlay while a fullscreen window is on its screen, and the toast stack's window, a slot on Overlay (order -10, tied with the popouts', nothing maps it again) that is always wanted), and the backing window (`qml/shell/BlurBackingWindow`, a pixel while it isn't drawing, so it keeps its place under the chrome on SwayFX). Resizing a mapped window doesn't remap it, and a held window that starts reserving is arranged in its map place (measured on sway and niri), so each keeps its place. A pixel-sized transparent window costs next to nothing.
- **A held window keeps one namespace.** A namespace change remakes its surface, which lands last on its layer and maps every window after it again; the overlay's reduced blur (`Overlay.reduceFullscreen`) is a rule turned off instead (`axiom-blur-reduced`; [translucency and blur](../theming/translucency-blur.md)).
- **Detached popouts** (bar popouts and edge popouts on a transparent bar's edge) aren't held. They open over the bar on the Overlay layer, in a window of their own, sliding in from off the screen (its window edge on the screen edge, `EdgePlacement.slideFrom`) over the bar, which draws the part over the bar itself and leaves the rest to the backing window, on every compositor.
