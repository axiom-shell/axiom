# Schema and its annotations

> **Files:** `qml/config/schema/`, `qml/config/json/config.schema.json`, `qml/components/methods/SchemaLayout.qml`, `qml/components/methods/SchemaValidation.qml`, `qml/components/forms/SchemaField.qml`, `backend/internal/compositor/render/layer.go`
> **Config:** every section
> **Related:** [Settings page](settings-page.md), [Saved configs and sharing](saved-configs-sharing.md), [Config manager](config-manager.md), [Config readers](config-readers.md), [Hyprland config modes](../hyprland/config-modes.md)

The schema is the single source of truth for config: shape, `default`s (there is no separate defaults file) and the generated settings page (`views/Settings/Settings.qml`). This doc is the complete list of `x-*` annotations: `scripts/check_docs.py` fails on one the schema uses that isn't named here, and building the schema (`axiom schema build`) refuses one missing from `qml/config/schema/annotations.yaml`, the registry with a line on each.

The schema is written in YAML (`qml/config/schema/`): `index.yaml` is the root and lists the sections and definitions in order; `sections/<Section>.yaml` and `definitions/{widgets,modules,views,common}/<Name>.yaml` hold one each. The YAML is read strictly (no anchors, aliases, merge keys or tags; quote `on`/`off`/`yes`/`no`, which YAML 1.1 reads as booleans; write `null` out), and every key of a schema node must be a draft-07 keyword the validators read or a registered annotation, so a typo fails the build with its file and line. A list of objects with declared `properties` (one the generic settings list draws) may require only fields with a `default`, plus `id` (an `ItemId`, which has none: a new item gets one free in its list, `SchemaValidation.newItem`), so the settings list's + never adds an item the config refuses; the build refuses any other. (Rule: AGENTS.md › Config.)

### Basics
- Adding a setting = a schema entry with a `default` + a reader property.
- Changing the layout of existing config = a format-2 step in the binary (`backend/internal/migrate/`) + a test; the format-1 migrations (`backend/internal/migrate/legacy/legacy.js`) are frozen.
- The live file is `~/.config/axiom/config.json` (`$XDG_CONFIG_HOME`, UI-owned).
- A schema reaches QML as a map, whose keys come out sorted, so order always comes from `x-order`.
- The settings page, forms and editors read the annotations: add an annotation rather than a hand-kept list in QML.
- A `$ref` may carry keys beside it (`default`, `title`, …) that override the definition's (`SchemaValidation._resolve`). `Lockscreen.layout` and `Greeter.layout` share `definitions/ScreenLayout`, each with its own default modules.
- `oneOf`s (bar widgets, overlay views and modules) are discriminated by `type`.
- A `pattern` is RE2 (a subset of JS's syntax), read as JS reads it: the binary widens `\s`/`\S` to JS's Unicode whitespace (`schema.CompilePattern`), and refuses a `\S` inside a character class.
- `x-inherit: "<path>"`: the setting may be `null`, and is by default, meaning the value at that dotted path (`Interface.radius` follows `Appearance.shape.radius`). On a `$ref`, the build makes an inheriting copy of the definition (`<Definition>Inherited`, every leaf `null` and inheriting from `<path>.<key>`): a bar's `style` from `Bars.style`. Validation lets the `null` through; the form shows the inherited value with "Follows … until set" (`SettingsManager.inheritedValue`), and readers resolve it (`BarsConfig.lookOf`).
- Build-time keys, never in the built schema: `x-inline: true` on a definition copies it into each use; `x-properties` beside a `$ref` makes a copy of that definition with its properties adjusted (a schema replaces or adds one, `null` removes one: `ScreenLayout` of `Layout`). `x-axiomActions: {except: [...], noArgument: true, extra: [...]}` (each key optional) on a string fills its `enum` from the bind actions table (`table.json`'s `ipcActions` less those named in `except`, then `exec`; with `noArgument` only those with no `{0}` and no `exec`; then the `extra` values, the field's own), its `x-enumLabels` from the Keybind definition's, its `x-enumIcons` from the table's icons and its `x-enumGroups` from the table's sections (an extra's from its own), and, on an `action` property, a sibling `argument`'s and `call`'s `x-showIf` (the actions whose IPC call takes `{0}`, and `exec`; those with `calls`): a hot corner's action, a QuickActions tile, a Button's click ([Actions](actions.md)).

### Placement
- `x-settings: false`: hides a key from the settings page (edited elsewhere, or UI-owned state).
- `x-category` (on a top-level section): names its sidebar category.
- `x-categories` (root, `[{ name, icon, cards, showIf }]`): orders the categories and gives their icons (`SchemaLayout.categories`). A category left out comes last, with a generic icon.
  - `cards: [{ card, title, first }]` are hand-built cards of the category's own (`views/Settings/<card>Card.qml`), always wide, after its sections' cards, in order (ahead of them with `first: true`: System's `SystemInfoCard`); `title` titles each, on the card and in the sidebar. A category with one can have no sections. Examples: System's `SystemInfoCard`, `DependenciesCard` and `SavedConfigsCard` ([Saved configs and sharing](saved-configs-sharing.md)); General's `DeveloperOptionsCard` (the developer options switch); Development's `DevTreeCard` and `DevConfigDiffCard` ([The axiom binary](../backend/README.md) › Dev mode).
  - `showIf` hides the whole category, its sections with it, as a section's `x-showIf` does (`/` keys only). Development's is `{"/$devOptions": true}`.
- `x-links` (on a section): pages its category's header links to: a view type (`Themes`, `BarEditor`), `Layouts`, or the layouts editor on a screen (`Layouts:lockscreen`, `Layouts:greeter`, `Layouts:desktop`). Labels, icons, availability and following go through `OverlayManager.pageLinkLabel` / `pageLinkIcon` / `pageLinkAvailable` / `followPageLink`.
- `x-link` (on a field, or a widget/module definition): where something it follows or names is set, drawn as a `SettingsLink` under the field in every form (`FieldLinks`), or in the bar widget / module inspector for a definition. `{ "setting": "<key path>" }` (a field, an object or a section: `SchemaLayout.locate` finds its card) or `{ "page": "<page link>" }` (as `x-links`), or a list of them. A link hides itself when its setting has no card or its page isn't shown. Examples: a bar's `style.shadow` → `Bars.style.shadow`, every `moduleScale` → `Widget.cardSize`, the Battery widget → `Battery`. `tst_SchemaLayout`'s `test_real_schema_links_resolve` checks every target.
- `x-order` (on an object): the keys shown first, in order. This applies to its form, its rows on a settings card (`SchemaLayout.rows`), or to its settings cards, whose order is their first field's. The build writes it from the properties' order on every object with more than one; one written in the YAML is kept.
- `x-group`: puts a field on a card of that name. One section or object can make several cards.
  - The bar and edge menu editors group a `Bar`'s / `EdgeMenu`'s own fields the same way (`SchemaLayout.objectGroups`, as `BarsConfig.fieldGroups` / `EdgeMenusConfig.fieldGroups`), and an `EntryListCard` its entry's (an `OSDEntry`'s Placement under the picker, Timing and behaviour beside it: [Settings page](settings-page.md) › Cards).
  - A nested object with an `x-group` joins that card (a group heading repeating the card's title is left out); `objectGroups` places a nested object's fields by their own or an ancestor's `x-group`.
- `x-scope` (`look` | `personal` | `commands` | `machine`, inherited, root `machine`): what a snapshot, example, import or export carries. See [Saved configs and sharing](saved-configs-sharing.md).
  - A new setting inside a look section that names a monitor, path or account needs `machine`; one that runs something (a command, a terminal) `commands`; a preference that means something on any PC `personal`.
- `x-scopeIf: { when, scope }` (on an array's item schema): an item that matches `when` (`x-showIf`'s form, over the item's keys) has `scope` as its own: an exec bind is `commands`, an app's OSD bar `personal`.
- `x-monitorRef` (`"off"` | `"drop"`, on a per-monitor part's `monitor`): a shared file names the monitor by its place, and a part for a place the user has no monitor for is turned off or left out (`share.Apply`).
- `x-libraryGroups` (root) lists in order the groups the bar editor's, layouts editor's and OSD editor's libraries sort their types into (by category; the last seven are the OSD systems': Keys & input, Audio, Connections, Power, Privacy, Capture, Events).
  - Each bar widget, overlay module and OSD system definition joins one with `x-libraryGroup` (`methods/LibraryOrder`, `reusable/TypeLibrary`).
  - `check_structure.py` errors on an unknown group.

### Hand-built parts
- `x-card: { file, title, wide, folds, perField }` (section):
  - `file`: adds `views/Settings/<file>Card.qml` as the section's first card, titled `title` (on the card and in the sidebar; the card's QML sets none).
  - `wide: true`: it spans both columns (the calendar accounts, chat API keys).
  - `folds: true`: it folds like the generated cards and joins Fold all, getting its group key `<Section>:<file>` as `foldKey`.
  - `perField: true` (with or without a `file`): each direct field becomes a card of its own, titled and described by the field, sorted by title, a switch's row labelled "Enabled" (`row.label`, `row.description` override the field's in `SchemaField`). The section's description gets a card first. Example: `ThemeIntegrations`, one card per app.
  - `check_structure.py` checks the file exists.
- `x-intro: "<Name>"`: puts `views/Settings/<Name>.qml` at the top of the section's own card, above its fields (NightLight's `NightLightStatus`).
- `x-row: "<Name>"` (field): its settings row is `views/Settings/<Name>.qml`, given the row (`row`) and the form (`form`), instead of the control its type picks (`SettingsField`), on its card among the generated rows and in search results (by its title and description). Only the settings page draws it; other forms leave it to its type. Example: `Input.keyboard.sources`, the Keyboard card's layouts (`InputSourcesField`).
- `x-rowDraws: [<dotted path>, …]` (field with `x-row`): other fields of its object that its row draws (`Input.keyboard.sources`' `method.enabled`, the input method switch). Their rows stay rows (search, the changed list, Discard, `/config` take them) with `drawnBy` (`SchemaLayout.rows`), but hide on the page (`SettingsField`), and a search, the changed list or a jump to it (`SchemaLayout.locate`, as `/config` and links make) shows the row drawing it instead (`SettingsSearch.filter`).
- `x-fold: true` (nested object): its rows fold behind its title, a `FoldHeader` row on its card, shut until opened (`SettingsManager.isFoldOpen`, kept as the cards' folds are) and always open in search results and the changed list, and opened by a jump to a row inside it (`SchemaLayout.rows`: the group row's `fold`, each row inside's `foldedBy`; `SchemaLayout.locate`'s `fold`). Example: the Keyboard card's Input method options.

### Behaviour
- `x-showIf`: hides a field unless a condition holds. `SchemaField` evaluates it (`SchemaLayout.showIfHolds`), so it works in every form; on a nested object it hides that object's cards.
  - Form: `{ sibling: value | [values] | { not: value } | { notEmpty: true } | { includes: value } }` (`includes`: a list holding that value, e.g. the OSD's Now playing options while its cards list picks `media`). Every key must hold. `backend/internal/schema/conditions.go` (`Holds`) is the same grammar in Go, checked against the shared fixtures.
  - `anyOf: [conditions]` holds when one of them does. Example: the OSD's `alongEdge`, shown only while its bars run along its edge.
  - A key starting with `/` is a dotted path from the config root (e.g. `"/Workspaces.layout"`), read through `SettingsManager.configValueAt`.
  - **Compositor.** Two `/` keys read the running compositor instead: `"/$supports.<capability>": true` (`CompositorManager.supports`) and `"/$compositor": "<kind>"`. See [The compositor](../compositor/README.md) › Hiding what a compositor can't do; `check_structure` fails a capability (here or in `x-needs`) that [contract.md › Capabilities](../compositor/contract.md#capabilities) doesn't list.
  - **Bar look.** In a bar widget's options, `"$bar.<key>"` (no `/`) reads the look of the bar it sits on: a `BarStyle` key as that bar uses it (`BarsConfig.lookContext`, passed as the form's `context` by the bar editor's inspector). The grouping reads `separate` for styles without boxes. Use it to hide a color the bar's style doesn't draw ([widget style](../bar/widget-style.md#which-color-fields-show)).
  - **Distribution.** `"/$distro": "<family>"` reads `DependencyManager.distro` (`Packages.distroFamily`: `arch`, `fedora`, or `""`), for a setting only one distribution has (the Updates options' AUR).
  - **Dev mode.** `"/$dev": true` reads `DevManager.enabled`, and `"/$devOptions": true` whether Settings shows the developer options: their switch (General's `DeveloperOptions` card, kept in dev.json; `DevManager.options`) or dev mode on (`DevManager.showsDevelopment`). Notifications' `devNotifications` shows by it.
  - **Package.** `"/$packaged": false` reads `Paths.packaged`, for what a packaged axiom doesn't have (the `SelfUpdate` section, `Greeter.source`; [packaging.md](../packaging.md)). `"/$clone": true` reads whether the tree is a git clone (`GreeterManager.report`'s `clone`, true until the first check), for what needs one (`Greeter.source`: a tree with neither `.git` nor `.packaged` has nothing to install the login screen from; [greeter-install.md](../features/greeter-install.md)).
  - On a whole section, `x-showIf` (with `/` keys only) takes the section out of its settings category when it fails (`SchemaLayout.categories`). The `Hyprland` section needs `configModes`.
- `x-enumShowIf` (`{ optionValue: condition }`): hides enum options whose condition doesn't hold. The current value stays listed.
- `x-enabledIf`: as `x-showIf`, but a field whose condition fails stays shown, greyed out, its value kept and not editable (`SchemaField.allowed`), with why above its description: `x-disabledNote`, or for `/$supports.<capability>` `CompositorManager.unsupportedNote(capability)` (the backend's `unsupportedHint` adds what can, e.g. "SwayFX can."), or "<Compositor> only." for `/$compositor`. Only a row shown on its own says it: a row that a sibling shows (a part's fields, `x-showIf: { part: true }`) is greyed without repeating the note under its switch. `SchemaLayout.compositorAllows` counts it too, so the launcher's `/config` doesn't offer such a setting.
  - **The rule for what the compositor can't do:** hide the row (`x-showIf` with a `/$` key). Grey it (`x-enabledIf`) only where a user would go looking for it (WindowBehaviour's `focusOnActivate`; the Workspaces layout and counts under niri, whose intro says why), or as a whole card through `x-hintedIf`.
- `x-hintedIf`: a compositor condition (`/$supports.<capability>` keys) for a row of a card the compositor might do with an upgrade: the row is hidden while it fails, unless every failing key's capability is one the backend names an upgrade for (`CompositorManager.unsupportedHint` isn't "": SwayFX on plain sway), when it's greyed out as `x-enabledIf`'s, with that note (`SchemaLayout.hintedHides`). It never says another compositor can. A card whose every row it hides goes too (`SettingsContent._groupShown`), and `compositorAllows` counts it. Every `WindowLook` row and the `Blur` definition's, and Appearance's surface opacity, carry it; a field only one compositor has adds `"/$compositor"` to its `x-showIf` (hidden elsewhere).
  - `x-disabledNote`: the note instead (English, translated); `false` for none, where the section's `x-intro` says why (the Workspaces section under niri).
- `x-beside: true`: puts a field beside the one before it on its settings card, each half wide (`SettingsGroupCard`'s two-column grid; Workspaces' rows beside columns). Give the pair the same `x-showIf`. A bar widget's options pair the same way in the widget inspector (`SchemaPropertiesForm`'s `pairs`), but only while both are shown.
- `x-wide: true` (field): the settings card the field lands on spans both columns (`SchemaLayout.groups`' `wide`). Put it on the field that needs the room, usually an array of objects (chat providers, Hyprland curves, session environment). See [Settings page](settings-page.md) › Columns.
- `x-applyOnSave`: keeps a setting in the draft until Save instead of applying it live (Hyprland's `mode`, which can take over files). An `x-takeover` setting waits the same way (`SchemaLayout.waitsForUser`).
- `x-snapshot: true`: a machine setting a saved snapshot carries too (the wallpaper setup: wallpapers, folder, mode, rotation, light/dark wallpapers, theme schedule), since a snapshot restores on the PC it was saved on. Exports and examples still leave it out. See [Saved configs and sharing](saved-configs-sharing.md).
- `x-takeover: true`: a setting that takes something over on this PC (Hyprland mode, locker, idle, polkit, greeter). Loading or importing a config, or editing config.json from outside while axiom runs, never changes it; only its own card does: the settings page holds it until Save (no preview) and the launcher's `/config` only opens it there. See [Saved configs and sharing](saved-configs-sharing.md).

### Controls
- `x-options`: a dynamic option list.
  - `"colors"`: a picker over `base00`–`base0F`, read with `Theme.resolveColor` (which also takes semantic names and hex).
  - `"screens"`: a monitor. Empty means the primary monitor, resolved by `General.screensNamed` (bars in `BarsConfig.expandBars`, docks, edge menus). Docks and OSDs pick all monitors through `monitors` instead.
  - On an array's `items` (strings), `"marketSymbols"`'s options become toggle chips, committed in the options' order (a `"screens"` list stays free text: it may name monitors not plugged in): `"marketSymbols"` (the Markets watchlist's ids, labelled by label or symbol: a markets widget's or module's `symbols`).
  - Others: `"languages"`, `"edgeMenus"`, `"customWidgets"`, `"marketSymbols"`, `"overlayPages"`, `"notes"`, `"timezones"`, `"regions"` (Qt locale codes, `DateFormats.regions`, labelled by their own language and country), `"calendars"`, `"chatProviders"`, `"chatPresets"`, `"cursorThemes"` (`SettingsManager.optionsFor`).
- `x-emptyLabel`: offers or renames the empty value under that label.
  - On a color: automatic (a bar's `widgetTextColor`).
  - A color without it lists its `default` first, labelled as the default, so an override can be undone.
  - On `"screens"`: renames empty where it means something else, as in `General.primaryMonitor` itself.
- `x-allScreens`: adds All monitors (`"*"`) to a `"screens"` picker.
- `x-enumLabels` (`{ value: label }`): labels shown instead of raw enum values in dropdowns (and on an array of enum strings' chips, on the array or its `items`).
- `x-enumIcons` (`{ value: icon }`, on an array of enum strings or its `items`): a Material Symbols icon on each option's chip (an OSD's status icons).
- `x-ordered: true` (on an array of enum strings): the order counts, so the field keeps the user's (`SchemaOrderedChips`): the chosen options drag into place, and the others are added at the end from a list below. Without it the chips are committed in the options' order. Marked where the order is shown: QuickActions' tiles, the power menu's and Power module's buttons.
- `x-enumGroups` (`{ value: group }`, on an `x-ordered` array or its `items`): files each option not yet chosen under a group header, the groups in the order each first comes. `x-axiomActions` fills it from the table's sections.
- `x-suggestions` (`"audioApps"`, `"wallpaperCollections"`, `"notificationApps"`: the history's apps and the shell's sources, labelled by name): chips under a text field (`SettingsManager.suggestionsFor`).
- `x-multiline: true`: a growing text area that holds line breaks (Enter makes one, Ctrl+Enter commits). Without it a text field is one line, wrapped to four as it grows.
- `x-control`:
  - `"slider"` | `"stepper"`: overrides the integer control choice (below).
  - `"readonly"`: shows a string with a copy button instead of a field (an edge menu's `id`).
  - `"folder"`: a string with a Browse button opening the desktop's folder picker ([File picker](file-picker.md); the wallpaper, notes, screenshot and recording folders, Claude usage's `configDir`, System stats' `diskPath`). It hands back `~/…`, so whatever reads the setting expands `~` (`Paths.expandHome`).
  - `"search"`: a long option list (e.g. `"timezones"`) is typed into to filter it (`SchemaField`; the Clock module's and World clocks' `timezone`).
  - `"icon"`: a string holding an icon: a field led by the icon itself, whose list searches the bundled Material Symbols by name and tag; anything else typed or pasted (a Nerd Font glyph) is kept ([Icons](icons.md)). Every icon setting takes it (`check_icons.py` checks their defaults).
  - `"toggle"`: a string enum of two or three values: a capsule with every label in an equal segment and an accent thumb that glides to the chosen one (`forms/SchemaToggle` on `reusable/StyledToggle`), instead of a dropdown. With two a click anywhere on the row flips it (a detached surface's `animation`: Slide or Fade); with three a click picks the segment under it (Interface's `density`). Give it to a choice that isn't on/off whose labels are short enough to leave the row its title (no more than about 15 characters each for two, 10 for three); longer ones, Hyprland's numeric enums, `x-takeover` fields and the monitor `mode` pickers stay dropdowns. More options, or a value from a filtered list that leaves one, fall back to the dropdown.
- Integers render through `forms/SchemaNumberField`:
  - a slider with a value box for 7–200 steps, else a stepper, with ±10 buttons past 20 steps
  - steppers commit debounced, sliders on release
  - `x-unit` (`px`, `%`, `ms`, …) is shown after the value. The duration units `s`, `min`, `h`, `d` mean the value is stored in ms and shown in that unit (`SchemaLayout.unitScale`): its default, bounds and `multipleOf` are in ms.
- `x-auto: { value, start }`: a switch in front of an integer whose `value` means automatic. Turning it on stores `start`, then the number shows (the toasts' `gap`). `value` is `null` in each (a bar's `floatingGap`, the toasts' `gap`, a per-app rule's `timeout`): validation lets the `null` through, as an inheriting setting's, and the number keeps the field's whole range.

### Types (bar widgets, overlay modules, views, custom widget elements)
- `x-icon`: a Material Symbols name on bar widget, overlay module and view definitions.
- `x-elastic: true` (on a bar widget definition, `elastic` in its `schema.yaml`): the widget shrinks when its bar is crowded (Window title, Media), so `BarWidgetHost` sizes it elastic and only it takes a `layout.minSize` and `layout.maxSize` (`BarsConfig.isElastic`, the only place it's stated: its QML sets no `sizePolicy`).
- `x-priority: N` (on a bar widget definition, `priority` in its `schema.yaml`): the widget's own priority when the bar is crowded (default 0: Clock 5, Workspaces 10), which its `layout.priority` overrides (`BarsConfig.defaultPriority`, read by `BarWidgetHost` and the editor's drop order).
- `x-keywords` (on a bar widget definition, `keywords` in its `schema.yaml`): more words the bar editor's library finds it by (`LibraryOrder.filtered`), such as the label it had before.
- On overlay modules:
  - `x-defaultSize` (`[w, h]` in grid units, four to a card): the size it's added at.
  - `x-minSize`: the least a drop into a gap shrinks it to; half the default when left out (`OverlayConfig.minSize`).
  - `x-hosts`: `overlay`, `edgeMenu`, `lockscreen`, `greeter`, `desktop`. `overlay`, `edgeMenu` and `desktop` when left out, so the lock screen and the greeter only take modules that list them. Every module on overlay pages goes on the desktop too (`check_structure`).
  - `x-lockActions`: what a module on the lock screen does there, each a set of service methods `check_structure` lets it call (`session`: `SessionManager.sessionAction`; `media`: `MediaManager`'s transport and player; `volume`: `AudioManager`'s mutes and steps, with their OSD; `layout`: `InputSourceManager.next|prev`; `unlock`: Password's `AuthManager` and required-field report). Any other call there but a read, or one marked `// lock-inert: <reason>`, fails.
  - `x-keyboard: true`: the module takes typing. The desktop, which otherwise never takes the keyboard, takes it on a click while its layout shows one (`OverlayConfig.moduleInfo(type).keyboard`, `ScreenLayoutView.wantsKeyboard`). Needed for a typing module on the desktop: `check_structure` fails a desktop module with a text field (in its file or its content parts) and no `x-keyboard`. `false` says it stays read-only there on purpose (ClockCalendar).
  - `x-required`: part of every grid on its hosts; never removed, duplicated or in the library (the lock screen's `Password`).
  - `x-canvasDetail`: a module property the layouts editor shows on its tile (a list joined). `x-canvasFill`: a color property the tile is filled with (`OverlayConfig`).
- On custom widget elements (`CustomElement`, `qml/components/content/parts/custom/elements/<Type>/schema.yaml`; `CustomWidgetsConfig.elementKinds`):
  - `x-defaultSize` (`[w, h]` in sub-cells, four to a grid unit): the size it's added at.
  - `x-slots`: its bindings, in order (keys of its `bind`), each a row of the inspector's Shows.
  - `x-actions`: the commands it runs, in order (keys of its `actions`), each a row of the inspector's Runs.
  - Its `options` are its look, a form of its own; `color: state` or `color: text` adds the colour (`CustomElementBase.yaml`'s parts: Auto takes the state's colour on graphics, a switch asks for it on text).
- On OSD systems (`OSDSystem`, `qml/components/surfaces/osd/systems/<Type>/schema.yaml`; [OSD](../features/osd.md) › Engine): an item of an OSD's `systems` list, its own settings beside `type` and `quiet`; `tile: standard` and `card: standard` add the switches `tile` and `card` for the parts it has (`OSDSystemBase.yaml`'s parts); `group` its group in the add-picker (one of `x-libraryGroups`, as a bar widget's). `barNames` (`x-barNames`): its bars, which the settings' Bars part lists and edits (`OSDBarsEditor`, `OSDConfig.barRows` / `barKinds`) and which name an OSD's tab (`OSDConfig.labelOf`), and how each is keyed (`OSDParts.barKey`: its key in the system's `exposes`, what an OSD's `barOrder` names after its type; `tst_OSDSystems`' `test_barKeys` checks the two agree): `{ bar }`, it is one bar of that key, named by its own label (Brightness's `{ bar: brightness }`; it isn't listed under Shows); `{ from, by, named, repeats, keys, barOnly }`, each entry of its setting `from` is a bar (left out of its form under Shows; each with an `ItemId` `id`), named by its `named` list joined, else by its `by` field's `x-enumLabels`, its row's icon its `x-enumIcons`; its kinds in the Bars picker are the `by` field's `enum`, `repeats` those it may have more than one bar of; a bar's key is its kind, else what `keys` names for that kind, and for a kind it repeats `<kind>:<its id>`; `barOnly` is what an item added only for a bar starts with, and an item left with no bars and only that is removed with its last bar (Audio's `{ from: bars, by: type, named: apps, repeats: [app], keys: { microphone: micLevel }, barOnly: { tiles: [], card: false } }`: an App bar by its apps, the others by their kind; keys `master`, `other`, `micLevel`, `app:<id>`).
- `x-tool: true` on the hand-built view types: the navigator's tool group.
- `x-window: true` on a tool page that can also open as a window of its own (`OverlayConfig.isWindowable`, `windowTypes`; [page windows](../overlay/page-windows.md)).
- `x-needs: "<capability>"` on a view type: the page is left out (and its launcher command unlisted) unless `CompositorManager.supports` has it (Keybinds, Monitors).
- `x-autoColor` (`accent`, `alt`, `warning`, `critical`, `off`, `neutral`): a bar widget color picked by its bar when left empty (`BarsConfig.autoColorFields`, `methods/BarAutoColors`). See [Bar widget style](../bar/widget-style.md).

### Compositor config (`x-compositor`)
A setting a compositor's config takes says how, per compositor: `x-compositor: { hyprland: {…}, sway: {…}, niri: {…} }`. `render.CompositorFields` in the daemon collects a section's annotated fields (inside its objects too) with their spec. Each is written, under a gated part (the input), only while its `if` switch is on, else once changed from its default; a managed config's options every one (`render.AnnotatedFields`).
- Every compositor's spec takes:
  - `key`: Hyprland's option path (or a list of paths), sway's command with `{}` for the value (`"input type:keyboard repeat_rate {}"`), or niri's node path (`"input.keyboard.repeat-rate"`, its value the node's argument).
  - `scale`: a factor for a value stored scaled (0.01 for a percent, 0.001 for ms written as seconds).
  - `if`: a boolean beside it (a part's `enabled`), or a dotted path to one under the same object (`keyboard.enabled`): written, default or not, only when that is on.
  - `from`: the value written is derived from the one stored: `xkbLayout` / `xkbVariant`, the input sources' xkb layouts or variants as comma lists (`render.XkbLayouts`, the port of `InputSources.xkb`; an engine's layout counts only while the section's `method.enabled` is on).
  - A list of specs instead of one: the field writes several options, each its own spec (`Input.keyboard.sources`: the layouts and the variants).
  - `skip`: a value written as nothing, so the compositor's own default stays (`"default"`, or niri's `0`).
- Hyprland (`render.ConfigTable`, one value of a nested `hl.config({...})` table):
  - `value`: `"int"` (a boolean as 0/1), `"number"` (an enum of numbers written as strings), `"color"` (a theme color name as `rgba(hex + alpha)`, `alpha` `"ff"` unless given).
  - `device: <kind>`: a per-device option (`key` its `hl.device` name), left out of the table and written for each device of that kind (`touchpad`: a pointer named like one; [Hyprland config modes](../hyprland/config-modes.md) › Input).
  - `always: true`: written even when it's the schema default. Other fields are only written once changed, so Hyprland's own default (and the user's files) stay in charge otherwise.
- sway (`render.SwayOptionLines`; [Sway backend](../compositor/sway-backend.md)):
  - `value`: `"enabled"` (a boolean as `enabled`/`disabled`), `"yesNo"` (`yes`/`no`), `"enableDisable"` (`enable`/`disable`), `"raw"` (as it is, unquoted). Without one, the value is quoted as one argument (`render.SwayQuote`).
  - `map`: `{ value: sway's word }` for an enum whose names differ from sway's; a value missing from it is left out.
  - `configOnly: true`: sway takes the command only from a config file (`xkb_numlock`): left out of what's sent at runtime.
- niri (`compositor/render`'s `niri.go`; [niri backend](../compositor/niri-backend.md)):
  - A boolean is written both ways (`prefer-no-csd false`), so axiom's off wins over a user's own on.
  - `value`: `"flag"` (the node alone when on, left out when off, for a flag niri has no off form for: `tap`, `focus-follows-mouse`), `"onOff"` (a child `on` or `off` under the key: `animations`, `xwayland-satellite`, `layout.tab-indicator`), `"not"` (a boolean written negated: `clipboard.disable-primary` for middle-click paste), `"offFlag"` (the node alone when off, left out when on: `warp-mouse-to-focus` for `noWarps`) or `"float"` (written with a point, where niri wants a float).

- `x-greeter: true` on an `Input` option: the greeter's compositor takes it (`methods/GreeterBundle`). See [Greeter install](../features/greeter-install.md).
- Details: [Hyprland config modes](../hyprland/config-modes.md), [Window look](../compositor/window-look.md).

### Theme integrations
- `x-hookup` (on a `ThemeIntegrations` boolean): how the integration hooks into its app (targets, place, text).
- `x-hookupNote`: a note shown with it.
