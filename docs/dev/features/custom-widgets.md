# Custom widgets

> **Files:** `qml/config/CustomWidgetsConfig.qml`, `qml/services/apps/CustomWidgetsManager.qml`, `qml/services/apps/CustomWidgetsEditor.qml`, `qml/components/views/CustomWidgets/`, `qml/components/methods/CustomWidgetData.qml`, `qml/components/content/CustomWidget/CustomWidget.qml`, `qml/components/content/parts/custom/` (the elements in `elements/<Type>/`), `qml/components/bar/widgets/CustomWidget/CustomWidget.qml`, `qml/config/schema/sections/CustomWidgets.yaml`, `qml/config/schema/definitions/custom/`, `qml/config/schema/definitions/kinds/CustomElementBase.yaml`
> **Config:** `CustomWidgets.items` (reader `CustomWidgetsConfig`)
> **Related:** [Services pattern](../core/services-pattern.md), [Protocol](../backend/protocol.md) (`exec.watch`)

A custom widget is a script drawn as a bar widget, that widget's popout and a module (overlay, desktop, edge menu and, when allowed, the lock screen), all from one definition in `CustomWidgets.items`, so the script runs once for all of them. Its output is read as Waybar reads a `custom/*` module's, so Waybar scripts run unchanged.

### The page
Two `ToolPane`s on a `BaseView` (docs/recipes/tool-page.md): "Custom widgets" on the left (the list pinned above, then the selected script's fields) and "Custom widget" on the right (an `InspectorHeader` for the selected definition, its Data, Bar and Module tabs, the Data and Bar tabs' groups in `GroupColumns`); the Module tab's element column and canvas are two boxes side by side.

### Definitions
Each item (`definitions/custom/CustomWidget.yaml`) holds:
- the script: `command` (run by `sh -c`), `mode` (`poll` every `interval`, `stream` one sample a line, `once`), `output` (`waybar`, `json`, `text`), `execIf` (Waybar's exec-if) and `refreshName`;
- `actions`: Waybar's on-click, right and middle click, scroll up and down, and `actions.named` (the same five as named actions, below); `invoke.command` is the action command those run;
- Waybar's `format`, `formatIcons`, `maxLength`, `escape`, plus `states` (class → theme colour), `hideEmpty`, `tooltip`;
- `bar` (the bar widget's style) and `module` (its design size, its base `elements`, its `views` (screens), its `font` for Text elements, whether the lock screen offers it);
- `samples`: a sample output per screen (the screen's id, `""` for no screen), at most 16 entries and 64 KB as JSON, saved in the definition (`x-settings: false`, edited through the Data tab).

The fields, each read from the output's key of the same name (the script shapes its own JSON; nothing maps them): Waybar's `text`, `alt`, `tooltip`, `class`, `percentage`, and axiom's `icon` (Material Symbols), `value` / `min` / `max` / `unit`, `subtext`, `state`, `badge`, `urgent`, `image`, `items` (rows of `{text, icon, value, subtext, id}`) and `hidden`. Plain text that's a number is the `value`; text matching a `formatIcons` key is the `alt`; a format-icons pick that's a Material Symbols name is the `icon` when the output has none.

### Reading an output
`CustomWidgetData` is the pure half:
- `parse`: a JSON object as is; Waybar's text output as lines text, tooltip, class (a streamed line is only text).
- `resolve(definition, sample, context)`: the fields, the format filled (`{}` / `{0}` the text, `{icon}` the format-icons pick, any field or path), `escape` before filling, Pango markup turned into Qt rich text (`pango`), the colour (`stateColor`, see the script contract), `ratio` (the value between min and max; `percentage` alone is a value on 0–100), `hidden` (empty text, as Waybar; never while failing), and `state`, `rev`, `actions` (`actionsOf`), `failure` / `error` (`failure`), `hiddenByScript` (the output's own `hidden`) and `interactive`. The `context` is the manager's (`CustomWidgetsManager._context`): the theme's colour names, the script's last run and whether the definition is interactive; without one `resolve` still works (no colour names, no failure).
- Named actions: `actionEnabled(actions, id)` (a built-in always; no `actions` in the sample: all; else only the ids it lists on), `shellQuote` and `fillCommand(template, {action, value, rev, tree})` (one pass, each value inserted already quoted: a plain number bare, else single-quoted, empty `''`; a placeholder after `$`, with no value, or `{text}` stays as typed), `builtinAllowed(id, refused)` (false for `axiom:<x>` with `x` a session or destructive action).
- `truthy` (what a script's value counts as on), `isThemeColor`, `actionsOf`, `failure`: the rules the script contract names.
- `flatten` lists a sample's paths for the editor's dropdowns.
- Screens: `allElements` (the base and every screen's elements), `matches(when, fields)` (a screen's condition), `pickView(module, fields)` (`{ index, builtinError }`), `historyBindings` (the Sparkline `value` and `value2` bindings of every layer), `series(v, cap)` (a script's list as its finite numbers, the last `cap`; null for a non-list).
- `lattice`, `designSize`, `pageSize`, `rect`: the module's lattice, 4 sub-cells a grid unit (16 a card), the elements' bounds (so the box fits them), laid out proportionally over whatever size the module gets.

### Script contract
What a script prints and how the definition reads it. Output modes (`poll`, `stream` one sample a line, `once`) and formats (`waybar`, `json`, `text`) are as above; Waybar `custom/*` scripts keep working unchanged.

| key | meaning |
| --- | --- |
| `text`, `alt`, `tooltip`, `class`, `percentage` | Waybar's (Pango in `text` / `tooltip` unless `escape`) |
| `icon`, `value`, `min`, `max`, `unit`, `subtext`, `badge`, `urgent`, `image`, `items`, `hidden` | axiom's, as above |
| `state` | the script's **mode name**: matched by screens (`module.views`), looked up in the definition's `states` for the colour |
| `rev` | the screen's revision, kept as text; later passed back to an action as `{rev}`, so an action can refuse a stale screen |
| `actions` | `{<id>: {enabled}}`: with it, an action it doesn't list is off; `enabled` is read through `truthy` (`false`, `"false"`, `0`, `no`, `off`, `""` are off; missing is on). Ids that aren't action ids (`^[A-Za-z0-9_.-]{1,64}$`) are dropped |
| `error` | non-empty: the widget is failing (interactive definitions only, below). Plain text (`false`, `0` and other values `truthy` reads as off are no error) |
| anything else | data, bound by path (`player.title`, `items.0.text`) |

- **Colour.** `stateColor` is the first that holds: `states` (over the default class map: `ok`, `warning`, `critical`, …) maps the `state`; the `state` is itself a theme colour name; `states` or the class map maps the first `class` that it knows. **A `state` that is none of these, or a hex, colours nothing** (it used to pass a hex through): `state` names a mode, the definition maps it to a colour.
- **Interactive.** A definition with an action command (`invoke.command`; the command's placeholders and the actions that run it come with the named actions) or with screens (`module.views`) is interactive. Only an interactive definition fails: `failure` is, in this order, `start` (the script couldn't start), `stopped` (a stream that ended with a non-zero exit), `exit` (a non-zero exit with no output) or `script` (the sample's own `error`). It carries `kind`, `message`, `exitCode` and `stderr`; `resolve` returns it with `error` (the message) and never hides a failing widget. While it fails, an element's `stateColor` (`CustomElementBase`) is the error colour (`Style.error`), over the state's. A definition without an action command draws and hides as it always did: exit codes, start errors and `error` change nothing there.
- **Stderr and exits.** An entry carries the run's last non-empty stderr line (300 bytes) and, for a stream that ended with a non-zero exit, `exited`: the exit is published even with no output, so a stream that dies at once (`echo boom >&2; exit 3`) is `stopped` with "exited with code 3: boom". `exited` clears (with the exit code and `stderr`) once the next process has run 1 s. A stream restarts after a backoff; Restart (`axiom ipc customWidgets restart`) doesn't wait for it.
- **Lifetime.** A watched command runs only while some bar widget, popout, module or the editor shows its widget (`CustomWidgetsManager._sync`; a stream is killed). A stateful widget keeps its state **outside** the stream (a daemon or a file), and its action command must not need the stream. An element or bar click always has its widget shown. `invoke`'s `fromIpc` answers `not shown` when nothing shows the widget (shown = an id in the manager's registry; the editor's running definition counts), for the named-action IPC (`axiom ipc customWidgets act` / `actValue`), which isn't added yet. Long jobs (an update) detach and report through that state; the action command exits quickly.
- cava and other frame-rate streams are unsupported: a stream is coalesced to 4 pushes a second.

### Named actions
Elements and the bar name an action instead of holding a command (`CustomElementBase.yaml`'s `action`, the bar's `actions.named.*`; a non-empty name wins, the commands stay for Waybar-style widgets). One id rule: `^(axiom:)?[A-Za-z0-9_.-]{1,64}$`. `CustomWidgetsManager.invoke(id, action, value, continuous, fromIpc)` runs it and returns `""` or why not:
- **Built-ins** (`axiom:refresh`, `axiom:restart`, `axiom:<ActionsManager id>`; `CustomWidgetsConfig.builtinActions` lists the first two) need no command and are always enabled. `builtinAllowed` refuses a session action (`ActionsManager.sessionActions`) and a destructive one (`ActionsManager.destructive`): `"refused"`.
- Any other id runs the definition's action command (`invoke.command`, one `sh -c` line through `CommandManager.run`, so it waits for the exit): `{action}`, `{value}` and `{rev}` are filled in (`fillCommand`; `{value}` is a Button's `value` slot, a List row's `id`, else `value`, else its text, a Toggle's `on` / `off`, a Bar element's released number), and at exit 0 the script runs again when `actions.refreshAfter`. `"no action command"` when it is empty; `"failing"` while the script isn't answering (`start`, `exit`, `stopped`; a `script` failure leaves the sample's `actions` in charge); `"disabled"` when the sample's `actions` don't list it (or list it off); `"locked"` in the greeter or with the built-in lock up.
- `fromIpc` (for the named-action IPC, not added yet: nothing passes it today) answers `"not shown"` when nothing shows the widget (an id in the manager's registry; the editor's running definition counts), before anything else but a missing definition. An element or bar click always has its widget shown.
- `act(id, action)` (the bar) runs the named action for `actions.named[action]` (a scroll is continuous), else the command as before. `actionLabel(id)` names a built-in for a button with no label (Refresh, Restart, the action's name).
- In an element, `CustomElementBase.run(kind, value, continuous)` runs the element's named action, else its `kind` command; `canRun` is false (greying Button, List rows, Toggle and a Bar slider) when actions are off, the sample disables it, or a script action can't run (`invokeSet`, `failing`, which `CustomLayout` passes down). The Button's `enabled` slot (a bound value read through `truthy`) can switch it off too.
- **Hold.** A discrete press (a Button, List row, Toggle or a bar click) holds the widget's script actions (`CustomWidgetsManager.busy[id]`, `{action, run, phase, until, sampled}`; `invoke.hold`, on by default, switches it off): `"busy"` for another one meanwhile (hold covers the whole widget's script actions, not just the pressed element's), so a double press acts once. It lasts while the command runs (`holdCap`, 15 s), then until the next sample or a second after the exit (`holdGrace`; a sample that arrived while it ran ends it at the exit); a failing command releases it at once. Each hold carries its run's number, so a late exit of an older run leaves a newer hold alone. A **continuous** run (a bar scroll, a Bar element's slider) never holds: one runs at a time per action and the value sent meanwhile waits, the latest replacing any waiting one. Built-ins never hold and stay enabled; one `Timer` is set to the earliest end. Elements read `busy` through `CustomLayout`, so `canRun` greys them.
- **Failure feedback.** `lastAction[id]` (`{action, failed, exitCode, message, at, run}`; the message is the last stderr line, 300 chars, or "The action failed with code N") is what an element reads as `failed` (`CustomElementBase.failed`, its action's last run): a Button flashes (`Style.errorWash` through `ColorGlide`, held 1.2 s by a fixed Timer) and says it in its tooltip until it runs again; a failure is also one `console.log` line (a script failing is not a shell problem). The Button's `color` (a theme name, `Style.resolve`) makes it a filled `Surface` with `CustomElementBase.inkOn` for its label and icon (the one place that computes the ink of a data colour; Status uses it too); `disabled: hide` hides it while the script or its `enabled` binding has it off.
- The editor's inspector offers an Action combo in "Runs" (none, the built-ins, the shell's allowed actions, the ids the output's `actions` lists; any id can be typed), shows the commands only while it is empty and warns "Set the action command first" when the definition has none; the Script group edits `invoke.command`, the Bar tab `actions.named`.

### Running
`CustomWidgetsManager.acquire(owner, id)` watches the definition's command through `CommandManager` (format `json` unless the output is plain text) under its own owner per id; the merge by command string means a widget on two bars and a module still runs one script. Each push whose `CommandManager.runs[command].at` changed is resolved into `fields[id]`, and an edited definition (its format, icons, states: the page's preview) re-resolves its last output at once, without adding to the history; `outputs[id]` keeps the raw text, value, exit code and error for the editor, and `history[id]` the last 60 values of the widget's value and of each Sparkline element's binding. With an `execIf`, the script is watched only once that command succeeds (checked when first shown and on refresh).

`runCommand(id, command, value)` runs a command detached (`{value}` filled in by `fillCommand`, shell-quoted unless a number), then refresh the script 300 ms later. Nothing runs in the greeter or while the built-in lock screen is up. `axiom ipc customWidgets refresh <name>` (refresh name, id or name) stands in for Waybar's `signal`: a script calling `pkill -RTMIN+N waybar` should call that instead.

A stream is coalesced to 4 pushes a second by axiom (`backend/internal/command/stream.go`), so frame-rate scripts (cava) look choppy. `outputs[id]` also keeps `stderr` (the script's last stderr line) and `exited` (a stream that ended with a non-zero exit; its output is its last line), which come with each push (`CommandManager.runs[command]`) and feed `_context`. `CustomWidgetsManager.restart(id)` (`axiom ipc customWidgets restart <name>`, name as `refresh`) stops a stream's process and starts a new one at once (`CommandManager.restart`, `exec.restart`); a poll just runs again. `_command(def)` is the command a definition's script runs as.

### Screens
`module.elements` is the **base layer**, drawn under every screen (today's elements: no migration); `module.views` adds a layer per screen: `{ id, name, base, when: { key, test, values }, elements }`. `when.key` is a key or path in the output (`state` when empty), or `error` for the failure; `test` is `is` / `isNot` (the value's text is, or is not, one of `values`; `isNot` with none never holds, `is` with none never holds; an `error` key's `is` / `isNot` never hold while the widget isn't failing) or `set` / `unset` (`truthy`). The first screen whose condition holds is drawn over the base (`base: false` hides the base under it); none: the base alone, and a definition with neither screens nor elements draws the default icon and text. While the widget fails (`fields.failure`) only screens keyed on `error` are tried, none: the **stock error screen** (an `EmptyState` with the message and, while actions are on, a Restart button running the built-in `axiom:restart` (`CustomWidgetsManager.invoke`)). A definition with screens is interactive, so a script printing no `text` still draws (`hiddenByScript`, not `hidden`, hides an interactive module) while a Waybar script that exits 1 with no output stays hidden. All layers share one lattice (the bounds of every layer, `allElements`), so the popout is sized once.

### Samples
So a screen can be designed before the script reaches it, the definition keeps a sample per screen. `CustomWidgetData.viewKey(module, index)` is the key (a screen's id, `""` for the base alone), `keepSample(samples, key, sample, limits)` returns `{ samples, refused }` (`"count"` for a new key past the entries cap, `"size"` past the byte cap; nothing is changed when refused) and `sampleForView(definition, index, seen, liveFields)` picks the one a screen is previewed with: the kept one, else the last one seen live for it, else the live one when it is what picks that screen. `CustomWidgetsManager.resolveSample(id, sample)` resolves a sample as a successful run would be (`exitCode` 0, so it never fails). The editor keeps `seen` (view key → the last live sample that picked it) and `seenStates` (the distinct `state` values seen, the first 8) for the page only, cleared when another definition is selected; `keepSample()` saves the live sample for the edited layer, `removeSample(key)` forgets one and `previewFields` is what the Module tab's previews draw (a `Notice` says "No screen for this sample" when the base is empty and nothing picks a screen). The Data tab's Samples group has Keep (greyed with the cap's reason) and the list of kept ones. These editor members read the manager only while the page shows (`pageShown`), as the manager creates the editor.

### The module
`qml/components/content/CustomWidget/CustomWidget.qml` is a `Panel`: in a card (`properties.definition`) it fills its slot; as the bar widget's popout (`definitionId` from the anchor's `extraData`) it's the definition's design size at the screen's card size (`OverlayConfig.cardUnitOn`, `GridPlacement.span`), declared up front as `maxImplicitWidth/Height`, since an open popout never resizes. It acquires its definition while shown; actions are off on the lock screen (`host.kind`) and in previews (`host.preview`). It sets no `fullMinWidth`/`fullMinHeight` and has no `compactContent`: its elements are laid out proportionally, so any size draws them (the editor's previews show the usual ones). It builds either the layout or, with nothing to show, an `EmptyState` saying why.

`CustomLayout` (`qml/components/content/parts/custom/`) draws the elements in two layers, each a `KeyedLoader` (key `base` or `v:<screen id>`; nothing built while empty) holding a Repeater by count over the base elements (or `CustomWidgetsConfig.defaultElements` when there are neither screens nor elements) and over `module.views[viewIndex]`'s, each a `CustomElement` (a Loader of `elements/<Type>/Custom<Type>.qml`: prefixed, so an element named after a Qt type, Text, Image or List, never shadows it) at `CustomWidgetData.rect` of its place, a `Widget.px(6)` gap between neighbours.

Element kinds are a schema kind like bar widgets and modules (`index.yaml`'s `kinds.CustomElement`): each `elements/<Type>/schema.yaml` (a `label`, `icon`, `defaultSize` in sub-cells, `slots`, `actions` and its look as `settings`, expanded over `CustomElementBase.yaml` into `<Type>CustomElement`) beside its QML. So its options have their defaults filled at load like any setting, `CustomWidgetsConfig.elementKinds` reads the library from the schema, and the reference is generated (`docs/dev/config/CustomElements/`). The `color` part gives graphics an Auto colour that's the state's when the script gives one (`color: state`) and text a colour plus a Colour by state switch (`color: text`); `CustomElementBase.colorOf` reads either. Each element is a `CustomElementBase` with the element's config, the fields, the history and helpers for its bindings (`value`, `text`, `ratio`, `range`, `colorOf`, `act`, `vertical`: a box taller than wide), drawn with the shell's own pieces. A binding starting `=` is a literal (`=Show answer`, `=task_alt`, `=5`: `elementValue` returns the rest as text, nothing filled or looked up). A bound Text or Text block value is plain text unless the element sets `markup` (then `pango` draws it); the widget's own `text` and `tooltip` keep Waybar's Pango handling. Their font is the element's `font`, else monospace, else the module's `module.font` (`moduleFont`, passed `CustomLayout` → `CustomElement` → the element), else the shell's.
Every element has two more slots, from the base (`CustomElementBase.yaml`'s `x-slots`, merged into each kind's list by `kinds.go`; `CustomWidgetsConfig.elementKinds` lists them after the kind's own): `show` hides the element (its `visible`, never unloaded, so a value flipping every sample rebuilds nothing) while the bound value isn't truthy (`CustomWidgetData.elementShown`), and `tone` colours it by the bound value looked up in the definition's `states` (a theme colour name passes through; a hex or an unknown word colours nothing: `elementTone`), for text kinds too (`CustomElementBase.colorOf`: a bound tone first). `resolve` hands `states` and `colorNames` on for it, and `elementValue` never reads those, `actions`, `interactive` or `failure` of `resolve` as an output key (a sample's own key of that name binds to the sample's).
- Text (fitted to its box when plain; `size: fill` grows it to the box with no cap, wrapping; rich text at a size from the box), Text block (scrolls; the tooltip by default), Icon (Material name or the format-icons glyph, a `CountBadge`).
- Ring and Gauge (`PercentageCircle`, `sweep` 360 or 240; the value inside carries the output's `unit`), Bar (a `LevelMeter`, or a `StyledSlider` with a change command, holding the released value until the next sample), Segments (`SegmentMeter`), Sparkline (`Sparkline`, between `CustomWidgetData.graphRange`'s min and max: a list the script prints, in the `value` binding or a path, is the series itself, `CustomWidgetData.series` keeping the last 240 numbers, drawn at once and after a restart; a number is graphed from the service's history, which skips list bindings. `value2` is a second series the same way, drawn as a line in `Style.series[1]` on the one range; `style` is `line` or `bars`). Value, min and max are slots (`CustomWidgetData.elementRange`: bound, or the output's own `value`/`min`/`max`).
- List (rows `{text, icon, value, subtext, id, state, max, image}` (`CustomWidgetData.rows`) in a ListModel updated in place, drawn as `CustomListRow`s (an `ItemRow` with a thumbnail from `image`, via `CustomElementBase.imageUrl`, which the Image element shares) down the element, or with `orientation: horizontal` as `CustomListTile`s (icon or image over text over subtext) of equal width, none narrower than `Widget.textPx(56)`; a row's `state` tones its icon and meter through `states`, and a numeric `value` with a `max` above 0 draws a `LevelMeter` under it; the row files sit beside `CustomList.qml`, so `CustomElement` imports that folder for qs to scan it; a click runs the named action with the row's id, else the click command with the row's text), Image (`ClippingRectangle`), Button (`StyledTextButton`; its label from the action's name when it has none), Toggle (a `StyledSwitch` beside its label or an `ActionPill`; holds its new state until the next sample), Entry (a `StyledTextEntry`: Return runs the element's named action, else its `submit` command, with the typed text as `{value}`, then clears the field unless `clear` is off; `run` refusing it (a hold, a failing script, an action the sample turned off) keeps the text and the focus, and the field stays enabled during a hold; it never takes its text from a sample, doesn't pass `module.keys` on, and is off where the host can't take keys: `CustomWidget.keysHost`, true in a popout, an overlay card and an edge menu, is passed `CustomLayout` → `CustomElement` → the element; a popout holding an Entry sets `wantsKeyboardFocus`, so it keeps the keyboard and a click outside closes it), Status (a `StatusChip` or a dot), Separator (`SeparatorMark` with the Separator bar widget's style, thickness, length and colour; its style is the shared `SeparatorStyle`).

The module library offers each definition by itself (`OverlayConfig.customModuleTypes`, group Custom, A–Z by name), keyed `CustomWidget:<id>`; `GridEditor._newModule` turns the key into `{type: "CustomWidget", properties: {definition}}` (`CustomWidgetsConfig.splitKey`), and the definition's design size is where it starts. The lock screen's library lists only definitions with `module.lockscreen`, and a module there whose definition lacks it (switched off after placing, or picked in its settings) runs nothing: its `widgetId` is empty and it says the widget isn't offered there.

### The bar widget
`qml/components/bar/widgets/CustomWidget/CustomWidget.qml` is a `BarWidget` (the built-in widgets' display styles, [Display styles](../bar/display-styles.md); `bar` extends their `BarDisplay` settings) drawing the definition's `bar.style`: `label` (icon and the format filled, as plain text: Waybar's look), `icon` (the icon alone), `ring`, `fill` (`LevelMeter`), `segments` (`SegmentMeter`), `sparkline` (a graphic in `IconTextRow`'s `lead` slot, `leadLength` long, before the icon), `pill` (the widget's background filled to the value: its `backgroundLevel`, which its background's `LevelFill` draws in the background's own shape, so it keeps the bar's caps and radius), `ticker` (the text, as long as it is up to `bar.width`, scrolling past that) and `stacked` (the text over the subtext), both after the icon where a label goes (`IconTextRow.leadAfterIcon`); a vertical bar turns the ticker along it, as its label is, and draws stacked as a label. The state colour is the base's `stateColorName` (the guard's one exception, T8: a script names it), so the bar's widget style shows it (a fill, tint, outline or the icon); the graphics draw in `colors.icon`, which reads on a filled background; `urgent` pulses it; `hidden` hides it. While the script fails (`fields.failure`) the widget shows the error text with the `error` icon in the error colour, whatever its style. Clicks and scrolls run the definition's actions; hovering opens the CustomWidget popout (`extraData: {definitionId}`) while `bar.popout` and the widget's own popout are on (`popoutOpens`); otherwise, with the definition's `tooltip` on (its switch is greyed while `bar.popout` is), it shows the output's `tooltip` field as Waybar does, rich text (Pango converted) in a `BarToolTip`.

The bar editor's library is `BarsConfig.libraryWidgetTypes`: the types without CustomWidget, then one entry per definition (`CustomWidgetsConfig.libraryEntries`, keyed `CustomWidget:<id>`), which `BarManager.addWidget` splits back into the type and its definition; a placed one's chip goes by the same key, so it's named after its definition.

### The page
The Custom widgets tool page (`qml/components/views/CustomWidgets/`, `/widgets` in the launcher) edits `CustomWidgets` through `CustomWidgetsManager.editor` (`CustomWidgetsEditor`: a `ConfigDraft`, `selectedIndex` / `selectDefinition`, `elements` (a `GridEditor` over the selected module's elements), `tab`; registered in `EditsManager`). The layer being edited is `viewIndex` (-1 the base, else a screen; `layerPath()`, `layerElements`, `element`, `selectView`, `addView`, `removeView`, `setView`): the element grid, its undo history and `setElement` work on that layer's elements (`elements.scopeKey` includes the index, so switching layer starts the history over), `_fitSize` sizes the module over every layer, and Start from the default layout is offered only on the base of a definition with no screens. Edits show live on the bars and pages through `ConfigManager.setPreview("CustomWidgets", …)`, and the selected definition stays acquired while the page is shown (`pageShown`), so its sample is there to bind from.
- **Left** (`DefinitionsPanel`): the definitions (add, duplicate, remove), the selected one's script fields (`SchemaPropertiesForm` over the definition's schema, limited with `Utils.pick`), Pick a script (`FilePickerManager`), the refresh command, and the script's first lines when the command starts with a path to a script (text starting with `#!`, read through `head` off the UI thread; a program such as `/usr/bin/sensors` shows nothing).
- **Data** (`DataTab`): the run state and Run now, the raw output with the exit code and last stderr line of a failed run, and every value in it by its path (`CustomWidgetData.flatten`, by count, the first 200), which the module's elements bind to.
- **Bar** (`BarTab`): one full-width banner holding the real bar widget on the first bar's look, across and down a side, and a caption, over the `WidgetBackground` its WidgetGroup would draw (a lone widget's caps, the pill's fill), then, in columns, the bar style, the text (format, longest text, escape, hide when empty, tooltip; the format icons and state colours typed as JSON) and the actions.
- **Module** (`ModuleTab`): a strip of layers (Base and a `ToggleChip` per screen, Add a screen) with the selected screen's form (name, show the base, when, remove); the canvas edits that layer's elements and draws the base dimmed under a screen (`GridCanvas.underlay`); previews across the top (the popout at the design size, and square, wide, large and strip, since a page can give the module any size, drawn at the zoom `CustomWidgetData.previewZoom` fits to the tab's width and height, so they never widen the editor below them) with whether the lock screen offers it; under them `ElementInspector` down the left (the element library as wrapped `ModuleChip`s, the column `min(340 px, 34 %)` wide: drag one onto the module or click it, then the selected element's bindings per slot, its look as a schema form of its kind's options, and its commands), and the layouts editor's `GridCanvas` filling the rest, in a `GridDragLayer` over `editor.elements` that is its own file's root (`ElementEditorLayout`, as `LayoutsEditorLayout` is): the same drag in, move, resize from any side, push, box-select, guides, keys and undo as a submenu's modules.

`editor.elements` is a `GridEditor` over the selected module's elements, kept from the top left as a submenu's grid is, inside 32 × 32 sub-cells (`GridEditor.area` bounds them: `module.size` is at most 8 units, so the definition can always be saved). `shiftsBack` applies only while the definition has no screens (with screens every layer is placed absolutely in the area, as they share one lattice). So the module's box is its elements' bounds (`CustomWidgetData.lattice`); `module.size` follows them rounded up to whole units (`pageSize`), the size a page starts it at, and the popout is the exact `designSize`. A `factory` makes elements instead of overlay modules (`GridEditor.factory`: `make(type, place)`, `size(type)`), and the drag layer names element kinds through `GridDragLayer.describe` sizes in grid units through `sizeLabel` and counts them as elements through `countLabel`. **Undo** covers every edit on the page, not only moves: `editor.set` and `editor.setElement` record one step per field (`def:<path>` / `el:<index>:<path>`, so typing in one field is one step) in the `elements` history, whose `snapshotExtra` takes the selected definition (its module's elements left out, since the history keeps those as modules) and `restoreExtra` puts it back in place. A definition's edits clear the history on `selectDefinition`. A definition with no elements draws `CustomWidgetData.defaultElements` (an icon, or a ring with a value, and the text left-aligned against it, as a built-in figure sits); Start from the default layout copies those into it.

### Sharing
Custom widgets never travel in a community setup or a look-only export: the `CustomWidgets` section is `x-scope: personal` (its commands `commands`), and the bar `CustomWidget` widget and the `CustomWidget` module are `personal` too (each type's `schema.yaml` `scopeIf`), so a shared look can't hold one that points at a definition it lacks, and the setups' CI refuses a file holding either. Export with personal on keeps them with the section; applying a shared file keeps the user's own. The overlay page type `Custom` is a different thing and isn't affected.

### Import and presets
- **Import from Waybar…** (the list's panel) takes a pasted `"custom/…": { … }` block, a bare `{ "exec": … }` or a whole Waybar config (`CustomWidgetData.fromWaybar`, after `stripJsonc` drops comments and trailing commas): `exec` → `command`; `interval` in seconds → poll, `"once"` → once, none → stream (Waybar reads such a script line by line); `exec-if`, `format`, `format-icons`, `max-length`, `escape`, `tooltip`, the click and scroll actions; `signal` → a `refreshName`. Each custom module becomes a definition.
- **From a preset…**: `CustomWidgetData.presets`, well-known scripts and commands (SwayNC, dunst, Waybar's mediaplayer.py, updates, wttr.in, failed services, WireGuard, NVIDIA load). Their icon maps hold Material Symbols names, drawn as icons (a pick that's a symbol name is the `icon`). Waybar's own icons are usually Nerd Font glyphs, drawn in the text font: they need a Nerd Font installed (fontconfig falls back to one), which axiom doesn't install.
- A script that refreshes Waybar by signal (`pkill -RTMIN+N waybar`) gets a note on the page naming the `axiom ipc customWidgets refresh` call to use instead.

### CommandOutput, folded in
The CommandOutput module is gone: migration v81 (`backend/internal/migrate/steps/v81.go`) turns each one, in any module grid, into a definition (its command polled as plain text every `interval`, escaped so it shows as typed, its click command the click action, `hideEmpty` off) drawn by one Text block filling a module of the place's size (monospace when it was), and the module into a `CustomWidget` showing it. A format-1 config converts to CommandOutput first (`migrate/convert`), then v81 runs on it like any other.
