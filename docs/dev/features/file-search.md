# File search

> **Files:** `backend/internal/filesearch/`, `backend/internal/fileindex/`, `backend/internal/procprio/procprio.go`, `backend/internal/thumbnail/`, `backend/internal/mimeapps/globs.go`, `backend/internal/daemon/filesearch.go`, `backend/internal/cli/filesearch.go`, `qml/services/apps/FileSearchManager.qml`, `qml/services/ui/LauncherFiles.qml`, `qml/components/methods/FilePaths.qml`, `qml/components/surfaces/launcher/LauncherRow.qml`
> **Config:** `Launcher.providers.files.*` (reader `LauncherConfig`: `files`, `fileShowHidden`, `filesInSearch`, `fileThumbnails`)
> **Related:** [Launcher](launcher.md), [Launcher providers](launcher-providers.md), [Default apps](default-apps.md), [protocol](../backend/protocol.md)

The launcher's files: `~` (or `/files`) searches them, `~/` browses folders, `~` alone lists the recent files, and the main search shows the best few below the apps. The axiom daemon keeps its own index of the folders searched, current through inotify, so a search is a scan of memory, not of the disk. One rule shapes all of it: **building and keeping the index never slows anything down**.

### What the user gets
- `~report` searches every folder searched; `~/Documents/` lists a folder from the disk; `~/Documents/rep` searches below it; `~` alone, the recent files (`recently-used.xbel` and what the launcher opened).
- **Matching:** smart case (an upper-case letter anywhere makes the whole query case-sensitive), every space-separated token must match (the first 8: each costs a search two tables the index's size), and fzf's folder segments (`doc/rep` is `rep` in a folder matching `doc`, `doc/` anything below one). Hidden entries are found only with `showHidden` on (the index holds none otherwise); a listed folder shows them for a query starting with `.`.
- **Enter** opens the file with its default app (`DefaultAppsManager.open`, [Default apps](default-apps.md)), **Shift+Enter** shows it selected in its folder, **Ctrl+C** (nothing selected in the field) copies its path, **Tab** types its path (a folder's lists it).
- Pictures show their thumbnails (`Launcher.providers.files.thumbnails`), shared with the file manager's.
- **Settings** (`Launcher.providers.files`): `enabled` (on), `inSearch` (files in the main search, 0–5, 3), `thumbnails` (on), `showHidden` (off), `roots` (`["~"]`, `x-scope: machine`), `excludes` (names or path tails, `*` globs: `.git`, `node_modules`, `.cache`, `target`, `go/pkg`, `.local/share/Trash`, `*.pyc`, …). The daemon reads `enabled`, `roots`, `excludes` and `showHidden` itself (`fileSearchSettings`, a `~` in a root is `$HOME`); the shell reads `enabled`, `inSearch`, `thumbnails` and `showHidden` (for browsing).

### No slowdown: where the work runs
- **The crawl runs in a child process, never in the daemon:** `axiom index-crawl` (hidden; `fileindex.RunChild`, `/proc/self/exe`, the request as JSON on stdin, never in argv). Before it reads anything it lowers every thread in `/proc/self/task` (`procprio.Idle`) to `SCHED_IDLE` (CPU only when nothing else wants it) and the idle I/O class (`ioprio_set`: the disk only when it's idle); threads made later inherit both. Failing to lower itself fails the crawl: it never runs at normal priority. It runs with `GOMAXPROCS=1`, `GOGC=20`, an empty environment and its own process group (killed whole on disable or shutdown).
  - Why a process and not an idle thread: the daemon's garbage collector stops every thread, so an idle-priority thread starved by a busy CPU would hold every shell RPC through the collection. A child has its own runtime.
- **It walks breadth first** and streams one folder per binary frame on stdout (`fileindex/wire.go`: a length, a kind, the folder's path, time and entries; the daemon reads names straight from the frame, allocating nothing per entry), plus a progress frame (`msgProgress`) at most every second, sent by the walking goroutine itself between folders, so a walker blocked in a read sends none. It sleeps 10 ms every 128 folders (`Options.Pause`), never follows a link (but a root), never crosses onto another device, always skips `/proc`, `/sys`, `/dev`, `/run`, `$XDG_RUNTIME_DIR` and `~/.cache/thumbnails` (a mount point of another device is left out by its path in the mount table, `/proc/self/mountinfo`, never stat-ed: stat-ing one whose server is gone blocks; `filter.setMounts`), and stops at `MaxEntries` (500k, at most 2M; `truncated` in the state).
- **Two lanes** (`fileindex/lanes.go`): the roots not on a network filesystem share one child, as when there are none; each network root (`filter.netRoots`) gets a child of its own, one at a time, in a second lane. Crawls, stat passes and refills are queued by root into their lane (`loop.work`, `loop.net`; moved over when a share is mounted over a root or goes, `sortLanes`), and each lane starts its next job on its own (`loop.next`), so a network root whose server is gone stalls only itself. The crawl phase ends once no lane crawls the first build (an unreachable root's crawl doesn't hold it, `loop.built`); the cache is saved only while neither lane runs a child.
  - **Stuck, not starved:** a child at `SCHED_IDLE` on a busy CPU can make no progress for minutes, so silence alone never kills. A network root's child is stuck when it sent no frame for 60 s (`Options.StuckAfter`) **and** none of its threads is runnable (`R` in `/proc/<pid>/task/*/stat`) **and** none woke since the last check (their context switches, `/proc/<pid>/task/*/status`, unchanged), in either kind of sleep: FUSE (sshfs) waits for its server interruptibly (`S`), NFS and SMB uninterruptibly (`D`); one reading a large folder from a slow server wakes on each reply (`checkStuck`, `Options.Threads`; checked every quarter of that while it runs). Its process group is killed and it's reaped by goroutines nothing waits on (a process blocked on a dead NFS server may outlive SIGKILL; a reset and the daemon's shutdown don't wait for it), and its root starts no other child until it's reaped (`loop.reaping`). The root is marked unreachable (`unreachable` in the state) and asked a stat pass of every folder (which also reads what its crawl never reached), tried after a backoff of 1 minute (`Options.RetryAfter`), doubling up to an hour (one due while another root's child runs waits for its end); a pass that ends clears it. Its entries stay in the index meanwhile.
- **The daemon only applies frames**, at normal priority, taking the write lock for one folder at a time (microseconds), so searches (read lock) never wait. The idle child holds nothing the daemon needs: no priority inversion.
- **Watching:** raw inotify through `golang.org/x/sys` (`fileindex/watch.go`; fsnotify exports neither flag), each folder watched with `IN_DONT_FOLLOW | IN_ONLYDIR` (and `IN_EXCL_UNLINK`; a root that is a link without `IN_DONT_FOLLOW`, as the crawl follows it; such a watch sits on the folder the link led to, so each housekeeping tick stats the link, and one leading elsewhere or nowhere empties the root and watches it where it leads, which reads and crawls it again). A root's read takes the root's device anew, so a disk mounted again at a root with another device number is read, not emptied; a folder below it read first finds the device kept stale and takes it anew too (`filter.rootOn`). A root on a network filesystem (NFS, SMB, any FUSE but a disk's `fuseblk`; a root reached through a link to one, itself or a folder above it, followed by readlink alone) is never watched nor read by the daemon itself, since every look at it blocks while its server is gone: the stat pass, in the idle child, keeps it current (`filter.onNetwork`; the mount table is read again before the loop reads or watches folders and each housekeeping tick, `loop.refreshMounts`, and a root newly on the network, such as a share mounted over it, has its watches dropped and a stat pass asked). The **watch budget** is a quarter of `/proc/sys/fs/inotify/max_user_watches`, at most 64k, since that limit is shared with editors, syncthing and the rest. A watched folder's events are debounced 50 ms (500 ms at most for events that never stop) and the folder is read again in the daemon (one folder: small). A lost queue (`IN_Q_OVERFLOW`) checks every folder (a stat pass over the watched ones too; one of its reads landing after a newer read the watch made is read again, `loop.recheck`).
- **The stat pass** checks the folders past the budget: a folder's mtime changes when an entry in it is added, removed or renamed. It runs in the same child (`CrawlRequest.Stat`: the folders and their times on stdin; paced too, every 1024 folders checked), every 10 minutes and on a search after a quiet minute; folders it finds new are crawled next. The cap is the crawl's alone: a pass reads every changed folder however full the index is (the index adds none past `MaxEntries`). A folder whose read left entries out at the cap is marked (`Index.LeftOutDir`, kept in the cache) with the time it was read, so a still-full index's passes don't read it again; once removals leave room of more than a hundredth of the cap (files deleted one at a time from a full index don't each re-read them all; a pass that didn't finish is asked again while marks remain), a pass of the marked folders (asked with time 0, so each is read) and those never read follows (`loop.refillPass`; once the index is full again the pass's other folders are passed over, still left out; a marked folder the child can't read is unmarked, `Index.ClearLeftOut`), what they add is crawled, and `truncated` is set again only by what's still left out.
- **The cache** (`$XDG_CACHE_HOME/axiom/fileindex.bin`, 0600, its folder made 0700 when it's new; `filesearch/snapshot.go`): magic, version, the settings' key (roots, excludes, hidden, the cap), the entries breadth first (a folder left out at the cap keeps its mark: `truncated` at load), and a CRC32. Only a change of its entries (one added, removed or renamed) makes it due, not a file's or folder's time: a loaded cache's stat pass reads a folder whose time differs again anyway. A due cache is written at most every 30 minutes (`Options.SaveEvery`; a new index's first at once) and when the daemon stops, never while the child crawls or runs a stat pass (`loop.save`). It's streamed to a temp file through a 64 KiB buffer (nothing its size in the daemon's heap) under the index's read lock, so searches go on, and renamed over the old one, never fsynced (`fsx.WriteCache`): a torn one fails its CRC. The loop is busy for it: about 30 ms at a million entries (`BenchmarkEncode1M`, ~27 MB), so a watch's changes wait that long at most every 30 minutes. A bad or foreign cache is removed and the index built again. It loads 20 s after the daemon starts (or at the first search, if sooner), so nothing competes with the session's start, then a stat pass over every folder catches what changed while nothing watched; its folders are watched only after that pass (`loop.watchAll`), since adding a watch looks the path up, which on a cold cache reads the disk at the daemon's priority, and the idle child's pass has read them by then. Turning file search off drops the index and deletes the cache; other roots or excludes drop it and wait for the next search.
- **Lazily started:** with no cache, the first search starts the crawl (`phase` `waiting` → `crawling` → `ready`); results grow as it goes.
- **Newest wins, without a cancel:** each `filesearch.query` carries an id that rises per connection; the daemon keeps the connection's newest (`queryKey`, gone with the connection), an older query answers `stale` with no items, and a scan replaced mid-way stops within 16k entries (`staleEvery`).
- **Thumbnails are made in a child too:** `axiom thumbnail` (`thumbnail.RunChild`) at nice 10 and the lowest best-effort I/O level (`procprio.Background`), with a 512 MiB Go memory limit, since a 50 MP image decodes into ~200 MB that must not land in the daemon's heap. At most 2 run at once (`maxRunning`), one per file however often it's asked, 30 s each.
- **The shell's side:** nothing is polled (the state is pushed); a keystroke sends one RPC (a search, a listing or the recent files) and nothing else; thumbnails are asked only for rows the list has built, at most 4 at once; answers to anything older than the newest asked are dropped by id.

### The index (`filesearch`, pure)
- **No pointers:** one byte arena of names and fixed 32-byte entries (name offset and length, parent index, mtime, flags, a character-class mask), plus a folder map by path. A million Go strings would make every collection scan a million pointers; this costs the collector nothing (about 22 MB at 500k files). Removals are tombstoned and compacted once they pass a quarter (built without the lock, swapped under it).
- **Matching** (`match.go`): the mask prefilter skips most entries cheaply; `Score` scores as `Search.score` does (100 exact, 80 prefix, 65 word start, 50 inside, 5–30 letters in order), so a match reads the same in files as in apps. Files are never ranked against apps (the main search lists them below), so the two needn't stay equal and nothing is shared between them.
- **Ranking** (`rank.go`): the match (a folder's counting 0.6), less 1 per level below the root (at most 10), plus recency (10 within a day, 6 a week, 3 a month) and the use bonus (as `Search.useBonus` weighs an app's, over the launcher's files history), less 5 for a hidden entry. The scan is split over `GOMAXPROCS` shards, each keeping its top K; only the top results cross the socket. The use bonus by entry is resolved at most every 2 s.
- **Recent files** (`fileindex/recent.go`): `recently-used.xbel` (only read, never written) merged with the launcher's own history (`$XDG_STATE_HOME/axiom/launcher-files.json`, 0600, written by `filesearch.used`).
- **Results' types** (`fileindex/meta.go`): shared-mime-info's globs through `mimeapps.Globs` (a plain `*.ext` map, the slow patterns apart, loaded once), its icons most specific first. An item is described from the disk (`Lstat`), but one under a network root from the index alone (`meta.fromIndex`: its kind and time, no size; a recent file the index doesn't hold is left out), since every look at a dead server's files blocks.

### RPC (every method the shell's alone)
- `filesearch.get {}` → the state `{ phase: off|waiting|loading|crawling|ready, entries, watched, unwatched, unreadable, truncated, unreachable, error }` (`unreachable`: how many network roots got their child stuck, tried again later; `error`: why the build failed, else ""; a later crawl's or stat pass's failure is only logged); pushed as `filesearch.state` (latest-wins, at most every 500 ms while it changes; the `fileSearch` hello topic).
- `filesearch.query { id, query, dir, limit }` (hidden entries by `showHidden`) → `{ id, items, stale, indexed }`; `indexed` is false while there's no index yet or for a `dir` it doesn't hold. limit 50 by default, 200 at most.
- `filesearch.browse { path, query, limit, hidden }` → `{ path, items, total }`, read from the disk (works while the index builds, and outside the roots), folders first, or best matching `query`; limit 200 by default, 1000 at most. A folder of a network root is listed within 3 s (`Options.BrowseDeadline`), else it answers as an unreadable folder does (`failed`); the listing left blocked keeps its goroutine, and while it does the root's other listings answer so at once (one in flight per root, `browseNet`).
- `filesearch.recent { limit }` → `{ items }`; `filesearch.used { path }` records an open.
- `filesearch.thumbnail { path, size: normal|large }` → `{ path, failed }`.
- `filesearch.reveal { path }` → `{ via: showItems|folder }`: `org.freedesktop.FileManager1.ShowItems` on the session bus (Nautilus, Dolphin, Thunar, Nemo select the file), else its folder opens through `openTarget` (shared with `apps.open`).
- An item is `{ path, name, dir, mime, icons, size, mtime (ms) }`; `dir` is a folder or a link to one.

### Thumbnails (`thumbnail`)
- The freedesktop spec: `$XDG_CACHE_HOME/thumbnails/{normal,large}/<md5 of the file URI>.png` (128 or 256 px), valid while its `Thumb::URI` and `Thumb::MTime` match the file, so a file manager's (videos, PDFs) are reused and axiom's are shared back. axiom makes them only for png, jpeg, gif, webp and bmp (`golang.org/x/image` for the last two), refusing over 50 MP or 64 MiB; an SVG under 1 MiB is its own thumbnail. A file it can't decode is recorded under `fail/axiom-1/` and not tried again until the file changes; any other failure (a timeout, a write) answers `failed`, which the shell keeps as no thumbnail. Files are written atomically and never fsynced (`fsx.WriteCache`: a cache), 0600 (folders made 0700 when new). The URI is escaped as `g_filename_to_uri` escapes it (`filesearch.FileURI`; `;` too), so the md5 names match a file manager's.

### The shell
- **FileSearchManager** ([Launcher providers](launcher-providers.md) › FileSearchManager): the calls, the state, icons and the thumbnail queue.
- **`FilePaths`** (pure, `tests/tst_FilePaths.qml`): `parse(text, home)` turns the text into `{ kind: recent|browse|search, dir, query }` (`~/a/` lists `a`, `~/a/rep` searches below it, `~/a` searches `a` below home, `..` resolved), `completion(path, home, isDir)` the text Tab types (through `..` outside home), `join`, `parentOf`, `thumbnailable(mime)` (images, videos, PDFs).
- **`LauncherFiles`** (LauncherManager's part): `rowsFor(text)` for `~` mode and `mainRows(q)` (from two characters, `inSearch` of them; none at 0) return the newest answer's rows and ask once per new text; `updated` tells LauncherManager, which sets the rows without searching again. Until an answer lands the previous text's rows stay, so the list doesn't flicker. A search below a folder goes to the index once it's `ready`; otherwise (or when it answers `indexed: false`, a folder it doesn't hold) the folder's own entries are listed instead. A folder that can't be listed shows a row by the error's kind (no such folder, or can't be read). While the index builds, a last row says "Indexing… {0} files", and a shown search asks again on each state push until an answer from the built index lands; a file the selection was moved to stays selected as the answers re-rank it (its path is the row's `key`), while an untouched selection stays on the top row, the best match. Closing the launcher makes the next read ask again (`LauncherManager.shown`; `~` mode's last rows show until its answer lands, as it often opens on the same text; the main search's are dropped, being another text's), and an answer that lands after the index's phase changed asks again too (the push can come first).
- **Rows:** `{ kind: file|folder, image (the type's icon), glyph, thumb, mtime, title, subtitle (the folder, size and date), hint, complete, run(shift), copy() }`; `LauncherRow` shows the thumbnail cropped once it lands ([Launcher](launcher.md) › Row shape).

### Security and privacy
- Links are never followed out of the roots; the crawl stays on each root's device. Unreadable folders are skipped and counted (`unreadable`).
- The index, the cache and the history stay out of config.json; the cache and the history are 0600 (their folders made 0700 when new). Logs carry counts, never file names. The crawl's and the thumbnail's requests go on stdin.
