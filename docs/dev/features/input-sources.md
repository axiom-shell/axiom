# Input sources

> **Files:** `qml/services/system/InputSourceManager.qml`, `qml/components/methods/InputSources.qml`, `qml/config/InputConfig.qml`, `qml/components/views/Settings/InputSourcesField.qml`, `qml/components/views/Settings/InputMethodSetup.qml`, `qml/components/bar/widgets/KeyboardLayout/KeyboardLayout.qml`, `qml/components/content/InputSources/InputSources.qml`, `qml/components/content/KeyboardLayout/KeyboardLayout.qml`, `qml/components/surfaces/osd/OSDStatusSource.qml`, `qml/components/methods/OSDItems.qml`, `qml/components/reusable/PasswordEntry.qml`, `qml/services/session/GreetdManager.qml`, `qml/services/compositor/CompositorManager.qml`, `qml/services/core/WaylandManager.qml`, `backend/internal/compositor/actions/table.json`
> **Config:** `Input.keyboard.sources` (`InputConfig.sources`, `savedSources`), `Input.keyboard.method` (`InputConfig.methodEnabled`, `savedMethodEnabled`, `savedFramework`, `savedMethodOptions`; `autostart` and `legacyApps` are the daemon's managed-mode writer's); the KeyboardLayout widget's `format`, `showIcon`, `hideSingle`, `popout`; the OSD's `keyboardLayout` status
> **Related:** [Input methods (daemon)](../backend/inputmethod.md), [OSD](osd.md), [Lock screen](lockscreen.md), [Greeter runtime](greeter-runtime.md), [Compositor contract](../compositor/contract.md), [Keybinds](../hyprland/keybinds.md)

One list, **input sources**, holds both the keyboard layouts and the input method engines (fcitx5's mozc, pinyin, hangul; ibus's engines). The engines count only while axiom manages the input method (`Input.keyboard.method.enabled`, off by default): off, the sources are keyboard layouts alone, as before input methods were added, and a running fcitx5 or ibus is left alone. axiom owns the list: the bar, its popout, the OSD, the module (overlay, edge menus, lock screen, login screen), keybinds, IPC and settings all read it through `InputSourceManager`, so no surface can disagree with another.

### The model
- `Input.keyboard.sources` is `[{ id, kind: "xkb" | "ime", layout, variant, engine }]`. An xkb source is a layout; an ime source an engine typing on the layout it names (empty: the first xkb source's).
- `methods/InputSources` derives every consumer's shape from it: the compositor's xkb list (`xkb`: the distinct layouts in order, so the lock screen, the greeter and password fields have the same layouts; an engine's typing layout joins it only while `Input.keyboard.method.enabled` is on, the `engines` argument, the renderer's from the saved switch), fcitx5's group (`fcitx5Group`: `keyboard-<layout>[-<variant>]` and the engines), ibus's engines (`ibusEngines`: `xkb:<layout>:<variant>:<lang>`), what a source switches to (`target`: an xkb index and an input method), which one is current (`current`: the framework's input method, an xkb one only while the compositor is on its layout, so a layout the compositor switched itself (a `grp:` option, its own bind) shows over fcitx5's still-current `keyboard-us`; else the compositor's index), the label (`label`), the next one (`step`), whether the framework's list is the sources' (`groupMatches`) and the framework's list back as sources (`fromGroup`).
- **While axiom doesn't set the keyboard** (`Input.keyboard.enabled` off) the compositor's layouts are its own config's: `InputSources.effective` then makes an xkb source of each layout the compositor has (`xkb:<index>:<code>`), followed by the ime sources (an engine whose typing layout the compositor lacks types on the first), so the widget still shows and switches what the compositor has. It compares against what axiom writes (`xkb(sources, engines)`, engines being `Input.keyboard.method.enabled`) from every source, so `InputSourceManager` keeps that list (`_counted`) and leaves out the engines it can't switch to (none running, not installed) only after, reading xkb indices against `_counted`.

### Who owns what
- **`InputSourceManager`** (`qml/services/system/`): the compositor's xkb state (`CompositorManager.withKeyboard`, read again on `keyboardLayoutChanged` and `configReloaded`, never polled; the xkb registry from the daemon's `input.layouts`), the daemon's `inputMethod` topic (listened to, `inputMethod.get` on every hello; `acquire(owner)` / `release(owner)` by the surfaces showing the source in use (not the lock screen's module: it shows the compositor's layout), which hold the `inputMethodPoll` topic while a framework runs, so a switch made in fcitx5 is heard without a tray: [daemon](../backend/inputmethod.md) › fcitx5), `sources`, `xkbSources`, `current` / `currentXkb`, `labelFor` / `nameFor` / `iconFor`, `next` / `prev` / `set`.
- **Switching** (`set(id)`, `next` / `prev`): the compositor's layout first (`CompositorManager.setKeyboardLayout(index)`, a contract member), then the framework's input method (`inputMethod.set`). A source the framework switched to itself (its hotkey, its tray menu) moves the compositor's layout to the one it types on (`_followIm`), so a password field, where no input method types, types on it too.
- **Current:** the framework's current input method when one runs and names a source, else the compositor's index. fcitx5's current is `""` until a text field had focus: the index then.
- **Managing it** (`Input.keyboard.method.enabled`; `enabled` as shown, `InputConfig.savedMethodEnabled` as saved): off, or on while no framework runs (an engine can't be switched to then), `sources` is the xkb sources alone (so the widget, popout, OSD, keybinds and IPC never offer an engine), and on with one running it leaves out an engine the framework hasn't installed (switching to it fails, so stepping would stop there; the card marks it); off, `running` / `framework` / `available` read as no framework, and nothing is sent to the daemon (no `inputMethod.framework`, `push` or `options`). `detected` / `detectedFramework` still say whether one runs (the daemon follows `auto` until told otherwise), for the card's offer. Pushes follow the saved switch, never an editor's preview: turning it on (saved) sends the framework's choice, then the list and options.
- **The framework's choice:** `Input.keyboard.method.framework` (`fcitx5` by default, `ibus`, `auto`: whichever runs, `none`) goes to the daemon as `inputMethod.framework` on every hello and saved change. Until the daemon's state names the chosen one (`auto` takes any), no list or options are pushed, so a list is never built for the framework it followed before. fcitx5 is the recommended one; ibus is supported for listing and switching engines.
- **Giving the framework the list** (`inputMethod.push`): while managing is on (saved). Before it's saved on, the settings card asks which list wins when the running framework's (a user's mozc set up in fcitx5-configtool) isn't the sources (`matches(sources)`): `importFromFramework()` puts the framework's list in the draft, "Use axiom's" keeps the sources; Save then gives the framework the draft's. A framework appearing with another list is given the sources, unless it was changed outside axiom since axiom pushed (`outsideEdit`), which waits for the card's choice (`importFromFramework()`, or `useOwn()`: push again over it); a saved edit of the sources pushes over it. ibus waits for the registry (its xkb names carry the language). The same list is never pushed twice in a row to one framework, so one that keeps a list its own way isn't pushed in a loop. Only installed engines are pushed (`InputSources.installed`, against the state's `available`; `fcitx5Group` / `ibusEngines` take it, and `groupMatches` compares with the same): one the framework lacks would be dropped from its list and read back unlike the push, a lasting `outsideEdit`. It stays in the config and in the card, marked not installed.
- **Options** (`inputMethod.options`: `shareState`, `verticalCandidates`, `candidateFont`, `showSwitchPopup`): sent when a framework appears and when they change. `showSwitchPopup` is off by default: axiom's OSD shows the switch. ibus takes only the font.
- Pushes use the saved config (`InputConfig.savedSources`, `savedMethodEnabled`, `savedFramework`, `savedMethodOptions`), never an editor's preview: the options rewrite the framework's own config.

### Settings
- **One Keyboard card** (the Input section is in Settings' General category; `Input.keyboard`, its `x-group: Keyboard`), top to bottom: "Set the keyboard" (`enabled`, which gives the compositor the layouts too, so it comes first), the layouts, the input method switch as their last row, the Input method options fold, then typing (XKB options, key repeat, Num Lock). Mouse, touchpad and cursor keep their own cards. Without `supports.inputConfig` only the layouts show (each other field's own `x-showIf`), as the widget still switches what the compositor has.
- **The layouts** (`InputSourcesField`, `Input.keyboard.sources`' `x-row`, a row of the card; links to it name the setting or the section, `Input`): the sources as edited (the settings draft, so the bar and OSD preview them), each moved, removed, an engine's typing layout picked (the first xkb source's, or one of theirs). Layouts are added from the xkb registry (`InputSources.searchLayouts`: layout and variant, by name or code), engines from the framework's `available` (fcitx5's `keyboard-*` and ibus's `xkb:*` left out); new ids from `InputSources.freeId`. Off, it lists the xkb sources alone (the engine ones stay in the config, in their places) and, while fcitx5 or ibus runs, offers "let axiom manage it?" above the switch (turns the switch on in the draft, and makes the running framework the chosen one unless `auto` or it already is; it never turns itself on).
- **The input method switch** ("Type other languages with an input method", `Input.keyboard.method.enabled`: the layouts' `x-rowDraws`, so its own row hides but search, the changed list, the card's Discard and `/config` still take it; drawn by `InputSourcesField` as a `SettingsField` of its own, with its unsaved dot and reset; shown only with `supports.inputMethod`). On, under it: a status line saying the chosen framework runs, or that it isn't running or installed (`DependencyManager`), the which-list choice when it applies, and outside managed mode `InputMethodSetup`: the variables and autostart command to add by hand, each with Copy, plus the legacy variables and Electron's `--enable-wayland-ime` (no variable turns it on). Its values are `InputSources.methodSetup(framework, legacyApps)`, the managed writer's (`render.InputMethodEnv` / `InputMethodCommand`) replayed through the shared fixtures, so the two copies can't drift; `auto` shows the running framework's, else the installed one's. Until Save the daemon follows whichever runs, so the card offers a framework's engines and list only while it's the chosen one (`chosenRuns`).
- **Input method options** (`Input.keyboard.method`'s other fields, `x-fold`: shut until opened, shown only while the switch is on and with `supports.inputMethod`): the framework, autostart and older apps (managed mode), sharing between windows, candidates in a column, the candidate font, fcitx5's switch popup.
- **The onboarder's Compositor page** shows `InputSourcesField` with `layoutsOnly`, in a `FieldGroup` of its own: always the off form, without the switch or the offer, each edit saved at once (`SettingsManager.commitValues`, as its other rows).
- **Managed mode** writes the variables and autostart only while `enabled` is on (and the framework is installed: `manager.inputMethodOf`); the goldens' `managed.*` have it on, `managed-no-im.*` off.

### Surfaces
- **Bar widget `KeyboardLayout`:** the current source's label (`format`: `short`, an xkb code in capitals; `full`, the layout's name; an engine always its own label, あ, from the framework's `available`), its kind's icon (`showIcon`: `keyboard` or `translate`), hidden with one source (`hideSingle`). Left click next, right click previous, the wheel steps (whole notches). Its popout `content/InputSources` lists the sources, the current one marked; a click picks one, the header's button opens the Input settings.
- **Module `KeyboardLayout`** (overlay, edge menus, desktop, lock screen, login screen; in the lock screen's library, not its default layout): the current source by name (`nameFor`: a layout's, an engine's display name); click, right click and the wheel switch. On the lock screen and the login screen it offers the compositor's layouts alone (`sourcesFor(true)`: `xkbSources`, `InputSources.compositorLayouts`, the layouts of `xkb(_counted, engines)` in the compositor's order, each its xkb source or one made for it, `xkb:<index>:<layout>`, so an engine's own typing layout, Mozc's `jp`, is among them while the method is on; `currentXkb`, the one on the compositor's index), by the layout's name: a password field types through the compositor's layout only, so offering mozc there would be a lie, and locked while on mozc's `jp` it shows Japanese, what the password types on. `set` takes those ids too (the layout alone). The layouts editor's preview shows a stand-in.
- **OSD `keyboardLayout`** status: `{ ids, current, label }` (`OSDStatusSource._sourcesState`, `OSDItems.tile`, `layoutSwitched`): an input method's switch shows it as a layout's does, but not one following a window focus change (fcitx5's per-window input method; see [OSD](osd.md)).
- **Keybinds and hot corners:** `inputSourceNext` / `inputSourcePrev` (Next / Previous input source, System; they work while locked, stepping through the compositor's layouts alone then, as the lock screen's module does), calling the IPC target. Bound by default to SUPER + CTRL + space and SUPER + CTRL + SHIFT + space (v95 adds them to older configs where the key, id and action are free): fcitx5's own hotkey (Ctrl+Space) reaches it only while a text field has focus, as an input method sees keys only then, while a compositor bind works everywhere.
- **IPC** `inputSources`: `next`, `prev`, `set <id>`, `list` (JSON `[{ id, kind, label, name, current }]`).
- **Login screen:** no framework runs there (`Paths.greeter`): the manager serves the compositor's layouts alone, pushes nothing and follows `keyboardLayoutChanged` like the session (the greeter had a copy of the layout state of its own, which went stale; it's gone).
- **Password fields** (`PasswordEntry`) set `inputMethodHints` to `ImhSensitiveData | ImhNoPredictiveText | ImhHiddenText`, so no input method sees or predicts a password, whatever the echo mode.

### Why the candidate window is themed, not replaced
The candidate (kanji) window stays the input method's. It must sit at the text cursor, and only input-method-v2's popup surface gives that position on all three compositors; drawing it from axiom (kimpanel) would put a layer-shell window at a guessed spot, take over every engine's UI and break per-engine features. So axiom replaces what it can draw well (the indicator, the switch popup, the picker, settings) and themes the rest: the fcitx5 theme integration's candidate window and menus, and the gtk integration's rules for ibus's panel ([Theme integrations](../theming/theme-integrations.md)).

### The capability
`supports.inputMethod`: the compositor offers `zwp_input_method_manager_v2` (`WaylandManager.inputMethod`, from the daemon's `wayland.state`), merged into `CompositorManager.supports` with or without a backend. False until the daemon has said (`WaylandManager.known`), so the input method settings appear once known rather than show and vanish. The input method switch and options (`Input.keyboard.method`'s `x-showIf: {/$supports.inputMethod: true, …}`) and the engine half of the layouts (`InputSourcesField.supported`: no engines listed, no "let axiom manage it?") show only with it; the layouts show without `supports.inputConfig`; the keyboard's other fields and the mouse, touchpad and cursor cards need that.

### Testing
`tests/tst_InputSources.qml` and `tests/tst_OSDItems.qml`. Never push a list or options to the live fcitx5 or ibus (it rewrites the user's profile): a nested shell (`scripts/dev/nested.sh`) runs on its own D-Bus session, where the live fcitx5 isn't.
