# Lock keys

> **Files:** `backend/internal/lockkeys/lockkeys.go`, `backend/internal/daemon/topics.go`, `backend/internal/daemon/greeter.go`, `qml/services/system/LockKeysManager.qml`, `qml/components/reusable/CapsLockHint.qml`, `qml/components/reusable/StyledTextEntry.qml`, `qml/components/reusable/PasswordEntry.qml`, `qml/components/bar/widgets/LockKeys/LockKeys.qml`, `qml/components/surfaces/osd/systems/LockKeys/`
> **Config:** none of its own; the LockKeys widget's settings (`showCaps`, `showNum`, `showScroll`, `hideWhenOff`, its colors)
> **Related:** [Services pattern](../core/services-pattern.md) (polled topics), [Protocol](../backend/protocol.md), [Shared UI pieces](../core/shared-ui-pieces.md) (`StyledTextEntry`, `PasswordEntry`), [Greeter runtime](greeter-runtime.md)

Whether Caps Lock, Num Lock and Scroll Lock are on: every password field warns about Caps Lock by itself, the LockKeys bar widget shows the keys that are on, and the OSD shows a key toggling.

### Source
- **The keyboards' LEDs** (`/sys/class/leds/<device>::capslock`, `::numlock`, `::scrolllock`, their `brightness`). Hyprland, sway and niri each keep the LEDs in step with xkb's locked modifiers, and every user may read them (the greeter's user too). No compositor reports the locked modifiers on all three otherwise: sway's `get_inputs` and niri's IPC don't, Hyprland's `devices` does only when polled, and Qt doesn't hand them to QML.
- **Polled**: LED files can't be watched (no inotify, no uevent on a change). The `lockKeys` topic (`lockkeys.Source`) reads them every 150 ms (floor 100 ms) only while someone subscribes, and pushes `lockKeys.state` only when it changed: `{available, caps, num, scroll}`.
- A key is on while **any** keyboard's LED is (a keyboard plugged in after the toggle may briefly disagree, by when its compositor sets its LED). `available` is whether a Caps Lock LED exists at all: none in a VM or a remote session, and then nothing shows rather than claiming the key is off.
- Caps Lock remapped away (`caps:escape`, `ctrl:nocaps` in `Input.keyboard.options`) sets no lock, so its LED stays off and nothing shows: correct.
- Registered on the session's axiom (`sources()`) and the greeter's (`greeterRegistry`).

### Shell
- `LockKeysManager` (`qml/services/system`): `available`, `capsLock`, `numLock`, `scrollLock`; consumers `acquire(owner)` / `release(owner)` with no request (they share the default interval). With no consumer it releases the topic and reads all off and unavailable, so a state from the last consumer never shows stale.
- **Password fields**: `StyledTextEntry` loads `CapsLockHint` at its right (left of the clear X when both show) while its `echoMode` hides text, it has focus and isn't read-only, so the key is polled only while a password is being typed. The hint is an `IssueIcon` (`keyboard_capslock`, warning, "Caps Lock is on" on hover) that pops in; the text makes room only while it shows. A revealed field (`echoMode` Normal) shows no hint: what's typed is visible. Every password field gets it with no setting: the lock screen, greeter and polkit (through `PasswordEntry`), Wi-Fi, VPN secrets, the CalDAV password and the chat API keys.
- `CapsLockHint` is plumbing, the one reusable piece reading `LockKeysManager`; hosts read `StyledTextEntry.capsHintShown`.
- **`PasswordEntry`** (lock screen, greeter, polkit, where a wrong password costs most): while its message is empty, its message line says "Caps Lock is on" in `Theme.warning` (under `inlineMessage`, the empty field's placeholder). A real message (a failure, a PAM prompt) always wins. `capsMessage` turns the line's warning off: the lock screen's and greeter's fields tie it to their Messages setting, since with no line reserved it would push the field (the icon still shows).
- **The LockKeys bar widget**: a glyph per shown key in its `lead` slot (a Repeater over the keys its settings show, never over live state). With Hide when off, only the keys that are on show and the widget hides while none is; without it, every shown key always shows, one that's off dimmed in the inactive color's icon color (`_offColor`), so a key turning on never tints the ones still off. The active color while any is on, else the inactive one; always hidden while `available` is false. Hovering it lists each shown key, on or off: the host's hit area lies over the module and takes the hover, so it reads `hitArea.hovered` (a `HoverHandler` of its own only without one) and shows a `BarToolTip` on the bar's inner side. It holds the topic as long as it exists, so the LEDs are polled the whole session (a few tiny reads every 150 ms, nothing pushed without a change). No clicks: toggling a lock key would need a virtual keyboard. With Boxes: One per item each shown key is a box of its own, its icon and short name (Caps, Num, Scroll) in its own on or off color ([widget style](../bar/widget-style.md#boxes-one-per-item)).
- **The OSD**: an OSD's `capsLock`, `numLock` and `scrollLock` status icons show the key's state, and open the OSD when it toggles ([OSD](osd.md) › Systems › LockKeys). LockKeys' watcher holds the topic while an OSD lists the system (the whole session), as the widget does.
