The user's window rules: the model, its validation, the renderers that compile it, the writers that put the rules in each compositor's config, and the Window rules page that edits them.

### The model
- `WindowRules.rules` is an id'd list whose order is the priority: the higher a rule, the more it counts when two set the same thing. `Parse` turns the section into `Config`.
- A rule's `windows` are kinds of window (any kind matches); a kind's conditions are `{field, op, value}` and every one must hold.
- `window` is what the compositor's config does when the window opens (float, size, workspace, ...); `shell` is axiom's own effects (do not disturb, keep awake, power profile, hide from, pause shortcuts, pause OSDs, hide the bar). Each shell effect has its own `enabled` switch, so a configured list survives turning it off, and its own `when` (open, focused or fullscreen). `when` defaults to open, except pause shortcuts, pause OSDs and hide the bar, which default to focused.
- `WindowRules.switches` are built-in rules, all off by default and ranked below the user's: float Steam's small windows, float picture-in-picture videos, float utility windows, keep the screen awake while fullscreen, and send games to a special workspace (no default special workspace: pick one). See Built-in switches.
- A rule sent to a workspace has a `follow` switch ("Go there too", off): off, the window opens there and you stay put; on, you switch to it, like the special workspace's shown or silent switch.
- An unset effect is its zero value (`false`, `''`, `0`; size 0 is "as it opens", opacity 0 is "unchanged"): every key is always filled, never null. Defaults come from the schema (a rule's `enabled` defaults to true); `Parse` expects the section after defaults are filled and reads a missing key as its zero value.
- `window.monitor` carries `x-scope: machine` itself, because a scope condition sees only an item's own keys: a shared rule travels without its monitor.

### Kinds: written or live
- Some fields only the daemon can test: `process`, `startedFrom` and `game` are live (`Field.Live`). A kind with one live condition is live, so no compositor config can match it; `Rule.CompiledKinds` and `Rule.LiveKinds` split a rule's kinds, in order.
- `steamGame` lowers to the app id `steam_app_<N>` and `app` (a desktop entry id) to the app ids a resolver gives, so neither is live. `Lower` gives a kind as tests, flags and the live bit.

### Processes and games
- `procinfo.Reader.Lookup` gives a window's process name (`comm`, with the kernel's 15-byte cut undone), the names of the processes above it and its game signals. It reads only the user's own processes, cached by pid and start time; the facts are taken at the first lookup and kept.
- Only process names and signal names leave the package; argument and environment values never do: environment and command line are scanned for a fixed list of names and dropped. A non-dumpable process reads as not ours.
- The signals and where each looks (the window's process, the processes above it, its environment) are the table in `procinfo/game.go`. Steam counts through what it launches (`reaper SteamLaunch` or a Steam game id), so Steam's own windows are not games. Lutris and Heroic count only through what runs the game (`lutris-wrapper`, `legendary`, `gogdl`, `nile`, or `LUTRIS_GAME_UUID` / `HEROIC_APP_NAME` in the environment), not their UI process. Wine and gamescope count only together with a launcher signal (Steam, Proton, Lutris, Heroic, umu): a bare `wine notepad` is not a game.
- An X11 bridge (`xwayland-satellite`, `Xwayland`) stands for many windows, so its windows have no process facts: on niri, X11 games are recognised only by their `steam_app_N` app id. `procinfo.Detect` adds that app id signal.

### Patterns
- A condition's value becomes one of three anchored forms: the literal (`is`, `isNot`), the literal inside `(?s:.*)` on both sides (`contains`), or the user's own pattern inside the same (`matches`).
- A user's pattern is re-printed through `regexp/syntax` (`Normalise`) so every compositor's engine (RE2, Rust regex, PCRE2) reads it the same way. Four constructs are refused (`(?m)`, `\Q…\E`, `\p`, `\b`), capture groups are dropped (their names and numbers would clash when patterns are joined), `$` prints as `\z` and `\v` as `\x0b`.
- Several `isNot` conditions on one field merge into one negated alternation.
- `tests/fixtures/windowrules/regex.json` pins the printed forms and what they match; a Go upgrade that prints differently fails its test.

### Validation
- `Validate` lists every rule's issues, enabled or not, then the switches'. A bad rule still saves and carries issues; `Usable` returns the enabled rules with none (a repeated id drops all its rules), the ones to write and match.
- An issue's `message` is an English template with `{0}` placeholders that `args` fill, so the page can translate it; a field in `args` is its raw id.
- The codes and their checks are in `validate.go`.

### Writing
- The daemon compiles the usable rules once per config change (`windowRules` in `buildInputs`) and each writer puts them where its compositor's rules go: the module, the managed config, niri's detached module, or the runtime (Hyprland's `AXIOM_RULES`, sway's `for_window`). Who wins per mode, the managed split on niri, and the runtime layers: [config modes](../compositor/config-modes.md), [Hyprland](../hyprland/config-modes.md), [niri](../compositor/niri-backend.md), [sway](../compositor/sway-backend.md).
- `compositor.state`'s `windowRules` reports the issues and, per usable rule, what the config applies, what the daemon will place after open, what's dropped; `compositor.checkRules` checks an unsaved draft the same way (unsaved rules never reach the compositor).

### Compiling
- `HyprRuleLines`, `NiriRuleNodes` and `SwayRuleLines` (`render/windowrules.go`) take a `RuleSet` (the usable rules, the app id resolver, the backend's `supports`) and give the rules in Hyprland Lua, niri KDL and sway config lines, plus an `Unwritten` per rule with something left out. One compile step decides which kinds and effects are written, from the capabilities (never the compositor's name); the printers only print.
- Rules are written lowest priority first: every compositor lets the later rule win for the same property, so the higher rule in the list lands last.
- Effects: the table in `windowrules.go` has the full lists. `ruleMaximize`, `ruleTearing`, `ruleNoScreenShare` and `ruleXwayland` are the new capabilities; `pin`, `namedSpecial`, `windowOpacity` and `windowBlur` gate their effects too. An effect without its capability is dropped and reported. Center is written by Hyprland and sway; niri writes nothing (it opens a new floating window at the center already).
- A workspace move is silent (the window opens there and you stay put) unless the rule's `follow` is on: Hyprland drops `silent`, sway adds a `workspace` command. niri's `open-on-workspace` has no following form, so the daemon follows (Placement). Hyprland writes `name:<name>` for every non-numeric workspace, so "-1" is a name, not a relative selector.
- Negation: niri `exclude` (a kind with a negation gets its own block); Hyprland `negative:<re>`, on `initial_class` or `initial_title` when the field also has a positive test; sway a PCRE2 lookahead in the one criterion.
- sway's `app_id` matches only Wayland windows and `class` only X11 ones, so an app id test is written on both unless an xwayland condition picks one.
- Quoting: Lua and KDL strings escape a pattern natively. sway unescapes a config file C-style before reading criteria and expands `$name`, so `SwayCriterion` writes `\x22` for a quote and `\x24` for a `$`, and a file doubles every backslash on top. Over IPC (`runtime`) each `for_window` command chain goes through `SwayBindCommand`, because an unquoted chain is split at its commas; a file's stays bare. `RuleEffects` lists the effects a rule sets.
- Left to the daemon, reported in `Unwritten`: live kinds (`Live`) and a numbered workspace on niri or a special workspace on sway (`Placed`: sway's named specials are a per-window mark a `for_window` can't write). A kind no config can match (XWayland on niri, an app with no app ids) is `Skipped`.
- niri's `open-on-workspace` names a workspace niri's own config declares. sway's look sets every window's opacity and blur as focus moves, which overrides a rule's opacity and No blur while the look sets them.

### The page
- The Window rules tool page (`needs: configModes`: rules reach the compositor only through the config writer) has the rules as a list, dragged to order (list order is priority), and beside it the selected rule: its name, icon and switch, its kinds of window and their conditions, its "When it opens" effects, and its problems. A condition is one compact row (field, test, value); the test's options and the value box follow the schema (`x-enumShowIf`, `x-showIf`).
- Edits are a `ConfigDraft` of `WindowRules` in `WindowRulesManager.editor`, saved like every editor. Problems come from Go only: the draft's from `compositor.checkRules` (300 ms after the last edit, on load and when the compositor's abilities change; only the latest answer is kept) while the draft differs from what's saved, else `compositor.state`'s `windowRules` (`WindowRulesManager.savedReport`, what the compositor actually has). A rule with problems still saves; it isn't applied.
- Right after a save the page shows the previous saved report until the daemon pushes the new state, and a dirty draft shows the saved report until its first check answers; a failed check keeps the last report.
- No preview: unsaved rules never reach the compositor (`WindowRules` stays out of `CompositorConfigManager._layerSections`).
- Effects the compositor can't do are greyed by `x-enabledIf` on the same capabilities `ruleGates` drops them for (a Go test keeps the two in step), with `CompositorManager.unsupportedNote` saying why; a greyed value is kept. A numbered workspace on niri, a special workspace on sway and kinds with live conditions are shown as "applied just after the window opens".
- Every field is offered (the schema's enum, process, started from, is a game and installed app included), filtered by its `x-enumShowIf` (`xwayland` only where `ruleXwayland`). Changing a condition's field to or from `app` clears its value (a typed text is no desktop file). The installed app's value is a search combo over `WindowRulesManager.apps(query)` (`DesktopEntries` less the launcher-hidden `noDisplay` ones, which are not offered, scored by `Search.score`, at most 60; the value is the `.desktop` file name `mimeapps.WindowAppIDs` takes); `appOption` shows the current one by its name, a launcher-hidden app a rule already names included.
- **The count**: each rule row shows "N open", the open windows its conditions match, on or off, updating as you edit before saving. `WindowRulesEditor` asks `windowRules.match` with the draft (a kind with an issue is left out) in the same 300 ms debounce as the check, on load, when the compositor's abilities change and on every `windowRules.state` push, only while a page holds the editor (`acquire`/`release`, a `ConsumerRegistry`); the latest answer wins. `State.open` (the open window ids) makes a window opening or closing reach the count even when no saved rule matches it. A recount only sets `_matches`, never the draft.
- **Pickers**: Add from open window (`windowRules.windows`: app id, title, process, and for a game why it counts as one; "process not known" for a bridge or an unknown pid) and Add app are `TypePickerPopup`s. The kind goes to the rule that was selected when the picker opened (found by id); one that is still the new-rule placeholder (an empty app id) is replaced, otherwise it is appended.
- **A rule from a window**: what a window gives a rule is decided once, in Go (`windowrules.KindFor`: its app id, a Steam game id for `steam_app_N`, else its process, else its title; one `is` condition), behind `windowRules.fromWindow {id}` (`""`: the focused window). The picker, `/rule` and `axiom ipc windowRules fromFocused` all call it. `/rule` and `fromFocused` open the page with a new rule appended last and selected, unsaved, named after the installed app (else the window's title, else its app id); `axiom ipc windowRules open` opens the page. "Focused" is the last window the engine saw focused that is still open (a layer surface, the launcher, holds the keyboard when `/rule` runs, and compositors differ on whether the app still counts as focused).
- **A missing app**: a kind whose installed app isn't installed is `missing` in the report (`Unwritten.Missing`, `windowrules.ErrNoApp`), not `skipped`; the page says "This app isn't installed, so this kind matches nothing." The compositor note is for `skipped` only.
- **"Don't focus when it opens"** isn't applied to the kinds axiom matches just after the window opens (PR 8): a rule with it on and any `live` kind in its report row gets a note.
- An issue's text is its English `message` through `I18n.tr` with `args` filled in (a field id as its label): `WindowRulesEditor.issueText`, which lists every message of `validate.go` for the translations (a Go test keeps the list complete).

### Watching windows
- `compositor/windows` reports the compositor's windows as `Event`s (`reset`, `opened`, `changed`, `closed`; `Window` has id, app id, X11 class, title, pid, XWayland, workspace, output, floating, fullscreen, focused) for Hyprland, sway and niri. The engine runs it.
- **Reset vs Opened**: the first full list after each (re)connect is one `Reset`, never `Opened`: only a window that appears after it is `Opened`. Windows already open are touched only on "Apply to open windows", and the while-effects are rebuilt from the `Reset` after a daemon restart.
- **A batch, then a diff**: the run loop reads every event that is ready, the watcher applies them to its table through the compositor's source (at most one refetch of each kind, in a fixed order, then any window an event described that the refetch lacks), and the watcher emits the difference: `Closed`, `Changed` (only when a field differs), then `Opened`. A burst costs one refetch, and a window that opens and closes inside one batch emits nothing.
- **What refetches**: Hyprland applies `windowtitlev2`, `activewindowv2` and `closewindow` from the payload and refetches `j/clients` (and `j/monitors` for a monitor event or an unknown monitor id) on `openwindow`, `movewindowv2`, `changefloatingmode`, `fullscreen`, `moveworkspacev2`, `renameworkspace` and `configreloaded`; sway refetches `get_tree` on window `new`/`move` and workspace `move`/`rename`/`reload` and updates the rest from the event's container; niri's stream is the whole state (only `Outputs` is requested, for the logical sizes, at each workspace change; so an output scale or mode change reaches the fullscreen rule at the next workspace change or reconnect). The watcher connects again after a drop with a fresh `Reset`.
- **Fields**: Hyprland ids keep their `0x` (socket2 leaves it off, the watcher adds it); focus comes from `activewindowv2`, never `focusHistoryID`. niri has no XWayland flag (`xwayland` is false; an X11 window shows as its class) and no fullscreen field: a tiled window as big as its output's logical size (within 1 px) is fullscreen. sway's scratchpad windows have no workspace or output.
- **Fixtures**: `compositor/windows/testdata/<kind>.json` are sessions recorded in nested Hyprland, sway and niri, replayed on the fetch seam; `<kind>.want.json` are the expected events (`go test -run TestFixtures -update`). To re-record, run the same script nested: open window A, then open B (its title changes), float it, fullscreen it and leave, move it to workspace 2, open an X11 window, focus A, close the X11 window then B, saving each step's events and the replies a refetch would get.

### The engine
- `windowrules/engine` follows the watcher's windows and matches every usable rule against them, live: when a window opens, on each `Changed` (a title that arrives late starts its holds then) and on every config or capability change. `windowrules/match.go` and `windowrules/holds.go` are pure and the same for every compositor: the engine sees only `windows.Window`, its process (procinfo) and the shell's `supports`, never which compositor.
- **Every kind counts**, written or live: the while-effects are axiom's, not the compositor's. A kind `Lower` refuses (an `app` with no installed entry), or testing `xwayland` while `supports.ruleXwayland` is false (niri), matches nothing, like the kinds `compositor.state` lists as skipped.
- **An unknown process** (no pid, not the user's, or an X11 bridge such as xwayland-satellite) satisfies no `process` or `startedFrom` condition, "isn't" forms included: "process isn't steam" means "known not to be steam". A window is a game when `procinfo.Detect` says so; with no known process that is only its `steam_app_N` app id.
- **Triggers**: *open* while the window exists, *fullscreen* while it is, *focused* while it is and for 0.5 s after it loses focus (one timer, so Alt+Tab doesn't flicker the effects); a closing window releases at once. After a `Reset` nothing is in that grace.
- **Holds** (`windowrules.Hold`): `dnd`, `keepAwake` and `pauseBinds` list the rules holding them (priority order); `hideFrom` is per place the window ids, `pauseOsd` and `hideBar` the outputs of the windows held; `powerProfile` is the highest-priority rule's. `pauseBinds.keep` is the union of the all-except rules' binds and `these` is the other rules' binds less `keep`, so an all-except rule's way out is never paused. The effects below consume every hold.
- **Restart**: a fresh daemon's watcher starts with a `Reset`, so the holds come back from the open windows; nothing is persisted. Nothing is placed.
- **Published** as `windowRules.state` (latest-wins) only when what the rules decide changes (`State`: the matches with each rule's name, the open window ids, the holds, the overrides, the look; never a window's title), and read with `windowRules.get`, `windowRules.windows` (each window with its process facts, why it is a game and its rules), `windowRules.fromWindow` (a window, or the last focused one still open, and the kind a rule made from it starts with) and `windowRules.match` (a draft section: the open windows each of its rules matches, a kind with an issue left out). `WindowRulesManager` mirrors the state.
- **The sway look**: `State.look` is each window's opacity a rule sets and the windows a rule turns the blur off for. `SwayState.windowCommands` sets those instead of the look's (`WindowRulesManager.look`), so the per-window look no longer overwrites a rule.

### The effects
The holds with consumers. Each effect lets go when its hold ends, and is `Hold`'s merge applied by one owner:
- **Do not disturb** stays in the shell: `NotificationDnd` (a child of `NotificationManager`) reads `WindowRulesManager.holds.dnd` and `state.overrides.dnd`, and `DndHold` (pure) decides `on = manual || (held && !overridden)`. `manual` is the user's own switch (saved as `dnd`). By hand (`setDnd`, `toggleDnd`, the `dnd` IPC target, every keybind, widget and OSD toggle) sets `manual`; turning it off while a rule holds it also asks `windowRules.override {effect: "dnd"}`. The schedule sets only `manual`, so its end time doesn't override a game's DND and a rule ending after the schedule's end turns DND off. A rule's change opens the Dnd OSD as the schedule's does (`quiet` on the system turns that off).
- **Keep the screen awake** is the daemon's: `windowrules` hands the rules' names to `idle.Service.SetKeepAwake`, which holds axiom's idle off and the one logind idle inhibitor caffeine holds (why `"Keep the screen awake"`), listed in `idle.state` as `{source: "windowRule", app: <rule name>}`. It is separate from caffeine: the Idle Inhibitor widget, the Caffeine popout and the OSD tile show only the user's switch, and neither ends the other's hold. Settings › Idle's status lists the rule ("Window rule: Games"). The last shell going turns only caffeine off.
- **Power profile** is the daemon's: `internal/powerprofiles` (`Holder`) holds `performance` or `power-saver` in power-profiles-daemon (`org.freedesktop.UPower.PowerProfiles`, else `net.hadess.PowerProfiles`) with `HoldProfile(profile, rule name, "axiom")`. It dials the system bus only while a profile is wanted. A change takes the new hold before releasing the old, so PPD doesn't fall back to the user's profile between. PPD restarting is not an override: the hold is taken again on the new owner. A refused hold (no performance profile) is logged once and not retried until the wanted hold changes. PPD restores the profile active before the first hold when the hold ends.
- **Overrides** (`windowrules.Overrides`, pure, kept by the engine's loop and published as `State.overrides`): turning DND off by hand, or picking a power profile, wins until the hold ends. DND's ends when no rule holds it; the power profile's when the held `{profile, rule}` changes or ends. The shell asks for DND's through `windowRules.override` (shell only); for the profile PPD sends `ProfileReleased(cookie)` for the cookie held now, which `Holder` reports (`OnOverridden`) and the daemon posts as an override. An override asked while the effect isn't held is ignored. Overrides aren't persisted: after a daemon restart the effects resume.
- Every hold ends with its connection: the PPD hold and the logind inhibitor are closed on any stop (a crash or re-exec included), and the holds come back from the engine's `Reset`.
- **Hide from** is decided once in Go (`holds.hideFrom`: per place, `dock`, `switcher`, `workspaces`, `launcher`, the ids of the windows held); the shell applies it through one function, `WindowRulesManager.shownIn(place, windows)` (`HideFromHold.shown`, pure), never reading `holds` itself. It is not in `CompositorManager`: that would make a singleton cycle through the editor, and `CompositorManager.windows` has users that must see every window. Applied at the dock (`DockManager.itemsFor`, before `DockLayout.buildItems`: an app whose windows are all hidden has no running item, a pinned one shows as not running; `windowsCover`, so the intellihide, is unfiltered), the switcher (`_open`: the list leaves them out; with the focused window hidden the selection starts before the first tile, `WindowOrder.startIndex`, so Alt+Tab lands on the last window used), the workspace icons (`CellContents`, `StripWindows`, `StripWindowsBox`, `ActiveStrip`, `OverviewGrid`, `WorkspacesMap`: only the window's own icon, strip cell or preview; the workspace stays occupied, counted and navigable) and the launcher's window rows (app rows untouched). Nothing is hidden until the daemon has answered (`holds` null: every window shows), so a window that opens shows for the moment until the push arrives. Not hidden anywhere else: the compositor's own overview, `CompositorManager.windows`, notifications.
- The inspector's "While it's open, focused or fullscreen" section (the schema's `shell` group through `SchemaPropertiesForm`, `order` `dnd`, `keepAwake`, `powerProfile`, `hideFrom`, `pauseBinds`, `pauseOsd`, `hideBar`) holds the seven effects, with notes for a power profile without power-profiles-daemon or without a performance profile.
- **Pause OSDs** (`shell.pauseOsd`) stops an OSD opening on the monitor, not showing: `OSDEngine.opens(item, def, change, onScreenChanges, paused)` says false for any change but an alert (a headset's battery, the laptop battery dropping to low or critical: Battery's `alertKinds`), so an OSD already open (from its hover strip, the Show button, the settings Preview, or before the hold) still shows its changes. `qml/shell/OSD.qml` gives each `OSDHost` `paused` from `WindowRulesManager.pauseOsdOn` (the outputs; the other screens of "all" mode still open theirs); the host and the engine name no system and no rule. Events aren't rerouted: a drive, screenshot, monitor or message event on a paused monitor shows nowhere and is filed in the notification history's Quiet section (`OSD.cardsToHistory`).
- **Hide the bar** (`shell.hideBar`) makes every bar on the monitor an always-auto-hiding bar: `ScreenEdgeManager` hands `BarEnrich` `hiddenByRule` for each bar whose monitor is in `WindowRulesManager.hideBarOn`, and `BarEnrich` gives `autoHide: "always"`, `autoHiding`, no reserved space (its room goes to the windows) and no automatic reveals (`revealOnWorkspace`, `revealOnActivity` off); everything downstream reads those fields as for a configured `always` bar. `BarRevealManager` hides each bar at once as it turns `hiddenByRule` (a pin or moment from before is dropped); its screen edge, its holds, the IPC `reveal` and a pin made meanwhile still show it. Nothing is undone when the hold ends: the bar is its config again.
- `pauseOsdOn` and `hideBarOn` are the only readers of `holds.pauseOsd` / `hideBar`: each is the same array while its content is, so a hold push for another effect re-enriches no bar and re-runs no OSD binding.
- **Pause shortcuts** (`shell.pauseBinds`): while the hold lasts the compositor stops answering the picked shortcuts (*these*), or every shortcut but the kept ones (*all except*: on Hyprland and sway your own too; on niri only axiom's), and answers again when it ends, the daemon stops or it crashes.
  - Who decides: `BindsHold.Pause(bound)` (pure): given the ids of the binds the layer binds, in order, it gives `Pause{AllExcept, Keep, Paused}`; every writer applies that and decides nothing.
  - One owner, `Manager.applyPause`: `SetPause` (from `windowRulesChanged`, enqueued, never blocks the engine) builds the inputs with the hold (`Facts.Pause`) and applies when the paused set changed (`pauseKey`). A pause never rewrites a Hyprland or sway file (`pause`/`pauseKey` are set after `liveRestKey`). It is applied again (forced) after each reload (it resets Hyprland's Lua state and drops sway's runtime unbinds and modes), after each runtime re-apply, and when the bind mode returns to the default while *all except* holds.
  - Hyprland: binds are kept by id (`AXIOM_BINDS`, `render.HyprBindLinesByID`); *these* switches each handle off (`set_enabled(false)`, in a `pcall`, ids in `AXIOM_PAUSED`); *all except* defines the submap `axiom_paused` holding the kept binds (`AXIOM_PAUSE_KEYS`) and enters it. If no kept bind is complete nothing is paused (never a trap). Every apply first switches the last pause's binds back on.
  - sway: *these* unbinds the paused binds (only those sway bound: the runtime layer's `applied` while it's on); *all except* defines the mode `axiom_paused_<hash of the kept lines>`, enters it and binds the kept ones in it. What gives it back is recorded first (`runtimeState.SwayPaused`, cleared by a reload, a clean stop and a fresh daemon). A bind taken as sway's floating modifier (mouse drag and resize) isn't paused.
  - niri: binds come only from files, so the paused ones are left out of axiom's files (`Facts.PauseInFile`) and the normal 300 ms apply rewrites them. A clean stop in included or managed mode rewrites them without the pause; after a crash they stay as they were until the daemon starts again (see Teardown).
  - Leaving a mode (`Reload.ModeChanged`: Hyprland `submap>>`, sway's mode events): the daemon puts the pause back when the mode went from another to the default, so the key recorder or a kept switcher bind needs no knowledge of the pause.
  - Teardown: `Manager.teardownSteps` returns the writer's `unpauseSteps` first whenever something is paused, in every mode, so the crash guard releases it too. A re-exec carries everything; the new engine's `Reset` brings the hold back. The manager starts with the applied pause unknown (all-except), so its first send gives back whatever the last image left (and teardown includes `unpauseSteps` from the start); a send that fails is recorded as unknown again, so the next inputs retry and teardown still gives back. On niri a clean stop in included or managed mode rewrites the files without the pause (`Manager.Teardown`); a crash leaves them, but they always keep at least one kept bind, and the next start rewrites them.
  - A way out that works: `windowrules.ContextOf` also lists the binds not bound (paused, or no key); *all except* with every kept shortcut among them is the issue `pauseBindsWayOutOff`. The check ignores a bind's "Only when" (`ContextOf` can't evaluate it), so a kept bind it leaves unbound passes; the runtime then fails open: `BindsHold.Pause` pauses nothing when none of the kept binds is bound (on any compositor, so no stop or crash leaves every shortcut paused).
  - A shortcut a rule uses can't be removed on the Keybinds page (a saved bind; a new or duplicated one has no rule naming it): `x-ref` of kind `keybind` on `shell.pauseBinds.binds` (an array of ids, `when` the rule's pause is on: a switched-off rule doesn't block) gives `KeybindEditor.usedBy`, which disables Remove with "Used by window rule {0}"; a rule's `window.special.id` is an `x-ref` too, so a special workspace it sends windows to can't be deleted. The rule inspector picks shortcuts with `RefChips` (chips and an "Add shortcut" picker).

### Placement
- **What is placed** (`windowrules.PlanFor`, `place.go`, pure): a usable rule matching a window gives it what the compositor's config left to the daemon. The engine reads that from `compositor.state`'s `windowRules.rules` rows (`SetReport`: `placed`, `dropped`, `live`, `skipped`), never from the compositor's name. A matched kind the config writes: only the row's `placed` (a numbered workspace on niri, a special workspace on sway, `follow` on niri). Only live kinds matched (process, started from, game): every effect the rule sets, less `dropped`, less "Don't focus when it opens" (it means nothing after open, and isn't applied to live kinds), less the look and maximize/pin when `supports.ruleLiveLook` is off. With no report (the layer isn't live) nothing is placed: a written rule may have acted already.
- **Merging**: per effect the highest rule giving it wins (a higher rule the config writes claims its monitor, workspace or special and size even where the daemon places none of them, so a lower live rule can't override it); the destination (workspace or special) is the highest rule giving one, with its own "Go there too" or shown/silent; the look is every rule giving any of it, in priority order.
- **Once per window**: from `Opened` only (never a `Reset`: windows from before the daemon started or a reconnect wait for Apply). Each window is planned after every recompute until it has a step or its grace (1.5 s after it opened) ends, so a late title (Steam) still places it; there is no timer, the grace is checked when the window next changes. It isn't placed again by a later change.
- **Batches** (`Plan.Batches`, sent `Settle` = 100 ms apart by a goroutine the engine owns, `Run` waits for them; a failed batch is logged and the next still goes): output, float, look and the move; then size alone; then center followed by the move; the last ends with fullscreen (left out when already fullscreen), maximize, pin, focus. Measured: sway loses a size sent at open, niri centres by the old size until the new one is set, sway's `move position center` pulls a floating window onto the shown workspace (so the move goes after it) and Hyprland's pin needs a floating window. Placement takes about a frame on niri, under a millisecond on Hyprland and before the window shows on sway.
- **Follow** is a `focus` step: the compositor goes to where the window is (Hyprland `hl.dsp.focus`, sway `focus`, niri `FocusWindow`). The moves themselves are always silent. A shown special workspace is the move's `Show` (Hyprland `follow = true`, sway `scratchpad show`).
- **Dispatchers** (`compositor/place`, picked by `ipc.Detect`; the engine and `windowrules` name no compositor): Hyprland one Lua chunk by window address (a pcall per step, errors raised together); sway one `[con_id=N] …` command list, the special mark `axiom-special-<id>-<con_id>` as `SwayState.specialMove`; niri one by-id action per step. niri answers `Handled` even for an unknown id, so a failure there only shows when the request is refused.
- **Hyprland tag rules**: a rule with a live kind and any of opacity, no blur, hide from screen sharing or tearing also gets `hl.window_rule({ name = "axiom-rule-<id>-tag", match = { tag = "axiom-rule-<id>" }, … })` (`HyprRuleLines`); the look step tags the window, and the dynamic effects apply at once. sway's opacity and blur are the engine's look, so its look step sends only `allow_tearing`.
- **`ruleLiveLook`** (Hyprland, sway; not niri, which has no by-id action for them): the look, maximize and pin can be given to an open window. Without it they apply only through the compositor's config.
- **Apply to open windows** (`windowRules.applyNow` → `{windows: n}`, the Window rules page's button, dimmed and inert until the engine runs and the draft is saved, since it applies the saved rules): every open window, those from before too, gets every matching rule's effects, written ones included, as a fresh open would, except "Don't focus when it opens". It never follows and shows no special workspace, so many windows can move at once and you stay where you are. A window still in its open grace is left to the open-time placement (Apply skips it). On sway a window moved into a special group first loses its marks of any other group.

### Built-in switches
- **One table in config form** (`windowrules/builtin.go`): each built-in is a row `{key, name, on, rule}` (the id is `"_"+key`) whose `rule` gives the rule's `icon`, `windows` and `window` as a user would save them. `Builtins` parses them with `parseRule` (so they are lowered and matched like any rule), and Copy as rule returns the same tree (`BuiltinRule`, a fresh one per call): a copy is exactly what the switch did. Table order is priority, below every rule of the user's.
- **`windowrules.Effective`** (`Usable`, then `Builtins`) is the one entry point: `manager.windowRules` (the writers and the report rows, so placement on sway and for the live kinds reads them like any rule) and `engine.configure` (matching, placement, Apply) call it. `engine.Match` stays on the draft's own rules, so the page counts only yours. A switch with an issue (`Rule ""`, at `switches.<key>` or under it) is left out.
- **Ids** `_steamFloat`, `_gamesSpecial`, `_pictureInPicture`, `_utilityFloat` and `_fullscreenAwake`: a leading `_` is outside the pattern of an id the page makes, and valid in Hyprland rule names (`axiom-rule-_gamesSpecial-0`, so Hyprland detached's `axiom-rule-` switch-off covers them). `Validate` seeds its seen ids with `BuiltinIDs`, so a hand-written rule with one is a `duplicateId`.
- **Float Steam's small windows**: one kind, app id `steam`, a title matching `.`, and a title that isn't `Steam` or `Steam Big Picture Mode`: every Steam window but the main one and Big Picture floats, in any Steam language (only the main window's title is the same in all). The positive `title matches .` keeps a window that opens with no title from floating (Hyprland tests the negation on `initial_title` only when the field has a positive test). A window that gets its title later may open tiled; the main window never floats by mistake.
- **Send games to a special workspace**: kind 0 is app id `^steam_app_\d+$` (written into the config: most games open in place), kind 1 is `game is` (live: Lutris, Heroic, umu and the rest are moved just after they open; a Steam game kind 0 wrote is skipped by placement already). The special workspace is the switch's `special`; it has no default, and an enabled switch with none is a `specialMissing` issue ("Pick a special workspace.") under the games form, so no rule is written. On niri `namedSpecial` is off, so `special` is dropped and the rule does nothing; the switch is greyed (`x-enabledIf`).
- **Float picture-in-picture videos**: one kind, a title matching `^(Picture-in-Picture|Picture in picture)$` (Firefox, Chromium), `float` + `pin`, no size (the browser's own keeps the video's aspect). No app id: the title is specific, so every Firefox and Chromium fork matches. No other fact tells a PiP window from the browser's (same app id and process), and both titles are translated with the browser: English only. niri drops `pin` (floats only). Hyprland tests the title as the window opens.
- **Keep the screen awake while fullscreen**: one kind `appId matches .*` (how a rule says "any window": a kind with no condition is refused), `shell.keepAwake` when fullscreen, no window effect. A rule with only shell effects is never written to a compositor config; only the engine acts. Any window on any workspace counts, so a fullscreen window on a hidden workspace holds it; niri has no fullscreen flag, a window as big as its output counts, so a maximized one does too.
- **Float utility windows**: one kind, an app id alternation (`utilityAppIDs` in `builtin.go`: GTK, GNOME and KDE file picker portals, KDE and GNOME polkit agents, pavucontrol, pwvucontrol, nm-connection-editor, blueman-manager), `float`, written everywhere. Compositors already float a window with a parent or fixed size, so a picker may open floating without it (floating twice is a no-op). Sway matches the app id on `class` too; these apps' X11 classes are capitalised, so X11 builds don't match. A wrong id floats nothing.
- **Copy as rule** (`WindowRulesEditor.copySwitch`, a link under each switch (any key) through `SchemaPropertiesForm.fieldAction`): asks `windowRules.builtin {key, section}` (any connection; the draft's values, so an unsaved special id is copied), adds the rule last among the user's, selected and unsaved, named after the switch's schema title, and turns the switch off in the same draft (the games switch's link is hidden where `CompositorManager.supports.namedSpecial` is off, e.g. niri) so the thing isn't done twice. The switches' problems (`Rule ""`) show under the games switch (`SwitchesGroup`).
- **Not a deletion-guard site**: `gamesSpecial.special.id` has an `x-ref` of kind `specialWorkspace` (the dropdown), but `SchemaRefs.sites` walks list items only, so deleting that special workspace isn't blocked by the switch (Hyprland and sway make a special on use).
