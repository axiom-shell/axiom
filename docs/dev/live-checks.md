# Live checks

> **Files:** this file only
> **Config:** none
> **Related:** [roadmap](roadmap.md) (Running it unattended › Pick adds to it), [testing](testing.md)

Everything that waits for the maintainer's own session, in one place: what only the live environment can confirm or build, and code no real hardware has run yet. None of it holds up a roadmap row ([roadmap](roadmap.md#running-it-unattended) › Pick). A confirmed check is deleted; a failed one becomes an [issues.md](issues.md) entry.

## Untested on real hardware
Code tested only against fakes (unit tests, a fake D-Bus service, nested sessions), by the hardware a check needs; the steps are under [Checks](#checks). Small code a reader can trace whole isn't listed.

### Bluetooth (the daemon owns BlueZ)

Seen live: pairing a controller from the Bluetooth menu. Tested against the fake BlueZ in `backend/internal/bluez/*_test.go`.

- **A second device of any kind** (a controller works for most): connect / disconnect from the menu (the Connecting… / Disconnecting… states, `Service.Connect` / `Disconnect`), forget, rename, auto-connect (trusted), block and unblock (`bluez.go`), and the OSD's Connected / Disconnected cards with the Bluetooth system in an OSD's systems (`events.go`: connects within a second joined, the radio's own disconnects dropped).
- **A device that reports its battery** (most headsets, many mice and controllers): `Battery1` read into the state, the Battery widget's and module's peripheral lines (`BatteryManager.peripherals`), the low / critical card or notification once per drop (`DeviceBatteries.step`, `Bluetooth.notify`).
- **A device that pairs with a code** (a phone: compare a code; a keyboard: type one shown): the pairing agent's requests in the shared prompt (`agent.go`, `BluetoothManager._agentRequest`): confirm, PIN, passkey, a code to type with its typed digits lit, authorize; a pairing started from the device (the agent as BlueZ's default); Cancel and a device cancelling (`agentCancel`).
- **A headset:** its OSD card folding in the audio output switching to it, and its level arriving late (the Bluetooth system's `absorbs`, `AudioManager.bluetoothAddress`).
- **A headset with a low battery** (under `Bluetooth.lowBattery`) connecting: whether its low-battery card gives way to Audio's Output card for it ([known PLAUSIBLE](issues.md#a-headsets-low-battery-card-gives-way-to-audio-switching-to-that-headset)).
- **An rfkill switch** (`rfkill block bluetooth` from a terminal by the user, or a laptop's airplane key): the Unblock button (`rfkill.go`: the change-all event written to `/dev/rfkill` without root), and a hardware switch's message.
- **Discoverable** from the menu (a phone scanning for this computer): the countdown (`discoverableUntil`), BlueZ's timeout set to 180 s when it was 0.
- **BlueZ restarting** (`systemctl restart bluetooth`, by the user) while the menu scans and while a prompt shows: the scan starts again, the prompt is withdrawn (`sync`, `NameOwnerChanged`).
