# Packaging: install.sh and the AUR packages

> **Files:** `install.sh`, `packaging/aur/axiom-shell/PKGBUILD`, `packaging/aur/axiom-shell-git/PKGBUILD`, `scripts/check_packages.py`, `scripts/release.sh`, `.github/workflows/release.yml`, `.github/workflows/edge.yml`, `scripts/build_binaries.sh`, `backend/internal/release/`, `components/methods/Packages.qml`, `config/Paths.qml`
> **Config:** none
> **Related:** [Self-update](features/self-update.md), [Greeter install](features/greeter-install.md), [Onboarding](features/onboarding.md), [Config manager](core/config-manager.md)

How axiom gets onto a machine: the installer (a clone in the user's home) or a distribution package (root's copy in `/usr/share/axiom`). The user-facing side is `docs/installation.md`.

### Three package lists, kept in step
- `Packages.packages` (the onboarder's install hints), install.sh's `PACKAGES` table and the PKGBUILDs' `depends`/`optdepends` all say what installs a dependency.
- They share keys: a command, a compositor by its lowercase name, `iconFont`, or a package without a command (`xdg-desktop-portal-gtk`).
- `scripts/check_packages.py` (CI, `check_all.sh`, `verify.sh` when one of them changes) fails when:
  - an install.sh key's Arch or Fedora package differs from `Packages.packages` (a COPR is `owner/project:name` there and `{ name, repo }` here; `download` is `{ file, to }`, the same URL and file; `-` and `n/a` are `null`);
  - a key in `REQUIRED` or `FEATURES` isn't in `PACKAGES`;
  - a PKGBUILD's `depends` aren't `REQUIRED`'s Arch packages (less `git`, which only fetches it: `makedepends` with `go`), or its `optdepends` aren't exactly the compositors' and `FEATURES`' Arch packages.
- Adding an optional feature: its keys in `Packages.packages` (if new), a `PACKAGES` row, a `FEATURES` row, and an `optdepends` line in both PKGBUILDs, in the same words.

### install.sh
- One self-contained file, wrapped in `main` so `curl | bash` reads all of it first. Questions and the package manager read `/dev/tty`.
- **Distribution:** `distro_family` follows `Packages.distroFamily`'s rule (os-release `ID`, else the first known `ID_LIKE`). Arch uses `pacman -T` / `pacman -S --needed`; Fedora `rpm -q --whatprovides` / `dnf install`, each COPR enabled first (`dnf copr enable`, the copr plugin installed if missing), and the icon font downloaded into `~/.local/share/fonts` as the user.
  - `PACKAGES` cells: a package, `owner/project:name` (from that COPR), `download`, `-` (nothing needed there: `checkupdates` on Fedora) or `n/a` (not packaged there: `awww` on Fedora, whose feature is listed as not available).
  - COPRs: quickshell from `errornointernet/quickshell` (the one quickshell's docs name; Fedora's own is too old), Hyprland and its tools from `nett00n/hyprland`. Each is asked separately; declining one a required package needs stops the install.
- **Compositor:** the main one is `--compositor` if given; else the running one (`HYPRLAND_INSTANCE_SIGNATURE`, `NIRI_SOCKET`, `SWAYSOCK`); else the installed one whose config already starts axiom (an earlier run's); else it asks among the installed ones; with none installed, it asks which to install (Hyprland by default, and without a terminal). The main one is what the session gets into (the TTY offer).
  - Every other installed compositor is offered the autostart line too, asked separately and defaulting to no: sway may be there only for the login screen, whose feature installs it.
  - Each gets the autostart line its `*ConfigWriter.autostartTarget` writes (`AUTOSTART`), unless a line matching the same `accept` pattern is there. A missing config is seeded from the compositor's default (`/usr/share/hypr/hyprland.lua`, `/etc/sway/config`, `/usr/share/doc/niri/default-config.kdl`); with no default to seed from, it says what to add instead of writing a config with no binds.
  - Night light's tool and X11 apps' helper (`xwayland-satellite` on niri, Xwayland on sway) depend on the compositors (`FEATURES`' third column; `DependencyManager.tools`' `compositors`). The login screen's feature installs sway, which it runs whatever the session's compositor is. With Hyprland among the compositors it's two features instead (the first entry matching wins): greetd alone, and sway on its own, recommended (so "all" takes it); declined, the login screen runs in Hyprland.
  - Versions: Hyprland below 0.55 warns; sway and niri below what axiom is tested with (`TESTED_SWAY`, `TESTED_NIRI`) only say so.
- **The binary** (maintainer, 2026-10-27: "Download, build fallback (Recommended)"): `official_binary` downloads the official build of the clone's checkout into `$XDG_BIN_HOME` or `~/.local/bin` (`AXIOM_BIN`): the checked-out `v*` tag's release, else the [edge build](#edge-builds) when its `COMMIT` is HEAD's, from `AXIOM_RELEASES` (the official releases; tests serve their own). `COMMIT` and the binary are each checked against the release's `SHA256SUMS` (`sha256sum -c`), the binary checked to run (`version`), then it writes the tree's schema copy (`axiom schema build --tree`) and is swapped in. With none to take (another architecture, offline, an untagged commit edge wasn't built from, a sum that doesn't match: said, not fatal), it builds as before: `go` (installed then through the same `sudo` step if it's missing; it's no longer in `REQUIRED`), `scripts/generate.sh --no-docs` (the reference docs are a developer check that mustn't stop an install), then `CGO_ENABLED=0 go build -trimpath` beside the old binary, swapped in. A package brings its own. The binary needn't be on `PATH`: the autostart line names it by its path, as `Paths.shellCommand` does.
- **Autostart:** `autostart_line` is the line each `*ConfigWriter.autostartTarget` writes (`'<AXIOM_BIN>' run`), and `STARTS_AXIOM` is `Paths.startPattern` (`axiom run`). `axiom run` from `$HOME` finds the tree in the installed places (`tree.Find`: `~/.config/quickshell/axiom`, then `/etc/xdg/quickshell/axiom`).
- **`--dry-run`:** every change goes through `run` / `sudo_run` / `append_line`, which print instead (the binary step prints the download, and that it would build without one).
- **Packaged:** with `/usr/share/axiom/.packaged` and no clone, it skips the clone and the build, and only does packages and autostart (with `/usr/bin/axiom`).
- **Testing:** `--dry-run` on the host, and real runs in `fedora:latest` / `archlinux:latest` containers with a sudo user and `AXIOM_REPO` pointing at a mounted clone (copy install.sh out of the clone first, or it treats the read-only mount as the install). Never run it for real on the dev machine.

### The AUR packages
Not on the AUR yet: AUR account registration is closed, so they wait in `packaging/aur/` until it reopens ([#76](https://github.com/axiom-shell/axiom/issues/76), help wanted). The user docs describe installing them and say they aren't published.

- `axiom-shell` (a release's tag tarball) and `axiom-shell-git` (main, `pkgver()` from `git describe`, `provides`/`conflicts` `axiom-shell`). The same `prepare()`, `build()` and `package()` otherwise. They stay two whole files: each is its own AUR repository, and a PKGBUILD there must stand alone (makepkg and `.SRCINFO` read only it, so it can't source a shared one). `check_packages.py` keeps their `depends`/`optdepends` in step; an edit to a function goes in both.
- **The binary:** `arch=(x86_64 aarch64)`, `makedepends` `go`. `prepare()` downloads the modules; `build()` runs `scripts/generate.sh --no-docs` (the embedded copies and `config/json/config.schema.json`, neither committed; not the reference docs, which `package()` would drop anyway) and `go build` with `CGO_ENABLED=0` and `-buildmode=pie -trimpath -mod=readonly`; `package()` installs it as `/usr/bin/axiom`.
- **No compositor in `depends`:** pacman has no "one of"; `hyprland`, `sway` (which `swayfx` provides) and `niri` are `optdepends`. The package is the shell, not the session.
- **Layout:**
  - The code in `/usr/share/axiom`, with the built schema, less what only development needs (tests, docs, CI, git hooks, `install.sh`, the check scripts, every `*.md`, and `backend/`, the axiom binary's Go source).
  - The binary, `/usr/bin/axiom`.
  - `/etc/xdg/quickshell/axiom` → `/usr/share/axiom`, so `axiom run` finds it after `~/.config/quickshell/axiom` (a clone there still wins).
  - The license in `/usr/share/licenses/<pkgname>/`.
  - The marker `/usr/share/axiom/.packaged`, holding `pkgver-pkgrel`.
- Nothing writes under the code ([config-manager.md](core/config-manager.md) › Where files live). Python's bytecode cache can't be written there either, which Python ignores; the package ships none, since bytecode for one Python version goes stale on the next.
- `axiom-shell.install` prints the autostart lines on install (`'/usr/bin/axiom' run`), and on upgrade to run `axiom daemon reexec` then `axiom restart` (pacman replaces files, which qs's watcher can miss).
- **Releases:** `scripts/release.sh` checks main, opens the notes and pushes an annotated `v*` tag. CI runs on pull requests, not on main, so it first wants a passing full run on the commit it tags (`gh workflow run checks.yml --ref main`); the release workflow's cross-builds are the only arm64 build. The tag runs `.github/workflows/release.yml`, and nothing is committed back:
  - **The GitHub release** (`binaries` job), once the tag is checked to be on main: the tag's message as its notes, and the assets `axiom-linux-amd64` and `axiom-linux-arm64` (static: `CGO_ENABLED=0 go build -trimpath`, the tag stamped in as `buildinfo.version`, checked with `axiom version` to report it and the tag's commit), `COMMIT` (that commit's full hash) and a `SHA256SUMS` listing them, as `sha256sum` writes it. `scripts/build_binaries.sh <version> <dist>` builds them, for a release and the edge prerelease alike, so every official build has the same files. The greeter install, self-update and the installer take the binary from there for a tag ([greeter-install.md](features/greeter-install.md), [self-update.md](features/self-update.md)).
  - **The AUR** (`aur` job, skipped without the `AUR_SSH_PRIVATE_KEY` secret): `packaging/aur/` as main has it, `axiom-shell` given the tag's `pkgver`, the `pkgrel` and the tag tarball's `sha256sums`, built once with `makepkg --nodeps` as a check, `.SRCINFO` made for both, and each pushed to its AUR repository when it changed. The repository keeps no `.SRCINFO`, and the PKGBUILD's version fields are only the last release's.
  - Settings: the `AUR_SSH_PRIVATE_KEY` secret (the AUR account's key); optional variables `AUR_HOST_FINGERPRINT` (pins `aur.archlinux.org`'s ed25519 key, `SHA256:…`), `AUR_GIT_NAME` and `AUR_GIT_EMAIL` (the AUR commits' author).
  - **A packaging-only fix:** merge it to main, then run the workflow by hand (Actions → Release → Run workflow) with the tag and a higher `pkgrel`. A rerun also publishes the binaries again.
- **Edge builds** (`.github/workflows/edge.yml`): every merge to main publishes the `edge` prerelease, main's newest build, for a clone following main (maintainer, 2026-10-27: "Rolling CI build (Recommended)").
  - The same build as a release (`scripts/build_binaries.sh`), stamped `edge-<short commit>`: `axiom-linux-amd64` / `axiom-linux-arm64` (the full commit, which `axiom version --json` reports), `COMMIT` (the full hash and a newline), all three listed in `SHA256SUMS`.
  - The `edge` tag is moved to the commit built, so the release's page and its source archives are that commit's; the release is made on the first run. The repository's tag ruleset (`v*`) guards only `refs/tags/v*`, so CI may move `edge` but no release tag. Readers go by `COMMIT`, checked against `SHA256SUMS`, never by the tag. The tag isn't `v*`, so the tags channels never see it, and the release is a prerelease never marked latest (`releases/latest` stays a `v*` release).
  - The files are uploaded first and `SHA256SUMS` last, so a download racing an upload fails its check instead of taking a mismatched binary. A run whose commit main has moved past by publish time publishes nothing; runs never cancel each other mid-upload. Run it by hand (Actions → Edge → Run workflow) to publish main again.
  - It also makes the cross-builds run at every merge, not only at a release.
- **Reading them** (Go): `backend/internal/release` (pure) names the files and urls (`release.Official`, pinned to the official repository whatever a clone's remote; `release.Edge`; `release.Asset`, `release.SumFor`, `release.ParseCommit`), and `release/fetch` downloads one and checks it against its release's `SHA256SUMS` (`Binary`, `EdgeCommit`, and `Edge`: the binary and its commit from one `SHA256SUMS`): `ErrMissing` when there's nothing to take (fall back), `ErrMismatch` when it doesn't match (never used). The greeter install uses it, its `main` channel through edge ([greeter-install.md](features/greeter-install.md)).
- **Testing:** `makepkg` in a scratch copy of the folder (or its functions sourced with `srcdir`/`pkgdir` on a scratch clone, which tests uncommitted work), then `axiom schema check --tree <pkgdir>/usr/share/axiom`, `namcap` on the PKGBUILD and the package (in an `archlinux` container if it isn't installed: its QML-module and `bash`/`sh` warnings are expected), and `tar -tf` the package to see its files.

### A packaged shell
`Paths.packagedVersion` reads the marker beside the code (`Paths.packaged` when there is one). It changes:
- **Self-update:** off ([self-update.md](features/self-update.md)): it never checks, its settings section (`"/$packaged": false`), the onboarder's rows and `/update` are hidden.
- **Login screen:** always the `package` source ([greeter-install.md](features/greeter-install.md)): the greeter runs `/usr/share/axiom` itself, and `Greeter.source` is hidden.
