# Profile switching runs in the shell on sway and niri

> **Issue:** Profile switching runs in the shell on sway and niri, replaced on decision by the plan's items in issues.md, from The session switches monitor profiles in QML on sway and niri (fixed by item 3) on
> **Status:** decided: B (2026-10-28)

Decided (maintainer, 2026-10-28), verbatim: "go owns profile switching for every compositor". The options below are only about how.

Option chosen (maintainer, 2026-10-28), verbatim: "B; go switched anywhere. A user attempting to switch their monitor profile on hyprland (created in axiom) while axiom is not running is attributed to user error"

### Problem
The rule "which saved profile fits what's connected" lives in two places, and on sway and niri the shell does the switching:
- **The picker, twice.** `MonitorLayout.matchProfile` / `savedRules` (`components/methods/MonitorLayout.qml`, about 35 lines plus `tst_MonitorLayout` cases) and `applyMonitors`, the Lua `render.MonitorsLua` sends Hyprland (`backend/internal/compositor/render/hyprlua.go`, about 60 lines). Nothing keeps them in step except `TestMonitorsLuaPicks` and comments that name each other.
- **The session switches in QML.** Without `supports.outputProfiles`, `MonitorManager` waits for `outputsHotplugged`, reads the outputs again (`refresh`), then `_applySavedProfile` → `CompositorManager.applyOutputs`. Getting there takes `_applyProfilePending`, a `configReloaded` branch keyed on `CompositorConfigManager.status`, a `pending` guard and `useWholeScale`'s own pending flag. CompositorConfigManager's `_outputRules` runs the same match again and sends the result to Go as the `outputRules` fact (`manager/inputs.go` `Facts.OutputRules`). The sway and niri writers write that fact as `output` lines and nodes (`swayWriter.outputLines`, `niriWriter.outputs`). Go already knows the profiles (`buildInputs` reads `Monitors.items`); the only thing it's missing is what's connected.
- **The greeter matches only once.** `GreetdManager._applyCompositor` applies `savedRules` for the outputs it sees at start. `applyGreeter`'s sway branch (`daemon/compositorsocket.go`) sends only input. A monitor plugged in while the greeter is up is never matched on sway, where Hyprland's Lua picks again on every hotplug.
- **The Monitors page** runs `matchProfile` over its draft for `liveProfile` (the "(connected)" label, `selectedIsLive`) and `_detect`.

This affects every sway and niri user who keeps more than one profile. The shell has to be running and caught up for a hotplug to switch, and every hotplug does three reads: the backend's, `MonitorManager.refresh` and the writer's.

Go already has most of the pieces. `wayland/outputs.Tracker` follows hotplugs over the daemon's own Wayland connection on every compositor (`OnChange`). It lists only enabled outputs, though, and with wl_output's descriptions rather than the shell's ("make model serial"). So the switcher still needs the compositor's own list: sway's `GET_OUTPUTS`, niri's `Outputs`. `applyOutputs` (sway commands, niri `Output` requests) is already Go. The greeter only ever runs on sway or Hyprland (`greeter-session.sh`), so the greeter only needs sway handled.

### Options
#### A. Go switches on sway and niri; Hyprland keeps its Lua, checked against Go's picker
- **Picker:** one Go picker (`MatchProfile`, `SavedRules`). The Lua `applyMonitors` stays, because Hyprland's files have to switch without axiom running (managed or included mode, a session where the daemon is down). `TestMonitorsLuaPicks` runs the Go picker's case table through the Lua, so both always give the same answer.
- **Session:** on sway and niri, the session `Manager` reacts to `Tracker.OnChange` (debounced). It reads the compositor's outputs, picks, applies them live and computes `outputRules` in `buildInputs` itself, so included and managed files follow.
- **Greeter:** on sway, the greeter's axiom does the same for as long as the greeter runs.
- **Monitors page:** reads the profile the daemon matched from `compositor.state` on every compositor.
- **Size:** QML loses about 90 lines (`_applySavedProfile` and its flags, `_outputRules`, the greeter branch, `matchProfile`/`savedRules`). Go gains about 200: the output reads, the picker, the watch.
- **Leaves:** the Lua picker as a second implementation, but one that's tested against Go rather than kept in step by hand.

#### B. Go switches on every compositor, Hyprland included
- **Lua:** shrinks to the `hl.monitor` calls of the profile matched now (`render.MonitorCalls`). `applyMonitors`, `AXIOM_MONITOR_SUBS` and the `outputProfiles` capability (with every branch on it) go.
- **Size:** deletes the most, about 60 more lines than A. Leaves no second picker at all.
- **Costs:** Hyprland's managed and included configs stop switching when axiom isn't running. Every hotplug waits for a daemon round trip, during which Hyprland lays the new monitor out its own way first, so a visible modeset and then a second one. Every hotplug also rewrites Hyprland's module, so that a reload keeps the profile.

#### C. The shell keeps the trigger; Go picks and applies
- **What changes:** a new method `outputs.applySaved`, sent on each `outputsHotplugged` by the session and the greeter alike (the greeter's qs sees hotplugs too, which closes its gap). Go reads the outputs, picks, applies, and fills `outputRules` from its last read.
- **Size:** the least Go, with no watcher.
- **Costs:** a hotplug during a qs reload or crash is missed, and each hotplug still makes two reads. The reactor stays in QML, so the switch still depends on the shell being up, which is the dependency the decision is meant to remove. A's watch is about 20 lines over a Tracker the daemon already runs, so C saves little.

### Recommendation
**A** was recommended, for keeping Hyprland's switching without axiom. **B** was chosen: one picker, in Go, on every compositor, and a Hyprland whose files don't switch while axiom isn't running is the user's doing.

### Items
1. **One Go picker.** `render.MatchProfile(profiles, outputs)` and `render.SavedRules(profiles, outputs)`: the rule from `MonitorLayout.matchProfile` (an exact match wins, else the one turning on most, ties to the earlier), its `tst_MonitorLayout` cases ported to a Go table test. Nothing calls it yet; nothing in QML or the Lua changes.
2. **Go reads the outputs on every compositor.** `ipc.Sway` (`GET_OUTPUTS`), `ipc.Niri` (`Outputs`) and `ipc.Hypr` (`monitors all`) each return the neutral `{name, description, disabled}`, with descriptions built the way `SwayState`, `NiriState` and Hyprland's monitors JSON give the shell ("make model serial", "Unknown" parts dropped). Fixture tests from recorded replies.
3. **Done:** **The session switches in Go on sway and niri.** `manager.Manager` watches the daemon's `Tracker.OnChange` (debounced) and re-reads the outputs. It applies `SavedRules` live (`applyOutputs` moved where `Manager` can call it), and `buildInputs` fills the output rules from that read, so included and managed files are rewritten. In detached mode it applies again after a reload, replacing `MonitorManager`'s `configReloaded` branch.
   - **Deletes:** `Facts.OutputRules`, CompositorConfigManager's `_outputRules`, MonitorManager's `_applySavedProfile`, `_applyProfilePending`, its reload branch and `useWholeScale`'s apply flag.
   - **Trial Apply:** a hotplug during a trial Apply closes the Keep prompt without reverting, because the daemon has already applied the saved profile for the new set (the smallest handling of a rare path).
   - Docs: `compositor/sway-backend.md`, `niri-backend.md`.
4. **Done:** **The greeter switches in Go on sway.** (MonitorLayout's `savedRules`, left with no caller, went with it, its `tst_MonitorLayout` cases too.) `greeter.compositor` (`applyGreeter`) also starts the same watch for the greeter's lifetime, applying the bundle's `SavedRules` on each change. Deletes `GreetdManager._applyCompositor`'s `savedRules` branch. Hyprland's greeter keeps its Lua until item 5. Docs: `features/greeter-runtime.md`.
5. **Done:** **Hyprland switches through Go.** The watch from items 3 and 4 runs on Hyprland too, session and greeter. The module, the managed config and the runtime Lua carry only `render.MonitorCalls` of the profile matched at the last read, rewritten on each switch so a Hyprland reload keeps it (the writer's `monitorsApplied` key went: the profile switch applies the profile in every mode, and again after a reload in detached mode, so the runtime Lua carries no monitors). Without axiom running, Hyprland keeps the layout last written and switches no more: user error, as decided.
   - **Deletes:** `render.MonitorsLua`, `applyMonitors`, `AXIOM_MONITOR_SUBS`, `GreeterLua`'s picker (it sends the match's calls), `TestMonitorsLuaPicks`, and the `outputProfiles` capability with every branch and doc line on it (`HyprlandManager`'s `supports`, `compositor/contract.md`, the backends' "Not:" lists).
   - Docs: `hyprland/monitors.md`, `compositor/contract.md`.
6. **Done:** **A Hyprland hotplug modesets once where the profiles agree.** (Built as `render.HyprlandRules`: the agreed rule for each output the matched profile leaves out, connected or not (maintainer, on #188: connected ones too, or a monitor just plugged modesets again once the switch picks a profile not naming it), none where profiles disagree, which leaves Hyprland its own layout as `preferred`/`auto` did. The candidate was not taken: `MatchProfile` counts only enabled outputs, so a monitor held dark never picks its profile, and one no profile names, alone at login, leaves no monitor on. Detached mode runs the switch too, its eval holding the agreed rules until a reload.) B's cost: Hyprland lays a new monitor out itself before the daemon's switch lands, then again. For each output the matched profile leaves out, the written Lua gives the rule every profile naming it agrees on (an external monitor always set the same way, the common case), else `preferred`/`auto` as the Lua does now; and on Hyprland the watch switches on the first change without the debounce. A monitor whose rule differs between profiles still modesets twice; that's the cost B accepts. A table test over `MonitorCalls`' output. Candidate to check first (maintainer, 2026-10-28: "add that to item 6"): write the rule for outputs no profile names as disabled, so Hyprland lights nothing new until the daemon has picked, and no monitor modesets twice; a new monitor then stays dark while axiom isn't running (user error, per the decision). It applies in managed and included mode (in included, the user's own monitor rules can override it: user error too); detached writes no config, so confirm whether the runtime switch still runs there and say what it does.
7. **The Monitors page asks the daemon** (folds in "The monitor profile picker exists twice"). `compositor.state` carries the matched saved profile's name, or `""` for none, from the last read. `MonitorManager.liveProfile` and `_detect` find that name in the draft (names are unique, and the draft equals the saved config whenever `_detect` runs).
   - **Deletes:** `MonitorLayout.matchProfile` with its `tst_MonitorLayout` cases, and this plan file.
