# Touchpad settings apart from the mouse's

> **Issue:** Mouse speed, acceleration and left-handed reach the touchpad only on Hyprland; now its items in [Phase 11](../roadmap.md#phase-11-audits-clear-out-and-hardening)
> **Status:** decided: A, the touchpad's own fields, written per touchpad on Hyprland by the Lua itself (2026-11-05). The maintainer's answers, verbatim: "1 keep following the mouse." / "2 . recommend" / "3. note the touchpad needs independent configuration (i.e. its own acceleration)"

### Problem
Input's Mouse part (`mouse.accel`, `.sensitivity`, `.leftHanded`, `qml/config/schema/sections/Input.yaml`) is written on Hyprland as the global `input.accel_profile` / `input.sensitivity` / `input.left_handed` (`render.ConfigTable` through `render.InputLua`, into the module's `M.input()` and the live lines `hyprWriter.liveLines` evaluates). Hyprland applies those to every pointer, the touchpad included, while sway's `input type:pointer …` and niri's `input.mouse.*` leave the touchpad alone. The Touchpad part has no speed, acceleration or left-handed fields of its own, so no compositor lets a touchpad be set apart from the mouse. Decided by the maintainer: "Mouse and touchpad settings need to be seperate (i.e. one should be able to turn on mouse acceleration for touchpad only and adjust it seperatly)." Affects every laptop user who sets the Mouse part, on Hyprland most of all.

What the compositors offer (Hyprland checked against its Lua stubs, `/usr/share/hypr/stubs/hl.meta.lua`, 0.57.1 installed; axiom targets 0.55+):
- **sway:** `input type:touchpad accel_profile|pointer_accel|left_handed`, beside the `type:pointer` lines it already writes.
- **niri:** `input.touchpad.accel-profile|accel-speed|left-handed`, beside `input.mouse.*`.
- **Hyprland:** `input.touchpad.*` has no `accel_profile`, `sensitivity` or `left_handed`; those exist only globally (`input.*`) or per device, `hl.device({ name = …, accel_profile = …, sensitivity = …, left_handed = … })`, which wins over the global for that device. There are no device rules by type. `hl.get_devices()` lists devices (`name`, `type`), but a touchpad's `type` is `"pointer"` like a mouse's, so only its name tells them apart (libinput's names: `…-touchpad`, `…-trackpad`, `…-clickpad`). No Lua event fires when a device connects. axiom detects no input devices anywhere today (backend nor shell).

### Options
#### A. Touchpad's own fields; Hyprland writes them per touchpad, found by the Lua itself
The Touchpad part gets `accel`, `sensitivity` and `leftHanded`, mirroring the mouse's. sway and niri take them as plain `x-compositor` keys. On Hyprland a new spec form (`{device: touchpad, key: sensitivity, …}`) routes a field out of the `hl.config()` table into one `hl.device()` per touchpad, the touchpads found where the Lua runs: a loop over `hl.get_devices()` matching pointer names on `touchpad|trackpad|clickpad`. The Mouse part stays global, so every mouse (a hot-plugged one too) keeps working as now. The same Lua runs in the module, the live eval and the greeter's Hyprland, so nothing new is detected or passed around. Costs a small renderer change, its goldens and a test. Risks: a touchpad whose name says none of those words is missed (it follows the mouse, as today); a touchpad connected after the last apply gets no block until the next reload or live apply; whether `hl.get_devices()` already lists devices when the config first loads at Hyprland's start must be checked (the daemon's apply after every reload covers it otherwise).

#### B. The same fields; the daemon finds the touchpads
As A, but the daemon lists touchpads from udev (`ID_INPUT_TOUCHPAD=1` under `/run/udev/data/`, names from `/sys/class/input/event*/device/name`), turned into Hyprland's device names (lowercased, spaces to `-`, Hyprland's `-1` suffix for repeats), and bakes them into the file and the live lines. More exact than a name match, but the name conversion has to track Hyprland's own, the list goes stale on hotplug just the same, the greeter would need its own detection, and it adds a device-listing piece to the daemon for one compositor.

#### C. Every pointer per device, nothing global
The Mouse part also moves to `hl.device()` blocks, one per mouse, so neither part ever writes `input.*` and each part reaches only its own devices, even with the other off. The fullest separation, but a mouse plugged in after an apply (common, unlike a touchpad) keeps Hyprland's own settings until the next one, and every mouse name would need finding the same way as in A or B.

### Recommendation
A. It gives the touchpad its own acceleration, speed and buttons on all three compositors with the least new machinery: no device detection in Go, the same rendered Lua in every place that applies the input, and the mouse's behaviour unchanged. A's name match misses only odd touchpads, which then behave exactly as today; if one turns up, a machine-scoped device-name setting can be added then (logged, not built up front). B's exactness doesn't pay for its name conversion and extra daemon piece; C trades a rare hotplug gap (touchpads) for a common one (mice).

Questions for the maintainer:
1. **The Mouse part on, the Touchpad part off, on Hyprland:** the touchpad then still follows the global `input.*`, the mouse's values, as it does under Hyprland's own config. Leave it so (the Touchpad part off means "your compositor's own config applies", and a user's own `hl.device` for the touchpad stands) and say so in the Mouse part's description, or pin every touchpad to the device defaults whenever the Mouse part is on (the mouse never reaches it, as on sway and niri, but that overrides a user's own touchpad block while axiom's Touchpad part is off)? Recommended: leave it, with the description line.
2. **A format-2 migration:** the new fields need none (their defaults are filled at load: "Device default" accel, speed 0, right-handed). A step could copy `mouse.accel` / `.sensitivity` / `.leftHanded` into the touchpad's for configs with both parts on, so a Hyprland user's touchpad keeps the feel it had; but the config doesn't know its compositor, so the same step would change the touchpad of a sway or niri user, whose touchpad never followed the mouse. Recommended: no migration.

### Items
1. **Hyprland's per-touchpad Lua** (small): `render.ConfigTable` sets aside fields whose `x-compositor.hyprland` spec names `device: touchpad`, and `render.InputLua` / `GreeterLua` emit them as one `hl.device()` per pointer from `hl.get_devices()` whose name matches `touchpad|trackpad|clickpad`, each in a `pcall`; Go tests, goldens (`TestGoldenFiles`), and a check in nested Hyprland that a live eval applies to a connected touchpad and that the first load at start sees the devices (else the start's apply covers it, written down in the doc).
2. **The Touchpad part's three fields** (small): `touchpad.accel`, `.sensitivity`, `.leftHanded` in `Input.yaml` (same titles, enum, range, `x-greeter`, `x-scope` as the mouse's; sway `input type:touchpad accel_profile|pointer_accel|left_handed`, niri `input.touchpad.accel-profile|accel-speed|left-handed`, Hyprland the item 1 form), their `InputConfig` reader properties, the sway and niri goldens, `docs/dev/compositor/config-modes.md`' input lines and the greeter doc's.
3. **The Mouse part's description on Hyprland** (trivial): per answer 1 ("keep following the mouse"), a description line saying the Mouse part reaches a touchpad whose own part is off on Hyprland, and per answer 3, that the touchpad needs independent configuration (its own acceleration) through the Touchpad part's fields from item 2. No migration (answer 2).
